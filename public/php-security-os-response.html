独自ビルドは何が公開済み？

「ビルド成功」と「今のAL2 PHPをそのまま置換できる」は別です。
公開RPMは独立prefixの限定構成です。GD・mbstring・intl・zipなど、通常のAL2 Extraにある拡張が既存の最小RPMには不足しています。従来の独自構成を拡張するPR #2は、方針変更によりDraftのまま停止しています。現在はAWS公式SRPM / specを基準に、subpackage名・配置・設定・既存AWS patchsetを維持し、今回の対策と独自release IDを加えて再ビルドする案を精査中です。当面の自作対象は7.4 / 8.0 / 8.1で、8.2は到着を確認したAWS公式8.2.35の評価を優先します。この新方針のReleaseは未公開で、従来の7成果物を置き換えたわけではありません。

FIRST: BUILD IT YOURSELF?

セルフビルドして「今のPHPの横に置く」案は？

有力な候補です。「誰かのRPMを探す」だけではなく、今回の対策を含む公式ソースからPHPを自分で作り、いまのPHPを上書きせず別の場所へ置く方法があります。ただし、作れたことと、安全に本番へ切り替えられたことは別です。

今回やること・まだやっていないこと
以下はAL2上で7.4 / 8.0 / 8.1を維持する場合の設計・確認手順です。実環境の版・CPU・拡張は未確認で、build、配置、FPM起動、設定変更、切替は実行していません。旧3系列の公式ソースはEOL版向けの最小限対策で、一般の保守再開・現行版と同じ正式修正版を保証するものではありません。

最初に、言葉を3組だけ

ソース → build

ソースはプログラムの設計図。コンパイルを含むbuildは、設計図からサーバーで動く実行ファイルを作る工程です。今回は「今回の対策を含む、正確な版の設計図」が必要です。

成果物 → RPM

成果物は作ったPHP本体・拡張等のファイル一式。RPMはそれを梱包し、版・依存・配置・削除を管理する形式です。セルフビルドとRPMは二択ではなく、自分でbuildしてRPMに包むこともできます。

別配置 → FPM

例として標準PHPを残し、新PHPを/opt/php81-fixed-BUILD_ID/等へ別置き（説明用で、実行先は未決定）。同じpathの中身を上書きせず、buildごとに配置を分けて戻せる設計です。FPMはWebサーバーから依頼を受けてPHPを動かすプロセスです。新旧で別のFPM本体・設定・受付口を用意します。

8段階。置いただけで終わりにしない

  1. 01正しい設計図を固定7.4 / 8.0 / 8.1の今回CVE専用枝とcommitを指定。普通の旧枝・適当なforkでは代用しない
  2. 02隔離環境で作る同じAL2・CPU向けに、使う拡張と依存を揃える。本番でいきなりbuildしない
  3. 03作った物の台帳を残すsource・patch・build条件と、PHP / 拡張一式のhashを対応付ける。必要なら別名RPM化
  4. 04標準を壊さず別置き/opt配下等は例。OSの標準PHP、全体PATHやリンクを即上書きしない
  5. 05新PHP専用のFPM別のFPM master / service・ini・拡張・socketを用意。同じ古いFPMにpoolを足すだけでは不可
  6. 06少数の処理で試す閉じた試験環境から、許可したhandler / 接続先だけ新FPMへ。ログイン・upload・DB等を確認
  7. 07実際の稼働まで確認全Web経路・CLI・cron・queueを別々に照合。古いworkerが残れば完了ではない
  8. 08戻す条件も先に決める旧成果物・設定・状態互換を保持。ただし戻せば再び脆弱なので、公開隔離付きの明示rollbackにする

配置と、処理の行き先は別のこと

いまのPHP

標準のPHP / FPMと設定は保持する。これは「検証中も脆弱な旧系を公開し続けてよい」という意味ではありません。

新しく作ったPHP

別配置・別FPM・別socket。Webサーバーの限定した接続先だけを新側へ向け、動作と負荷を確認してから対象を広げる設計です。

重要：新しい実行ファイルを置いても、Webサーバーが古いFPMへ依頼を送り続ければ、サイトは直っていません。逆にWebだけ切り替えても、cron / queueが古いPHPを動かしていれば、その実体は別に残ります。エラー時に古いPHPへ自動で戻る設定も見落とし対象です。

「今の設定や拡張が、そのまま使える」は未確認です。
別配置では既存AWS RPMのpatch・既定値・設定を自動継承しません。PHP拡張の.soを無条件コピーせず、API / ZTS / debug・CPU・リンク先を合わせます。PHP 7.4 / 8.0はOpenSSL 3.xをそのまま使えない条件もあるため、AL2全体のlibraryを置換して解決しません。

Apacheのmod_phpを使っているなら別設計。これはApache内へPHPを組み込む方式なので、上の「新FPMを横に置いてsocketだけ切替」をそのまま当てはめません。FPMへの接続方式変更や別backend Webを検討し、Apache設定・アプリ互換も検証する段階があります。いまの実SAPIをまず確定します。

WHY IT MATTERS

何がエクスプロイトにつながるの？

アプリのログイン画面だけでは守り切れない、PHP内部のメモリ・リクエスト状態管理の問題です。影響はWeb workerの権限での未認証のコード実行。単なる「アップロードファイルの拡張子チェック漏れ」ではありません。以下は原因の概念図で、攻撃用データや手順ではありません。

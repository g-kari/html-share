FIRST: BUILD IT YOURSELF?

セルフビルドして「今のPHPの横に置く」案は？

有力な候補です。「誰かのRPMを探す」だけではなく、今回の対策を含む公式ソースからPHPを自分で作り、いまのPHPを上書きせず別の場所へ置く方法があります。ただし、作れたことと、安全に本番へ切り替えられたことは別です。

今回やること・まだやっていないこと
以下はAL2上で7.4 / 8.0 / 8.1を維持する場合の設計・確認手順です。実環境の版・CPU・拡張は未確認で、build、配置、FPM起動、設定変更、切替は実行していません。旧3系列の公式ソースはEOL版向けの最小限対策で、一般の保守再開・現行版と同じ正式修正版を保証するものではありません。

最初に、言葉を3組だけ

ソース → build

ソースはプログラムの設計図。コンパイルを含むbuildは、設計図からサーバーで動く実行ファイルを作る工程です。今回は「今回の対策を含む、正確な版の設計図」が必要です。

成果物 → RPM

成果物は作ったPHP本体・拡張等のファイル一式。RPMはそれを梱包し、版・依存・配置・削除を管理する形式です。セルフビルドとRPMは二択ではなく、自分でbuildしてRPMに包むこともできます。

別配置 → FPM

例として標準PHPを残し、新PHPを/opt/php81-fixed-BUILD_ID/等へ別置き（説明用で、実行先は未決定）。同じpathの中身を上書きせず、buildごとに配置を分けて戻せる設計です。FPMはWebサーバーから依頼を受けてPHPを動かすプロセスです。新旧で別のFPM本体・設定・受付口を用意します。

いまのPHP

標準のPHP / FPMと設定は保持する。これは「検証中も脆弱な旧系を公開し続けてよい」という意味ではありません。

「今の設定や拡張が、そのまま使える」は未確認です。

WHY IT MATTERS

何がエクスプロイトにつながるの？

アプリのログイン画面だけでは守り切れない、PHP内部のメモリ・リクエスト状態管理の問題です。影響はWeb workerの権限での未認証のコード実行。単なる「アップロードファイルの拡張子チェック漏れ」ではありません。以下は原因の概念図で、攻撃用データや手順ではありません。

CVE-2026-109618 · OOM

メモリ不足で
作りかけの状態が残る

入力処理等でメモリ不足OOM = Out Of Memory
↓
初期化途中の処理を中断内部データが不完全なまま
↓
後片付けが正しいデータだと思う不正なメモリ参照からコード実行へ

mod_phpはリクエスト開始に失敗しても後片付けを行うため、アプリの認証・入力チェックが動く前に成立する実証があります。FPMは開始失敗時にchildを終了するため同じ経路は残りませんが、正常開始後のアプリ処理でOOMになる場合は別に影響し得ます。

状態を残す処理＋次に使う処理＋同じworkerの組合せが条件です。セッション経路のRCEはmod_phpとFPMで実証されています。FPM側は正常開始後に適切なアプリ処理・fatal error等が必要。session_start()を呼ばないサイトでも、それだけで対象外とは言えません。

「全Web PHPに更新推奨」と「全部で同じ攻撃を実証」は違います。OOMの完全なRCE実証はmod_php、FPMのOOMはソース解析上の影響で完全な攻撃実証は未確認。FrankenPHP / LSAPIにも類似性から影響が考えられますが、同じ実証レベルとはしません。一方、stale stateのセッション経路ではFPMでも実証があります。

追加のCVE-2026-115560は、先の2件と何が違う？

PHP本家の10/23 informational advisoryを、10/24 05:08 JST（10/23 20:08 UTC）に確認しました。

セッションのupload progress機能に関する、まれな設定とアプリコードの組合せで起きる追加のRCE経路です。PHPは通常のbugfixリリース周期で扱い、次回リリース時に完全なadvisoryを出すと案内しています。次回の正確な日付、完全な影響バージョン表、各OSの修正packageは、この情報告知だけでは未確認です。

次の条件が重なる場合、という限定です

条件1

機能が有効

session.upload_progress.enabledが有効なまま。

条件2

最初の設定

session.serialize_handlerをphp_binaryまたはphp_serializeに設定している。

条件3

アプリで実行時に変更

session_start()より前に、ini_set()でhandlerをphpへ切り替える。

アプリが実行時にserialize handlerを変更しない場合、この追加CVEの条件には該当しないというPHP公式説明です。「追加CVEには非該当」と「元の109618 / 109619も安全」は別で、以前の更新や対策を解除する理由にはしません。

互換性と依存：同系列だから無試験でよい、ではない

3系列とも内蔵session upload progressをスキップしますが、ファイルupload全体を無効にする修正ではありません。変更したOOM経路では、そのコードを実行したprocessを即時終了。親や全workerが常に落ちる意味ではなく、SAPI・process / thread構成と補充方法により影響が異なります。request-shutdown、未完了request、worker再生成、8.1 OPcacheを回帰確認します。

compileの最低条件と、依存の安全性は別です。OpenSSLは7.4 / 8.0が1.0.1以上・3.0未満、8.1が1.0.2以上・4.0未満。7.4はlibxml2 2.7.6以上 / curl拡張libcurl 7.15.5以上、8.0 / 8.1はlibxml2 2.9.0以上 / libcurl 7.29.0以上がsource上の条件です。古い最低版を今安全と推奨したり、AL2全体のOpenSSLを3.xへ置換して解決したりしません。glibc最低版は未確認の値を補わず、実リンクsymbol / runtime / CPUで確認します。

拡張のAPI・ZTS・debug・リンク先を照合し、閉源loader等が対応しなければ停止。同じ系列でも古い.soのコピーだけで互換と判定しません。Git専用treeからのconfigure再生成とrelease tarballでは必要toolが異なり、ビルド成功だけでは本番互換の証拠になりません。

A SAFE CHECKLIST

自分の環境を確認する順番

  1. 導入元を知る：OS公式、外部リポジトリ、Homebrew、Dockerイメージ、ホスティング管理画面、製品同梱のどれか。
  2. 全部の実体を把握：Web用PHP-FPM / Apache、CLI、ジョブ、別コンテナは同じ版・設定とは限りません。
  3. 公式のCVE別修正版と照合：PHP表示の短い版だけでなく、完全なパッケージ番号、対象リポジトリ・ストリーム・OS・CPUを確認。
  4. 適用後を別確認：ファイル更新、稼働プロセスの切替、通常のログイン・アップロード等の動作確認を分け、反映して初めて対応完了とします。

製品・機器に同梱されたPHPは、開発元・提供元のマニュアルや公開セキュリティ情報も確認します。ただし、利用状況が不明な全製品を一つずつ個別調査するところまで広げる指示ではありません。IPA：公開前の棚卸し指針（修正版未公開という予告部分は当時の情報。現在の版は本ページ先頭のPHP本家告知を参照）

管理者向け：読み取り確認の例と注意

php -vとphp --iniはCLIの情報です。これだけでWeb側も安全とは確認できません。パッケージ管理情報で完全な版と導入元を調べ、Web用プロセス・管理画面・デプロイ記録と照合してください。

公開phpinfoページの新設、攻撃文字列やPoCの送信、外部サイトへの脆弱性スキャンは不要です。この調査では行っていません。

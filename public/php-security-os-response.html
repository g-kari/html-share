WHY IT MATTERS

何がエクスプロイトにつながるの？

アプリのログイン画面だけでは守り切れない、PHP内部のメモリ・リクエスト状態管理の問題です。影響はWeb workerの権限での未認証のコード実行。単なる「アップロードファイルの拡張子チェック漏れ」ではありません。以下は原因の概念図で、攻撃用データや手順ではありません。

CVE-2026-109618 · OOM

メモリ不足で
作りかけの状態が残る

入力処理等でメモリ不足OOM = Out Of Memory
↓
初期化途中の処理を中断内部データが不完全なまま
↓
後片付けが正しいデータだと思う不正なメモリ参照からコード実行へ

mod_phpはリクエスト開始に失敗しても後片付けを行うため、アプリの認証・入力チェックが動く前に成立する実証があります。FPMは開始失敗時にchildを終了するため同じ経路は残りませんが、正常開始後のアプリ処理でOOMになる場合は別に影響し得ます。

状態を残す処理＋次に使う処理＋同じworkerの組合せが条件です。セッション経路のRCEはmod_phpとFPMで実証されています。FPM側は正常開始後に適切なアプリ処理・fatal error等が必要。session_start()を呼ばないサイトでも、それだけで対象外とは言えません。

採用ゲート：FastCGIはHTTPSではありません。FPM TCPはbackendのprivate側にbindし、listen.allowed_clients（未設定なら全IP許可）とfirewall / SGでfrontを明示allowlistし、信頼境界を跨ぐ場合の認証付き暗号化経路を確認するまで切替不可。インターネットへの直公開は禁止し、pool分離だけをsecurity隔離と数えません。IP制限は暗号化の代わりではなく、既存の承認済み保護経路で成立するかを確認します。PHPソースは自動転送されずbackendにも同じcode / vendorと正しいSCRIPT_FILENAME / docrootが必要です。

uploadの一時ファイルはbackend側。永続media、session保存・serializer、cache、DB / queue、UID / lock、timeout / worker容量を検証し、session / upload等を壊さずroutingを戻せることが条件です。

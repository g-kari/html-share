教訓は、個別の手口より一段上にある

四つの事例は同じ原因ではない。共通の問いは「なぜその行為が可能だったか」「どこで被害を止められたか」「改善したと何で証明するか」。以下は事例を横断する本ページの分析であり、各社の非公表の根本原因を認定するものではない。

  1. 入口・操作

    侵入、正規権限の悪用、誤った選択が起きうる。

  2. 到達範囲

    一つの権限や作業場所から、別の領域へ広がる。

  3. データ量

    必要以上に読める・まとめられる・運び出せる。

  4. 観測・介入

    異常を検知し、判断して、途中で止められるか。

  5. 説明・回復

    対象を特定し、知らせ、安全に業務を戻せるか。

検討モデル。すべての事案がこの順序で起きたという主張でも、被害を数式化したものでもない。

注意力を、最後の防壁にしない

教育は必要。それだけに依存せず、混入・誤送付・過大権限を起こしにくい工程を作り、失敗を模擬して確かめる。

防御を、独立した層にする

入口が破られても、権限・データ境界・持ち出し制御・検知・復旧が一緒に無効にならない設計を目指す。

説明の確度を、維持する

閲覧、持ち出し、公開を区別する。未確認を安全と読み替えず、詳しい説明を不利にする採点もしない。

我々への問い：「対策を導入した」と言えるかより、「同じ失敗条件を入れたときに、どこで止まるか」を答えられるか。

このページは一般的な改善案。特定の組織に存在しない欠陥を推定したり、実施済み・実施予定の作業を宣言したりはしない。

経営・意思決定

「止まらないよう祈るだけなら、経営ではなく賭けだ。」

俯瞰評価・改善案失敗しない人を求めるより、失敗しても損失が限定される予算・権限・責任を設計する。事故件数だけで現場を評価すると、早期報告を避ける誘因を生む可能性がある。

判断すること
止められない重要業務、許容停止時間、保有が必要な情報、残す例外を決める。業務責任者が対策の優先順位と残余リスクを引き受ける。

設計・開発

「ひとつの入口から、なぜ台帳まで届く？ 境界を描いただけでは壁にならぬ。」

俯瞰評価・改善案認証の成功と、その後に読めるデータ量は別の問題。侵入の防止に加え、利用目的ごとに到達範囲を絞る。誤送付も、宛先と内容の不一致を許す設計として検討する。

判断すること

運用・防御・復旧

「導入した、で満足するか。鳴るか、止まるか、戻るかを試せ。」

俯瞰評価・改善案防御の有無より、実際に危険な行為を検出して人が対応できるかを見る。外部攻撃、正規権限の悪用、誤操作で観測ポイントは異なる。

判断すること
誰が異常を受け、何を根拠に遮断し、どの順で復旧するかを決める。攻撃された本番とは別の経路で証拠と連絡手段を保つ。
変える仕組み
公開面の脆弱性修正期限と未修正時の暫定防御、重要なログの保存・改変防止、抽出・権限変更・送付の検出、到達範囲の制限、バックアップの保護と復元テスト。必要なサービスには耐フィッシングMFAを検討する。
確かめる証拠
安全な模擬イベントから通知・判断までの時間、権限失効の反映、代表データの復元結果。バックアップの取得成功と復元成功を分けて記録する。

代償・限界：検知を増やすほど誤報も増えうる。重大な操作を先に絞り、対応容量に合わせて調整する。復元できても、既に持ち出されたデータの機密性は戻らない。

委託・サプライチェーン

「任せたから終わり？ 責任まで封筒に入れて送れたつもりか。」

判断すること

利用者・被影響者

「不安だけ渡して「ご注意を」で済ますか。人が動ける情報を渡せ。」

社会・制度・学習

「数だけ並べて裁くか。明日も同じ事故を作るなら、その採点こそ愚かだ。」

発生日・発見日・公表日、件数・人数、確認済み・可能性を区別する。公表資料だけでは見えない統制は、未確認として残す。

EDRの具体的な手順

コンテナ・サーバーレス

ホストを管理できるかで分ける。EC2ノードとFargate/Lambda/Workersを同じ導入手順にしない。対応runtime検知と、イメージ/依存・IAM・アプリ認可・監査を組み合わせる。

配置別に選ぶ

Web/API・アプリの欠陥

コードの境界：既存frameworkの認可・エスケープ・CSRFを活かし、必要ならZod、pg、Helmet、DOMPurify、rate limiter等。ライブラリを入れた後の設定と否定テストまでが仕事。

コード側の具体策

最小の実装セット：重要資産の範囲 → 認証/認可・公開面/データ境界 → 配置に合う実行時検知 → 修正工程 → 監査と当番通知 → 復旧試験。『最小』は無料や、これだけで完全防御という意味ではない。

必要なcoverageを持つ既存機能を優先。新しいエージェントや依存は、互換性・CPU/RAM・権限・送信データ・契約・維持費も増やす。いきなり本番全体へ適用せず、代表構成で検証する。

「EDRを入れる」の意味を、配置別に決める

EC2 / Azure VM / GCE のWindows・Linux

顧客管理OSに対応するEDR sensorを入れる。Windows EC2にはGuardDuty Runtime Monitoringを当てはめず、対応するサーバーEDRで調査/隔離を設計。OSとagentの互換性、AV競合、アウトバウンド接続が前提。

EKS・ECSのEC2ノード

ホストEDRやGuardDutyを、対応Linuxノードの範囲で検討。EKSはGuardDuty add-on、ECS on EC2はEC2 host agentで監視。ノードを守っただけでアプリ内の認可・tenant分離が成立するわけではない。

ECS Fargate

一般的なサーバーEDRを基盤ホストへ自由にインストールする手順は使わない。GuardDuty-managed sidecarはLinux ECS Fargateの新規タスクに入る。既存taskの置換、execution role、イメージ取得/テレメトリの接続を確認。EKS Fargateとは別。

Lambda / Cloud Run / Workers 等

一般的なVM向けhost agentを基盤OSへ入れる前提にしない。対応するサービス固有の検知、コード/依存scan、最小IAM、外部通信、認可・監査・設定の防御を選ぶ。AWS Lambda Protectionはネットワーク活動の別機能で、Lambda@Edgeは対象外。

目的から選ぶ、導入・設定レシピ

VMにEDRを入れる：Microsoft Defender for Endpoint

EC2・Azure VM・GCEなど、自分でOSを管理するWindows/Linuxサーバーで、実行時の調査と端末隔離まで必要な場合の具体例。以下はMicrosoft製品での実装例であり、既存EDRが同等の要件を満たすなら二重導入を先に決めない。

入れる・有効にする
サーバー向けライセンスを確認し、OS・版・CPUアーキテクチャ・カーネルの対応表を照合。直接導入ならDefenderポータルの Settings → Endpoints → Device management → Onboarding でOSを選び、公式オンボーディングパッケージを配布する。LinuxはMicrosoft公式リポジトリの署名済み mdatp を導入してオンボード。Windows Server 2019/2022/2025は組み込みAV/EDRをオンボードし、主AVとして使うならreal-time/behavior monitoring・cloud protectionのpolicyを確認する。
Linuxは初期のAVがpassive mode。主AVとして使うなら、競合・性能確認後にreal-time enforcement、behavior monitoring、cloud protection、定義更新を明示的に有効化する。
観測するもの
プロセス・ファイル・通信のEDRテレメトリとAV検出。Linuxは mdatp health と mdatp health --details edr を確認。Windowsは sc.exe query sense と Get-MpComputerStatus でEDR稼働とAV設定を別々に見る。
通知から対応へ
担当者がDefenderのアラート・端末タイムラインを調査。隔離が妥当なら端末ページの Isolate device を実行し、Action centerで成功を確認する手順を準備する。申請・Pendingは完了扱いにしない。Linuxのiptables/ip6tables・カーネル要件を確認し、隔離中はSSH・SSM・業務通信が切れる可能性を前提にする。公式文書では7日後に隔離が自動解除され、Linuxのfirewall rule変更でも解除されうるため、隔離を永久の封じ込めと見なさない。
完了の証拠
ポータルで対象VMとの対応、Onboarded、Active、最近の報告を確認。Linuxはhealthy、想定org_id/edr_machine_id、最新定義、主AVならpassive_mode_enabled=false・real_time_protection_enabled=trueなどを確認。検証用VMで公式AVテストとEDR検知テストを別々に行い、端末タイムライン・通知・隔離/解除を記録する。AVのEICAR検知だけでEDRまで合格にしない。
費用・限界
サーバー数・稼働時間・契約/プラン・追加ログ/運用費。Defender for Servers P1/P2はMDE P2相当のサーバー保護を含むが、クライアント用MDE P1と同じ意味ではない。MDEの licensed=true は商用契約確認の代わりにならない。AL2 ARM64対応は2026-10-31終了予定。AL2 x64まで同日終了とは一般化しない。Linux隔離とWindowsの選択的隔離は機能差がある。

AWSの実行時検知を足す：GuardDuty Runtime Monitoring

Linux EC2、EC2上のECS、EC2上のEKS/EKS Auto Mode、Linux ECS Fargateの実行時挙動をAWS側のfindingにつなげる。端末EDR・AV・自動隔離を丸ごと代替する機能ではない。

入れる・有効にする
対象アカウント・Regionで GuardDuty → Runtime Monitoring → Configuration → Enable。次にリソース別のエージェント配備を行う。
EC2：SSM管理対象でFleet Managerに表示されることを確かめ、EC2 automated agent configurationを設定。手動なら公式SSM文書 AmazonGuardDuty-ConfigureRuntimeMonitoringSsmPlugin のRun CommandでInstall、パッケージ AmazonGuardDuty-RuntimeMonitoringSsmPlugin を指定。
EKS：自動配備または対応する aws-guardduty-agent add-on。ECS Fargate：自動配備で新しいタスクにsidecarが入り、既存タスクは更新・置換が必要。
観測するもの
プロセス実行、ファイル、コマンドライン、通信などのテレメトリからfindingを生成。Runtime coverage のHealthy/UnhealthyとIssue、対象漏れ、エージェント版も観測する。機能をEnableしただけではカバーされない。
通知から対応へ
findingはEventBridgeへ送り当番が調査。Unhealthyも別経路で通知する。必要ならEDRやクラウドの封じ込め手順へつなぐ。最初からサンプルfindingを本番自動隔離へ直結させない。
完了の証拠
想定したすべてのリソース・アカウント・RegionがRuntime coverageでHealthy。Healthyは収集/配送の健全性であり無侵害の証明ではない。サンプルfindingで通知経路を試し、センサー健全性の確認とは分ける。
費用・限界
OS/カーネル/CPU・eBPF等・エージェント互換性・配備権限・テレメトリ到達性を公式表で確認。Windows、EKS Fargate、EKS Hybrid Nodes、ECS Anywhere、ECS Managed Instancesは対象外。ECS Managed EC2 Instancesという別の名称と混同しない。Lambdaにはこのホストエージェントを入れない。費用はvCPUと監視時間が基本だが、10/2以降のSecurity Hub統合課金は下記を参照。

修正すべき穴を見つける：Inspector＋修正の工程

VOISINGの教訓は「検知を入れた」で終わらないこと。スキャン、修正期限、暫定遮断、再スキャンを一つの工程にする。

入れる・有効にする
AWS例：Inspector → Account management → Activate で対象アカウント・Region・EC2/ECR/Lambdaのscan typeを選ぶ。EC2のOS更新は Systems Manager → Patch Manager のbaseline・対象・maintenance windowを設計。BI製品・自作アプリ・言語依存はベンダー更新とCIでの更新/再ビルドを別に持つ。
観測するもの
Inspectorの対象一覧、scan status、Last scanned、修正可能性と外部露出。EC2スキャンはSSMベースとEBSスナップショットのhybrid方式があり、常に「エージェント不要」とは言わない。
通知から対応へ
公開面で悪用される脆弱性は担当者と期限を決め、修正に間に合わない時の公開停止・アクセス制限を判断する。WAFルールで一時軽減しても、製品やコードの修正は継続する。
完了の証拠
対象漏れなし、対応した版/イメージへの置換、再スキャン、findingの解消、業務テスト。OSパッチ合格だけでBIアプリの脆弱性も直ったことにしない。
費用・限界
EC2稼働・ECR監視イメージ・Lambda数/scan typeなど。Security Hub Essentialsに含まれる能力は統合課金になる。スキャン結果はEDRの実行時挙動検知や隔離とは別で、未検出の脆弱性や業務ロジック欠陥は残りうる。

誰が何に触れたかを残す：API・通信・アプリ・DBを分ける

NTT西日本グループや情報持ち出しの教訓を、個人に結びつく操作記録と抽出の観測にする。一つのログにすべてが入ると期待しない。

入れる・有効にする
AWS例：CloudTrail → Trails で継続記録と保存先を設計。複数Region/組織の範囲を確認し、重要なS3バケット/プレフィックスの Data events を明示選択。VPC → Flow logs で必要なネットワークメタデータを保存。アプリは利用者ID・対象ID・操作・許可/拒否・件数を構造化記録。RDS PostgreSQLはpgAudit、RDS MySQLは対応するMARIADB_AUDIT_PLUGIN等を用途に合わせて検討。
観測するもの
CloudTrailはAWS API監査。Event historyはRegionごとの過去90日間のmanagement eventsで、S3 GetObject等のdata eventsやSQL実行ログの代替ではない。Flow Logsは通信メタデータで、パケット本文・SQL・ユーザーの操作意図は分からない。DB監査はクエリ本文/個人情報を増やすリスクもある。
通知から対応へ
重要データの大量取得、管理権限変更、監査停止等を、正常なバッチ処理との違いを踏まえて通知する。件数・時間帯・役割別の基準を定め、担当者が利用目的と資格情報を確認する。
完了の証拠
ダミーのS3オブジェクト読取、許可/拒否操作、検証用DBの読取を行い、各ログにactor・時刻・対象が出るかを照合。ログ削除/設定変更の権限と保持・復元性も点検する。
費用・限界
data events件数、CloudWatch/S3への取込・保管・検索、Flow Logs量、DB負荷。SQL本文・session token・秘密・不要な個人情報を安易に集めない。Session Managerの通常セッションログと、SSH/port forwardingで内容を記録できない制約を区別する。

一次資料：CloudTrailの範囲 / Data events / Flow Logs / pgAudit / MySQL監査 / セッションログ制約

広がらせない：非公開DB・小さいロール・設定チェック

セイコーマートから引く問いは、入口から会員台帳へ届く権限の範囲。ここでは当該事案の未公表の実装を推測せず、自分たちの境界を検証する。

入れる・有効にする
AWS例：RDSをPublicly accessible=falseとし、DBのSecurity Groupは必要なアプリSGから必要ポートだけ許可。アプリ・BI・抽出・バックアップのIAM/DB権限を分ける。人の保守は個別の短期権限とSSM等の経路を使い、長期の共用キーに依存しない。S3のBlock Public Accessは業務上の公開/共有要件を確認して適用。
観測するもの
AWS Configの restricted-ssh、rds-instance-public-access-check、s3-bucket-public-read-prohibited などと、IAM Access Analyzerの公開/クロスアカウント権限の検査。CloudTrailで設定変更を追跡する。
通知から対応へ
非準拠や新規外部共有を責任者へ通知。例外は理由・期限・対象を記録する。公開停止や権限変更は影響を確認して行い、自動修復で正当な公開/共有を壊さない。
完了の証拠
許可したアプリからはDBに接続でき、別経路/別役割からは拒否されること。ダミーの別顧客データを読めないこと。Config合格は設定上の一条件で、アプリ認可や実到達性のすべてを保証しない。
費用・限界
Config記録・ルール、必要な分析プラン、SSM/ログ/接続経路の費用。IAMとDBのGRANTは別の制御。SGの変更だけでは既存の追跡済み接続をすべて切断できない。セッション/資格情報の失効と独立した封じ込め確認を持つ。

一次資料：RDS/VPC / SSH設定検査 / RDS設定検査 / S3設定検査 / 共有の事前検証 / 既存接続の注意

持ち出せる量を減らす：BIの複製と送付工程を小さくする

VOISINGの分析基盤とTOPPANの混入事故からの改善案。暗号化やEDRだけで、正当な権限による全件抽出や宛先ミスを解決しようとしない。

入れる・有効にする
BIには必要な列・期間・集計値だけを渡し、実名や連絡先の複製が必要か見直す。顧客別の作業領域とロールを分ける。送付前にファイルの帰属ID・宛先ID・再帰的な内容一覧を機械照合し、不一致なら送れない工程にする。S3の所在把握には必要に応じて Macieのsensitive data discovery job を追加する。
観測するもの
アプリ/抽出ジョブの件数と利用者、送付manifestと承認、保持期限。MacieはS3内の対応形式の検査で、RDSや全SaaSを直接全件検査する汎用DLPではない。
通知から対応へ
不要な複製や想定外の混入を担当者が止める。例外抽出は目的・上限・期限付き承認。保存義務と業務影響を確認してからデータを削減し、漫然と監視目的で個人情報を増やさない。
完了の証拠
別顧客ファイルの混入、禁止列、期限外データ、大量抽出をダミーデータで試し、拒否と監査記録を確認する。復号できる正当な利用者への認可も別にテストする。
費用・限界
Macieの分析量・バケット監視、設計変更と継続運用。仮名化しても結合で再識別できる場合があり、匿名化と同一視しない。暗号化は鍵で読めるアカウントの権限過大を解決しない。

一次資料：Macieの対象と制約 / BIの再発防止策 / 送付工程の原因 / 操作ごとの認可

戻せることを試す：AWS Backup＋保護された保管先

バックアップ取得成功ではなく、安全な復元と業務確認までを完了条件にする。漏えいした情報の機密性は復元で戻らない。

入れる・有効にする
AWS例：AWS Backup → Backup plans / Backup vaults で対象・頻度・保持・コピー先を定める。管理権限を分離し、必要な資源の別アカウント/Regionコピー可否と暗号鍵を確認。Vault Lockやlogically air-gapped vaultは対応資源と運用要件を調べて選ぶ。Restore testing は代表資源を隔離した検証環境に復元する計画と、業務/データのvalidationを持つ。
観測するもの
Backup/copy jobの失敗・遅延、復元時間、検証結果、復旧先に侵害した資格情報や設定が残らないか。
通知から対応へ
失敗を担当者へ通知。障害/侵害時は優先業務順にクリーンな環境へ復元し、再接続の判断を記録する。テスト資源の削除/クリーンアップまで確認する。
完了の証拠
Restore jobのCOMPLETEDに加え、アプリ応答・整合性・必要データ・権限の検証が成功すること。AWS Backupのrestore validationはEventBridge等の別workflowで実装する。
費用・限界
保管GB・保持・コピー/転送・復元テストの一時資源。Vault LockのCompliance modeは猶予後に原則変更/削除できず、保持が終わるまで費用が続く。最初から永久保持を選ばず、復元・保持・削除方針を事前承認する。対応資源・Regionによって機能が異なる。

アラートを担当者まで届ける：EventBridge → SNS →対応記録

愚か、愚か。コンソールに赤い印を出しても、誰も見る役でなければただの飾りだ。まずは検知から人の判断までを一本通す。

入れる・有効にする
AWS例：EventBridge → Rules → Create rule、default event busで source=aws.guardduty、detail-type=GuardDuty Finding を選択。通知のみのSNS等をtargetにし、購読確認・送信権限・再試行/失敗処理を確認。別ルールで GuardDuty Runtime Protection Unhealthy も通知する。集約にはSecurity Hub/Security Hub CSPMを必要なプラン・Regionで使う。
観測するもの
finding ID、account/Region、対象リソース、type、severity、直近の観測時刻。新規findingはnear-real-time、同じfindingの後続発生は既定6時間集約（管理者は15分/1時間にも設定可能）。
通知から対応へ
当番が一次判定、影響範囲確認、証拠保全、必要な隔離・資格情報/セッション対応、回復と通知へ進む。自動化するなら対象・承認・除外・失敗時復帰を先に設計する。EDR隔離でも盗まれたクラウド資格情報は別途対応が必要。
完了の証拠
GuardDuty → Settings → Sample findings → Generate sample findingsで[SAMPLE]を生成し、通知・担当者の受領・対応記録まで確認。これは合成findingの配送テストで、実センサーの捕捉や攻撃検知を実証しない。
費用・限界
SNS・targets・ログ・集約プラン・当番対応の費用。Security Hubはfindingの集約/相関/ワークフローを提供するが、設定しただけでホスト隔離や全攻撃の自動阻止を保証しない。アラート内のパス等に攻撃者由来の値が入りうるため、HTML表示やログにも安全な処理を使う。

一次資料：通知経路 / サンプルテスト / Coverage通知 / 集約 / 資格情報/権限対応

Azure・Google Cloud・Cloudflareでも、役割で対応させる

同じ製品名に置き換えるのではなく、host EDR、cloud posture、runtime検知、WAF、監査を別の役として選ぶ。以下は主要な対応例。全クラウドへ全部入れる提案ではない。

Azure

VM / 設定の評価
EDRはDefender for Servers P1/P2＋MDE sensor。CSPMを選択/VMを発見しただけで保護済みにしない。Defender for Cloud → Environment settings → 対象subscription → Defender plansで必要なplanを選び、MDEの報告を別に確認。Foundational CSPMは無料、高度なDefender CSPM/Workload protectionは別料金。
Web / 監査
地域のWeb backendにはApplication Gateway WAF、edgeにはFront Door WAF。Detectionで調整し、Prevention/各rule actionを意図して選ぶ。Azure Monitor → Activity log → Export Activity Logsでcontrol-planeを保持。個別resourceのDiagnostic settingsで必要なresource/data-plane categoriesと保存先を選ぶ。
分離 / 回復
NSGでapp→DB/adminの経路を絞り、managed identity＋Key Vault等で長期secretの配布を減らす。Azure Backupの保護とResource Guardによる特定vault操作のMUAを検討し、代表backupの復元を試す。
完了の証拠・限界
MDEはOnboarded/Activeと検知・隔離/解除。WAFは対象経路の診断ログと意図した動作。Activity Logは自動収集・90日保持の管理操作が中心で、resource logsは既定で収集されない。これだけでsecret/DBの読取を追えるとはしない。

一次資料：Servers plan / CSPM / App Gateway WAF / Front Door WAF / Activity Log / Diagnostic settings / NSG / Secretless / Backup MUA

Google Cloud

VM / 設定の評価
GCEのhost EDRには対応MDE等を直接導入/オンボードする選択肢。SCC PremiumのVM Threat Detectionはagentlessの定期的なmemory/disk検知で、同じEDRではない。Security Command Center → VM Threat DetectionのService Enablementで範囲/modulesを確認し、Findingsを調査。SCC Standard/Premiumの現行対応表を確認する。
Web / 監査
Cloud Armor policyのWAF/rate limitを対応load-balancer backendへ関連付け、previewのログからenforceへ。IAM & Admin → Audit Logsで重要サービスのData Access typesを有効化。Admin Activityは常時生成されるが、多くのData Accessは既定で無効。BigQuery等の例外、exemptions、公開/匿名アクセスの欠落も確認。
分離 / 回復

有効化した後に、何を試すか

すべてユーザーが後で許可した検証環境で行うための案。本ページ作成中にクラウドや端末で実行した結果ではない。担当者へ事前連絡し、sampleを本番自動対応から除外する。

  1. 実行時のcoverage：MDEはOnboarded/Active・recent reportingとAV/EDRの各health。GuardDutyは意図した全資源がRuntime coverageでHealthy。未対応OS・agent未配備・古いtaskを一覧から除外して「全台成功」にしない。
  2. 検知と配送を分ける：MDEの公式AV/EDRテストは検証用VMで行い、それぞれのalert/timelineを確認。GuardDutyの[SAMPLE]はfinding→EventBridge→通知の試験。sensorの実検知試験とは分ける。
  3. 拒否する経路：別tenant、低権限、禁止入力、混入ファイル、未scanオブジェクトをダミーデータで試す。正常操作も併せて通し、誤拒否を把握。
  4. 封じ込めと解除：隔離申請ではなく完了状態と、実通信の遮断/必要な管理経路を確認。SG・EDR・資格情報/role sessionの制御を分ける。EBS snapshotはRAMを保存しないため、証拠保全前の安易な再起動/終了を避ける。
  5. 回復と記録：代表backupを隔離環境へ復元し、データ整合性・app health・権限・再侵害経路を確認。資源の後片付け、検証時刻、責任者、未解決課題まで残す。

  • 件数と人数、閲覧と外部持ち出し、事故発生と続報公表を混同しない。過去の「二次被害未確認」は将来の無被害の保証ではない。
  • 具体的な手口や内部構成が非公表なら、特定の脆弱性・設定・人的ミスを勝手に補わない。
  • 評価の対象は仕組みと判断。被害者を責めず、現場に注意力だけを要求せず、監視やデータ収集にも必要性と限界を設ける。

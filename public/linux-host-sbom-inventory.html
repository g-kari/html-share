LinuxサーバーのソフトウェアをSBOM化する方法

2026年11月19日確認｜nginx・PHP・OpenSSLなどの構成管理

結論：サーバーに入っているソフトウェアを一覧化するなら Syft、脆弱性との照合まで行うなら Trivy が使える。共通形式の CycloneDX に出力すれば、複数サーバーの構成管理にもつなげやすい。

ただし、SBOMが示す「検出されたパッケージ」と「現在動作しているプロセス」は別の情報。nginxやPHP-FPMが実際にどのバイナリを使っているかは、別途確認する。

この記事の内容
  1. まずは1台でSBOMを作る
  2. 本当に動いているバージョンを確認する
  3. 何を検出できるか・できないか
  4. 複数台やAWSで管理する
  5. 公式資料

まずは1台でSBOMを作る

Syftのインストール方法は公式ガイドを参照する。対象サーバーでSyftを実行できる場合、ルートファイルシステムを指定して収集する。

Syft：インストール済みソフトウェアをCycloneDX JSONで出力 
syft dir:/ -o cyclonedx-json=host-sbom.cdx.json

出力例は host-sbom.cdx.json。OSのパッケージ管理情報や検出可能なライブラリを収集し、別の分析ツールへ渡せる。権限が足りないファイルは読み取れないため、必要に応じて適切な権限で実行する。[1]

Trivyでも同じ種類のSBOMを生成できる（上記とは別の選択肢） 
trivy rootfs --format cyclonedx \
  --output host-sbom.cdx.json /

Trivyの rootfs はホストや展開済みルートファイルシステムを対象にするモード。通常の開発用ディレクトリを調べる trivy fs とは用途を分ける。[3]

取得したSBOMを脆弱性と照合する

trivy sbom --scanners vuln host-sbom.cdx.json

生成済みSBOMから既知の脆弱性を調べられる。ただし、SBOMの検出漏れや脆弱性DBの対応範囲は残る。検出結果は「攻撃可能」の証明ではない。[4]

本当に動いているバージョンを確認する

例えばPHPのCLIとPHP-FPMで別のバージョンが導入されていたり、OSパッケージとは別にソースからビルドしたnginxが起動している場合がある。SBOMと稼働プロセスの情報を照合する。

# nginxの実行ファイルのバージョン・ビルド設定
nginx -v 2>&1
nginx -V 2>&1

# PHP CLIとPHP-FPMは別々に確認
php -v
php-fpm -v

# 起動中プロセスとコマンドラインを確認
ps -eo pid,comm,args

ディストリビューションによっては php-fpm8.2 のような別名になる。さらに、PATH 上の実行ファイルがサービスの実体と異なることもあるため、systemdの起動設定やプロセスの実行パスを合わせて確認する。

OSパッケージの正確なバージョンを直接取得する

RHEL・Amazon Linux系はRPMの Epoch / Version / Release / Architecture、Debian・Ubuntu系はdpkgのパッケージ名・バージョン・アーキテクチャを保存する。

RPM系 
rpm -qa --qf '%{NAME}\t%{EPOCHNUM}:%{VERSION}-%{RELEASE}\t%{ARCH}\n'
dpkg系 
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n'

アップストリームの 1.2.3 だけで更新要否を判断しない。ディストリビューションによる修正のバックポートがあるため、Releaseまで残して提供元のアドバイザリと照合する。[7]

何を検出できるか・できないか

知りたいこと主な取得方法注意点
OS標準パッケージの一覧Syft / Trivy rootfs、rpm・dpkgパッケージDBの検出範囲と権限に依存する。
nginx・PHPの導入版SBOMとパッケージDB導入済みでも稼働中とは限らない。
nginx・PHP-FPMの稼働版プロセス・サービス設定・実行バイナリnginx -v や php -v の結果だけでは実プロセスとの一致を保証しない。
DockerのソフトウェアイメージごとにSyft / TrivyホストのSBOMだけで各コンテナ内部を網羅したとは扱わない。イメージのdigestを記録する。
手動ビルド・独自配置ファイル検出 + 実行バイナリ確認パッケージ管理情報がない場合、名称や正確な版を検出できないことがある。

Syftのディレクトリ走査は、インストール済みのパッケージだけでなく、manifestに宣言された依存関係を検出する場合もある。検出結果を無条件に「そのサーバーで稼働中」と表示しない。[2]

特に重要な区別

インストール済み・稼働中・ネットワークから到達可能・CVEの影響を受けるは4つの別の状態。それぞれに証拠が必要になる。

コンテナも収集したい場合

稼働中のコンテナをホストと区別して管理し、使用しているイメージ（可能なら不変のdigest）ごとにSBOMを生成する。

# 例：事前に取得可能なイメージを指定
syft nginx:stable -o cyclonedx-json=nginx-image.cdx.json

# 代替：Trivyでコンテナイメージをスキャン
trivy image --format cyclonedx \
  --output nginx-image.cdx.json nginx:stable

上のタグは使用方法を示す例。継続監視では、タグが同名のまま更新される可能性を考慮し、実際に利用したイメージのdigestを保管する。

複数台やAWSで管理する

複数サーバーを対象にするなら、収集結果を単に上書きせず、資産IDと取得日時に紐づくスナップショットとして保存する。脆弱性の検出と修正承認は別の状態として扱う。

方式適する場面考慮事項
Syft + 定期収集クラウド・オンプレを混在させたいSSH / ジョブ / エージェントの方式、権限、実行負荷を設計する。
SSM InventoryAWSの管理対象ノードアプリケーション名・版などを収集。標準のSBOMエクスポートと同一ではない。[5]
Amazon InspectorInspectorが監視対象としているAWSリソース対応するEC2・ECR・Lambda等からSBOMをエクスポート。利用条件、サービス料金、S3・KMSの設定が必要。[6]

中央管理するなら残したい項目

  • 資産ID・ホスト名・OS・取得日時・検出元
  • パッケージ名・バージョン・Release・アーキテクチャ・PURL（取得できる場合）
  • 検出対象（ホスト・イメージ・アプリ）とコンテナのdigest
  • 稼働状態・実行バイナリ・収集の成否（SBOMと別の証拠として保持）
  • CVE、影響判定の根拠、修正・承認の履歴

運用案：定期収集に加え、デプロイやパッケージ更新の直後にも再収集する。収集失敗時は前回のSBOMを最新と表示せず「最終成功日時」を残す。ホストの内部パスやソフトウェア構成が含まれるため、生成したSBOMは原則として非公開で管理する。

公式資料

  1. Anchore OSS：Syft Supported Scan Targets — ディレクトリ・コンテナのSBOM生成、ファイルシステムの扱い。
  2. Anchore OSS：Package Catalogers — ソースの宣言依存とインストール済みソフトの検出。
  3. Trivy：Rootfs — ホスト・展開済みrootfsのスキャン。
  4. Trivy：SBOM — CycloneDX / SPDXの生成と脆弱性照合。
  5. AWS Systems Manager Inventory — アプリケーションとバージョンの収集。
  6. Amazon Inspector：Exporting SBOMs — 対応リソース、形式、S3・KMS要件。
  7. Red Hat：Packaging software with RPM — RPMのEpoch / Version / Release。

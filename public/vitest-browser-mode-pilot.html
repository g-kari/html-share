Vitest Browser Mode 試験導入の実測

対象：g-kari/tools の jsdom テスト17ファイル・283テスト / 実施日：2026年11月20日 / 前提：Vitest 5.1.1（tools PR #367、未マージ）

結論

jsdom で実行していた重い17ファイル（283テスト）を、Vitest 5.1.1 の Browser Mode（Playwright の Chromium）で実行しました。総時間（Duration）は現行の約32秒から 26.20秒に短くなりましたが、全通過にはならず、通過は 222/283（78%）でした。ファイル単位のテスト実行そのものは実ブラウザの方が概ね3〜10倍速く、遅さの主因は jsdom の環境構築でした。一方で、落ちた61件の大半は実ブラウザの性能ではなく、Node API 前提のモックやタイムゾーン切替など、テスト側の前提が実ブラウザで成立しないことが理由です。素直な DOM・hydration・ライフサイクル系の12ファイルは全通過しました。移行するかどうかは速度よりも「テストが Node の仕組みにどれだけ依存しているか」で決まります。

測った範囲と条件

対象リポジトリは g-kari/tools です。単体テスト全387ファイルのうち @vitest-environment jsdom を使う36ファイルが DOM 系で、その中から全スイート実行時に重かった上位15ファイルに、性質の異なる代表2ファイル（クリップボード、Canvas/Blob 系）を加えた17ファイル・283テストを対象にしました。対象だけで jsdom 群の実行時間の約68%を占めます。

この試験は Vitest を 4.0.16 から 5.1.1 へ上げる tools PR #367（未マージ）を前提にしています。

Browser Mode は上流 Vitest 5.1.1 と @vitest/browser-playwright 5.1.1 で実行しました。測定環境は共有1.5 CPU の VM で、数値はこの環境とこの対象範囲での実測です。CPU の多い CI や別のプロジェクトでは結果が変わります。

なお、現行のテストは vite-plus/test 経由で import しており、上流 Vitest の素の実行系では動きません。試験では試験用設定の resolve.alias で vite-plus/test を vitest に読み替えて実行しました。この読み替え自体は全ファイルで機能しましたが、本導入では import の扱いを決める必要があります。

5.1.1 のモジュールキャッシュ再利用

Vitest 5.1.1 の変更点の一つは、Browser Mode でモジュールキャッシュを再利用し、テストファイルごとにサーバーへ再検証せずブラウザキャッシュから取ることです。実測でも、依存最適化のキャッシュが冷えた初回はファイルごとの import が重く、遅れて最適化される依存があると実行中のリロードも起きましたが、キャッシュが温まった後は import の割合が Duration の 29%まで下がり、単独実行では各ファイルの総 Duration が 2.6〜4.5秒（うちテスト本体は 0.1〜0.6秒台）に収まりました。「2回目以降が速い」という 5.1.1 の説明と整合する挙動です。

ただし注意点があります。今回の比較は、並列実行から逐次実行への変更とキャッシュの温まりが同時に起きており、キャッシュ効果だけを分離した数値は取れていません。キャッシュ再利用の効果量そのものは、同一条件での再測定が必要です。

失敗の分類

通過しなかった61件（未実行26件を含む）は、次の5種類に分類できました。実ブラウザ側の不具合ではなく、テストの前提と実ブラウザの環境の食い違いが中心です。

1. Node API 前提のモックは実ブラウザに届かない（大）

hash-lifecycle（2/28）は、node:crypto の webcrypto と node:util の TextEncoder を import し、subtle.digest を段階制御できるモックに差し替える設計でした。ブラウザのグローバル crypto とは別物のため、アプリ側の digest 呼び出しがモックに届かず、26件が失敗しました。この型はモックの再設計が必要です。

2. ホストのタイムゾーン切替は実ブラウザで成立しない（中）

world-clock-hydration（2/8）は、SSR とクライアントでホストのタイムゾーンをテスト内に切り替える前提でした。実ブラウザのタイムゾーンはインスタンス固定で（この環境では UTC）、6件が失敗しました。Playwright の context の timezoneId をシナリオ別に分ける再構成が必要です。

3. Node API の import がブラウザで解決できない（小）

use-generated-gif（0/26）は node:buffer の Blob を import しており、ブラウザでは externalized されて import 自体が失敗しました。グローバルの Blob への置換で解消できる見込みです。同様に、cloudflare:sockets を import するモジュールに辿り着くスイートはブラウザで解決できないため、Browser Mode の対象外として分離が必要です。

4. 実ブラウザの実挙動との差（小〜中）

use-clipboard-dom の2件は、execCommand フォールバック時の選択範囲の保持が、実ブラウザ（headless Chromium）では jsdom と異なりました。実ブラウザの挙動が本物なので、テストの前提を見直すか、製品コード側が実ブラウザに準拠しているかを確認する対象です。nav-category-focus の1件は、アンマウント時のタイマー掃除のテストで、レイアウト計測（clientHeight）の参照タイミングが実ブラウザと異なり null 参照になりました。

5. 設定起因（解消可能）

password-generator-ui の初回だけのリロード失敗は、optimizeDeps.include の不足でした。React の二重解決を避けるには、react、react-dom の各エントリと react/jsx-runtime、scheduler を揃える必要があり、ファイルごとに遅れて最適化される依存（UI ライブラリ等）も含めて洗い出すことが安定化の要点です。揃えた後はキャッシュが温まれば再発しませんでした。また、Browser Mode では headless: true の明示が必要でした（既定では headed 起動を試み、表示環境のない場所では失敗します）。

移行の目安：向く環境、向かない環境

向いている

  • jsdom の環境構築と DOM 実行がテスト時間の支配的な割合を占めるプロジェクト。今回の対象範囲では environment の並列合計が約40秒と、テスト本体を上回っていました
  • テストが実ブラウザの挙動そのものに依存する、または依存すべきプロジェクト。クリップボードやレイアウト計測のように、jsdom と実ブラウザで挙動が違う部分は、実ブラウザで検証する方が正しくなります
  • モックが DOM レベルに閉じているスイート。DOM 操作・hydration・ライフサイクル系は、今回12ファイルがそのまま全通過しました

向いていない、または追加作業が要る

  • Node API のモックに依存するテストが多いプロジェクト。node:crypto の差し替えのような設計は実ブラウザに届かず、モックの再設計が前提になります
  • タイムゾーンや crypto をテスト内で差し替える設計。実ブラウザではインスタンス固定のため、シナリオごとにブラウザ context を分ける再構成が要ります
  • CI の CPU が少なく、並列実行が前提の環境。共有1.5 CPU では既定の並列実行が初期化タイムアウトで成立せず、逐次実行に落としました。並列度の調整か CPU の増強が要ります

導入の前提作業

  • Vitest 本体を Browser Mode 対応の版にすること。ラッパー経由の場合、そのラッパーが対応版を含むか、上流 Vitest へ切り替えるか（今回の tools では PR #367 が前提）
  • vite-plus/test のようなラッパー経由の import の扱いを決めること。試験では resolve.alias で読み替えましたが、恒常運用では alias の継続か import の付け替えかを選ぶ必要があります
  • optimizeDeps.include の洗い出し。React の二重解決を避けるエントリ一式と、遅れて最適化される依存を揃えます
  • CI への Chromium の取得（playwright install。Playwright の版に合うブラウザのリビジョン管理を含む）と、並列度の調整
  • Browser Mode 用の設定ファイルを分離し、headless: true を明示すること

全面移行の見込みと作業量

jsdom 群36ファイル全体でも、ファイル単位の実行時間が3〜10倍になる傾向は同様と見込めます。全スイート（387ファイル、Vitest 5.1.1 で 250.87秒）のうち、圧縮対象は jsdom の環境構築（36ファイルで並列合計 128.84秒）と DOM 実行で、数十秒規模の短縮が見込めます。ただし Browser Mode 側の import とワーカーのコスト、並列度の調整次第で最終値は変わるため、総時間は CI での実測が必要です。

作業量の目安は基盤（上流 Vitest 化のマージ、Browser Mode 用設定の分離、optimizeDeps の洗い出し、CI への Chromium 取得、並列度調整）が1 PR 規模、ファイル別対応は小さいもの（Blob の置換、クリップボードとフォーカスの前提見直し）から大きいもの（crypto の段階モックの再設計）までです。今回未対象の jsdom 群19ファイルは未検証で、同じ分類に収まる見込みですが、1回通しての確認が必要です。

出典と測定条件

  • 数値はすべて g-kari/tools での試験導入の実測（2026年11月20日実施）です。前提は Vitest 5.1.1 への更新 PR tools PR #367（未マージ）で、Browser Mode の試験設定は本導入ではなく試験用に分離したものです
  • 測定環境は共有1.5 CPU の VM です。現行方式は2回測定（Duration 32.18秒、31.29秒）、Browser Mode の 26.20秒はファイル逐次実行・キャッシュ温の条件です
  • ファイル別の jsdom の数値は、全スイート実行時（Vitest 5.1.1）の参考値です。Browser Mode の数値は対象17ファイルの逐次実行時の値です
  • Vitest Browser Mode と 5.1.1 のモジュールキャッシュ再利用については Vitest 公式ドキュメント（Browser Mode）を参照してください

この記事は試験導入の記録です。tools 本体への Browser Mode の導入は未実施で、PR #367 のマージ後に判断します。

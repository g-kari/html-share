Go / AWS Lambda / 配布形式と移行

ZIPからImageへ移れる。
ただし「同じ関数の形式変更」ではない。

Goならどちらも選べる。大事なのは「コードを包み直すこと」と「Lambdaというリソースを入れ替えること」を分けること。無理に切り替える方法も含め、できる範囲と失うものを整理する。

結論Goならどう選ぶ回避策4つZIPの再包装移行と戻し方公式根拠

まず、3種類の「変える」を区別する

同じLambdaリソース

ZIP → Imageの直接変更
できない

既存関数のPackageTypeは変更不可。CLI/APIのImageUri指定もZIP関数には使えない。コンソールだけの制限ではない。[1] [2]

別のLambdaリソース

Image関数を作って移行
できる

新しい関数にコード・設定を用意し、検証後に呼び出し先を切り替える。旧ZIP関数を残す方が戻しやすい。[1]

配布する成果物

ZIPの中身をImage化
条件付きでできる

Goバイナリと依存ファイルを展開してイメージへ入れる。ただしLinux・CPU・共有ライブラリ・Runtime APIの互換性確認が必要。[6] [7]

短い答え：「移行できる」は正しい。「今の関数へイメージを上書きして形式だけ変える」はAWSのサポート対象の方法ではできない。
CLIでも無理？ はい、既存ZIP関数へのImageUri指定は不可

AWS CLIのupdate-function-codeは、背後のUpdateFunctionCode APIを呼びます。ImageUriパラメーターはZIP定義の関数に使わないことが明記されています。コンソールを避けたりCLIを直接呼んでも、同じ関数のPackageTypeを変更する抜け道にはなりません。公式API仕様

CLIで「新しいImage関数を作る」ことはできます。それは既存関数の直接変更とは別の操作です。

Goなら、形式より運用理由で選ぶ

ZIPのままで十分なケース

  • 小さいGoバイナリと少数のファイルで完結する。
  • 既存のデプロイが安定し、OS依存をまとめる必要が薄い。
  • ECR・イメージ更新の管理を増やすメリットがない。

GoのZIPは、例えばprovided.al2023とbootstrapを使う構成。CGOの有無と対象CPUを確認する。[7]

Imageを選ぶ理由があるケース

  • ネイティブライブラリやOS依存を一緒に管理したい。
  • 他の実行環境とDockerのビルド手順を揃えたい。
  • ZIPのサイズ制約では足りない成果物を扱う。

Lambda用コンテナは、任意の常駐サーバーをそのまま動かす仕組みではない。Runtime API対応などの条件がある。[1]

ZIPは展開後250 MB（layers等を含む）、Imageは非圧縮10 GB。これは容量上限であり、速さの保証ではない。[13] 「コンテナだから遅い／速い」と決めず、同じCPU・メモリ・依存関係・処理でコールド／ウォームを分けて測る。

選び方は運用上の判断です。この資料は性能測定や費用見積もりではありません。

「無理やり変える」なら、実際にはこの4パターン

方法何が維持できるか代償・注意
別名のImage関数へ切替
第一候補		既存API Gateway等の入口を残して、統合先を変更できる構成がある。新関数の設定・権限・トリガー確認が必要。イベント種別ごとに二重処理、欠落、リトライを設計する。
旧関数を削除し同名で再作成
破壊的な置換		関数名は再利用できる場合がある。同じpartition/account/region/nameなら非修飾ARNの文字列も同形になると考えられる。同じリソースではない。全version・aliasは削除される。停止時間と復元不能な状態喪失がある。ARNの同形は命名規則からの推論で、連携の自動復旧を保証しない。[5]
旧ZIP関数を中継役にする
入口を残す暫定策		旧関数／Function URLを削除せず、新Image関数をInvokeする設計。直接変換ではない。追加の呼び出しコスト・遅延・権限・timeout・payload・エラー伝播が増える。通常は入口の統合先切替を優先。[12]
CloudFormation / SAMで形式変更
IaCによる置換		コード上はPackageTypeを書き換えられる。CloudFormationではReplacement。固定FunctionNameで置換が必要な更新は新しい名前が必要。SAMもこの属性をそのまま渡すため抜け道にならない。[3] [4]
同名の削除再作成は、通常の更新より危険。コードのバックアップから作り直せても、元の関数・version・aliasを復元したことにはならない。外部トリガーやevent source mappingは一括清掃されるとは限らず、残存状態と権限を個別照合する。削除用コマンドはこの資料には載せていません。
Function URL・API Gateway・aliasの落とし穴
  • Function URL：削除後に同じURLは復元できない。新しい設定には別のURLが発行される。[9]
  • API Gateway：同じAPI・stage・custom domainを維持して統合先だけ変えるなら、クライアントURLを維持できる構成。これは構成上の判断であり、無停止保証ではない。REST APIの統合変更は再デプロイが必要。[11]
  • alias：同じ関数のversionを指すもの。旧関数のaliasを新しい別関数へ向け替える仕組みではない。中継を使う場合も旧関数側のコード／version／aliasの更新が必要。古い公開versionへ固定された呼び出しは、そのversionを書き換えられない。[10]

ZIPの中のGoバイナリを、Imageへ包み直す

既存ZIPbootstrap・設定・静的ファイル
→
展開・互換性確認Linux / CPU / CGO / Runtime API
→
Lambda対応Image新しい関数へ配布する成果物
  • GoバイナリがLinux向けで、Image／LambdaのCPUアーキテクチャと一致していること。
  • aws-lambda-go/lambdaなどによるRuntime API対応が含まれること。古いgo1.x向けバイナリをそのまま動くと保証せず、可能なら現行ライブラリで再ビルドする。
  • CGOを使うならlibcや共有ライブラリの互換性を確かめる。単にbootstrapだけCOPYして終わりとは限らない。
  • 実行権限があり、read-onlyなルートファイルシステムで動くこと。書き込み先は/tmpを使う。
  • Image関数にLambda layerを設定として追加することはできない。必要な内容を/optへ含め、extensionは/opt/extensionsを含む配置を確認する。[8]
以下は説明用・未実行の例です。元ZIP・ビルド環境・依存ファイルは未確認です。安全な新規ディレクトリに展開したbootstrapを想定します。ビルド成功だけでLambda上の動作成功とは判定しません。

概念的なDockerfile

FROM public.ecr.aws/lambda/provided:al2023
COPY --chmod=755 unpacked/bootstrap /var/task/bootstrap
ENTRYPOINT ["/var/task/bootstrap"]

これは追加ファイル・共有ライブラリ・layersの不要な最小構成を想定した例です。必要なファイルがあれば別途含めます。既存GoバイナリがRuntime APIに対応していることが前提です。[6]

ローカルビルド例

docker buildx build \
  --platform linux/amd64 \
  --provenance=false \
  --load \
  -t lambda-go-migration:test .

arm64ならlinux/arm64を選び、バイナリも合わせる。Lambda向けには単一アーキテクチャのImageを作る。ECRへのpushや関数作成・切替は、この例には含めていません。[1] [6]

実際に移すなら「旧関数を残す」

  1. 現状を棚卸しする。runtime、CPU、memory、timeout、環境変数の設定元、VPC、実行role、resource policy、layers、URL、alias、version、トリガー、mapping、DLQ／destination、同時実行、監視を確認する。秘密値を資料へ転記しない。
  2. Imageを作り、別名の新関数で検証する。初期化・正常系・失敗系・timeout・リトライ・依存先接続・ログ・権限を確かめる。Imageのベース更新も再ビルド／再配布計画に含める。
  3. 入口ごとに切替計画を立てる。HTTP、queue、stream、非同期イベントでは方法が違う。event source mappingは対象関数の更新APIがあるが、移行の整合性はイベント種別ごとに検証する。[14]
  4. 戻す条件を先に決める。エラー率・遅延・重複処理などの判断条件と、旧関数へ呼び出し先を戻す操作を準備する。新旧で共有データを書き換える場合は、コードを戻すだけではデータまで戻らない。
  5. 切替後を確認し、削除は最後に別判断。ログとメトリクス、業務結果、残存呼び出しを確認する。旧関数を残すだけで課金ゼロとは限らないため、Provisioned Concurrency等の設定も把握する。
今回の判断：Goで今のZIP運用に困っていないなら、形式変更自体を目的にしなくてよい。Image化する明確な理由があれば、ZIPの再包装または再ビルド＋別関数への移行が現実的。同名削除再作成は「できるか」より「失ってよいものがあるか」で判断する。

公式根拠

  1. AWS Lambda：Create a Lambda function using a container image — 既存関数のpackage type変更不可、Image要件。
  2. UpdateFunctionCode API — ZIP関数へImageUriを使えない。
  3. CloudFormation：AWS::Lambda::Function — PackageTypeのReplacement、固定FunctionNameの制約。
  4. AWS SAM：Function / PackageType — CloudFormation属性への受け渡し。
  5. DeleteFunction API — version・alias削除とevent source mappingの扱い。
  6. Deploy Go Lambda functions with container images — Go用Image構築、CPU・ビルド条件。
  7. Deploy Go Lambda functions with .zip file archives — bootstrap、CPU、CGO。
  8. Lambda layers / Layers and extensions in container images — Imageへの依存物同梱。
  9. DeleteFunctionUrlConfig API — 削除したURLは復元不可。
  10. Lambda aliases — 関数versionへのポインタ。
  11. Update a REST API — 統合変更と再デプロイ。
  12. Invoke API — 別関数への呼び出し、中継の制約確認。
  13. Lambda quotas — ZIP・Imageの容量制約。
  14. UpdateEventSourceMapping API — 対象関数の更新。
この資料は公式仕様と、その仕様に基づく構成上の判断を区別してまとめたものです。実環境の棚卸し、移行、Docker実行、性能・費用測定は未実施です。破壊的な削除再作成や本番切替を実行する指示書ではありません。

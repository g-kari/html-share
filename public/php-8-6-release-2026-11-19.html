PHP 8.6の変更点：セッション既定値の厳格化と、自分のリポジトリへの影響

公開日：2026年11月25日
一次資料：php.net の PHP 8.6 リリースページ、移行ガイド、php-src の UPGRADING、Supported Versions。自分のリポジトリの走査は2026年11月25日に実施しました。同日のセキュリティ修正版についてはPHPのセキュリティ更新（2026年11月19日）に分けています。

要点
  1. PHP 8.6.0 が2026年11月19日に公開されました。新機能の中心は部分関数適用、\Time\Duration クラス、ポーリングAPI Io\Poll、clamp() 関数です。
  2. 既存アプリへの影響が一番大きいのは新機能ではなく、セッションの既定値の変更です。session.use_strict_mode と session.cookie_httponly が 1 になり、session.cookie_samesite の既定が Lax になります。SSOや決済サイトから戻るPOSTでログインが切れるのが典型的な壊れ方です。
  3. PHP 8.2 のセキュリティサポートは2026年12月31日で終了します。8.2 のまま年を越すと、新しい脆弱性が出てもPHP公式の修正が届きません。
  4. 自分のGitHubリポジトリを走査した結果（対象はアーカイブ済みを除く109件）、PHP 8.2 に固定されていたのは php-base の1件だけでした。もう1件のPHP関連リポジトリ phalcon-queue はバージョン固定ではありません。

概要

PHP 8.6.0 は2026年11月19日に公開された、PHP 8 系の新しいマイナーバージョンです。同じ日には、8.5.13、8.4.28、8.3.37、8.2.36 のセキュリティ修正版も公開されています。8.6.0 には、その修正版と同じ18件のセキュリティ修正が含まれています。修正版だけが目的であれば、8.6 へ乗り換える必要はなく、使っている系列の修正版に上げるのが先です。脆弱性の内容と確認手順はPHPのセキュリティ更新（2026年11月19日）にまとめています。

この記事では、8.6 の変更のうち既存のアプリケーションに影響しやすいものを先に扱い、新機能はその後にまとめます。あわせて、自分のGitHubリポジトリに残っているPHPのバージョン固定を走査し、8.2 のサポート終了に当たるものがあるかを確認しました。

サポート期限：8.2は2026年12月31日まで

PHP の各系列は、公開から2年間のアクティブサポート（バグ修正とセキュリティ修正）のあと、2年間のセキュリティ修正のみの期間に入り、合計4年でサポートが終わります。php.net の Supported Versions に掲載されている期限は次のとおりです。

8.2 はすでにセキュリティ修正のみの期間に入っていて、その期限が約1か月後に来ます。期限を過ぎた系列は、重大な脆弱性が見つかってもPHPプロジェクトからは修正版が出ません。OSのパッケージやレンタルサーバーを使っている場合は、提供元が独自に修正を続けることがあるため、提供元の案内も確認してください。

新機能

部分関数適用は、関数の引数の一部を先に渡し、残りを受け取る Closure を返す書き方です。プレースホルダの ? は1つの引数、... は残り全部を表します。これまで array_map() や array_filter() に渡していた小さなクロージャの多くを、関数呼び出しの形で直接書けます。

\Time\Duration クラスは、経過時間を表す専用の型です。ナノ秒精度で250年を超える範囲を表せて、時刻やタイムゾーンに依存しません。タイムアウトやリトライ間隔、処理時間の計測など、これまでマイクロ秒の整数で受け渡していた値の置き換え先になります。

ポーリングAPI Io\Poll は、多数のストリームをまとめて監視する仕組みです。OSごとに epoll、kqueue、event ports、WSAPoll のうち使えるものを使い、stream_select() の接続数の上限を避けられます。ReactPHP や AMPHP のようなイベントループのライブラリが土台として使う想定の機能で、通常のWebアプリが直接使う場面は多くありません。

そのほかの追加は次のとおりです。

  • clamp() 関数：値を最小値と最大値の範囲に収めます。max(min(...)) の入れ子の置き換えです。自前で同名のグローバル関数を定義しているコードは衝突するため、移行前に確認が必要です。
  • SortDirection 列挙型：並び順を表す共通の型です。ライブラリごとに違った整数や文字列で受けていた並び順を、型で統一できます。
  • readonly プロパティのデフォルト値：コンストラクタで代入しなくても、宣言時に既定値を持てるようになりました。
  • ストリームのエラー処理：ストリーム操作の失敗を警告ではなく StreamException として投げる設定ができ、失敗の内容は stream_last_errors() でも取得できます。
  • リフレクションの追加：引数ごとのドキュメントコメントを読む ReflectionParameter::getDocComment() と、プロパティの読み書き可否を返す ReflectionProperty::isReadable()、isWritable()。
  • URI の組み立て：Uri\Rfc3986\UriBuilder と Uri\WhatWg\UrlBuilder。
  • Sodium 拡張に、耐量子計算機の鍵カプセル化（X-Wing、ML-KEM-768）などが追加されました。

セッション既定値の厳格化

8.6 で既存アプリに最も影響するのは、セッション関連の3つの設定の既定値変更です。いずれも、設定していない場合に、より安全な値になる変更で、php.ini やアプリ側で明示的に設定済みであれば動きは変わりません。逆に、既定値のまま動かしていたアプリでは、バージョンを上げただけでセッションの動きが変わります。

設定変更前8.6の既定壊れやすい箇所
session.use_strict_mode01外部の仕組みから渡されたセッションIDをそのまま使う構成。カスタムのセッションハンドラ
session.cookie_httponly01JavaScript から document.cookie でセッションIDを読んでいるコード
session.cookie_samesite未設定LaxSSOや決済サイトから自サイトへ戻るクロスサイトPOST

strict mode が有効になると、PHPが発行していないセッションIDは拒否され、新しいIDが発行されます。セッションフィクセーションへの対策ですが、外部の認証基盤やモバイルアプリからセッションIDを引き渡す構成では、ログイン状態が引き継げなくなります。カスタムのセッションハンドラは validateId() と create_sid() の実装が要ります。この2つを持たないハンドラを session_set_save_handler() に渡すことも 8.6 で非推奨になりました。どうしても旧来の動きが必要な場合は、影響を理解したうえで明示的に 0 へ戻す選択肢があります。

HttpOnly が有効になると、セッションCookieは JavaScript から読めなくなります。XSS でセッションIDを盗まれる経路を塞ぐ変更で、通常のアプリは影響を受けません。document.cookie からセッションIDを読んでAPIリクエストに付けているような作りの場合だけ、別の受け渡し方法への変更が必要です。

SameSite の Lax が一番影響が出やすい変更です。Lax では、別のサイトから来るPOSTリクエストにはセッションCookieが付きません。決済サイトや SSO の認証先で処理を終えたあと、結果をPOSTで自サイトへ戻す流れでは、戻り先でCookieが送られず、セッションが見つからないため、決済や認証が完了したのにログイン画面へ戻される、という症状になります。

移行前に確認すること（設定を変えずに読むだけの確認です）

  1. 本番とステージングで、現在の値を確認します。
    php -i | grep -E 'session\.(use_strict_mode|cookie_httponly|cookie_samesite)'
    Web（FPM）とCLIで設定ファイルが違う環境では、Web側の値を phpinfo() やアプリ側の ini_get() でも確認します。3つとも既定のままなら、8.6で動きが変わる対象です。
  2. ステージングでは、PHP 8.5 のまま先に新しい既定値を有効化して試せます。ログイン、ログアウト、SSOの往復、決済サイトからの戻り、埋め込みiframeの流れを確認します。
  3. 問題が出たフローは、戻り先を署名付きペイロードで検証するなど、セッションに依存しない形へ直すのが本筋です。一時的に戻す場合は、対象フローの範囲だけ session.cookie_samesite を None にし、合わせて session.cookie_secure を有効にします。

その他の非互換と非推奨

8.6 では、古い別名関数を中心に非推奨がまとまって入ります。非推奨は警告が出る段階で、削除は PHP 9 が予定です。置き換え先が決まっているものは機械的に直せます。

  • finally ブロックの中で return することが非推奨になりました。例外を握りつぶし、try や catch の戻り値を上書きしてしまうためです。
  • __construct() と __destruct() から値を返すことと、この2つをジェネレータにすることが非推奨になりました。
  • mb_ereg() 系の mbstring 正規表現が非推奨になりました。エンジンの Oniguruma が保守されていないためで、置き換え先は u 修飾子を付けた PCRE（preg_*()）です。
  • define() の第3引数（大文字小文字を区別しない定数）が非推奨になりました。
  • trim()、ltrim()、rtrim() の既定の除去対象にフォームフィード（\f）が加わりました。対象文字を明示していないコードでは、結果がわずかに変わることがあります。
  • 引数の検証が厳しくなり、これまで警告や黙っての切り捨てで済んでいた入力に ValueError が投げられる箇所が増えました。範囲外の数値や NUL バイトを含む文字列を渡すコードは、例外として表面化します。

自分のリポジトリ走査結果

自分のGitHubリポジトリ（アカウント g-kari、全144件）のうち、アーカイブ済みを除く109件を対象に、ファイルツリーを走査しました。確認したのは composer.json、Dockerfile、.php-version、PHPファイルの有無です。Dockerfile が見つかったリポジトリは、ベースイメージが PHP かどうかを個別に確認しました。空のリポジトリ4件には内容がありませんでした。

リポジトリバージョンの証拠8.2期限への該当8.6で関係する変更
php-base docker/php/Dockerfile の FROM php:8.2-fpm。README にも PHP 8.2 と記載。composer.json や CI のバージョン指定はなし 該当。8.2 に固定されていて、セキュリティサポートが2026年12月31日で終わる ベースイメージの系列を上げる必要がある。PHP-FPM の土台なので、この上で動くアプリはセッション既定値の変更を受ける。mbstring 拡張を入れているが、非推奨になるのは mb_ereg() 系の関数であり、拡張そのものではない
phalcon-queue（fork） composer.json の require.php が ^8.1 非該当。バージョン固定ではなく、8.2 に縛られていない ^8.1 は 8.6 も範囲内に含む。ただし依存する拡張 ext-phalcon 5.* の PHP 8.6 対応は、この走査では確認できていない（未確認）。CLI 向けのキューライブラリで、セッション既定値の影響は小さい

主言語が PHP のリポジトリは、この2件のほかにアーカイブ済みのテスト用リポジトリ10件（フレームワークや管理画面の検証用）があり、今回は対象外にしました。バージョンの根拠が取れなかったものは「不明」として、推測で埋めていません。今回の走査で不明になったのは、非公開リポジトリ stream-friend の開発コンテナ用 Dockerfile の中身だけで、このリポジトリには PHP ファイルも composer.json もありませんでした。

PHP 8.2からの進め方

8.2 を使っている場合、移行先は 8.6 とは限りません。8.6 は出たばかりで、フレームワークや拡張の対応がそろっていないことがあります。期限に間に合うことと、使っているフレームワークが対応していることの両方で移行先を決めます。

  1. まず系列内の最新版へ上げます。8.2 なら 8.2.36 が、11月19日に公開されたセキュリティ修正版です。
  2. ステージングで、セッションの新しい既定値を先に有効化して、ログイン、SSO、決済の戻りをテストします。8.6 へ上げる前に、既定値変更の影響だけを切り分けられます。
  3. 移行先は、フレームワークと拡張の対応が済んだ系列を選びます。8.4 はセキュリティ修正が2028年12月31日まで、8.5 は2029年12月31日まであり、どちらも期限には十分間に合います。
  4. 8.6 は CI のジョブに入れて、非推奨警告とテストの結果を見てから判断します。composer why-not php 8.6 で、8.6 を妨げているパッケージを確認できます。

php-base については、Dockerfile の系列を 8.4 か 8.5 へ上げるのが実際の作業になります。タグは php:8.2-fpm のように系列までの指定なので、系列内では再ビルドで修正版を取り込めますが、系列自体は手で変える必要があります。

用語補足

部分関数適用とPHP 8.5のパイプ演算子
部分関数適用は「関数を組み立てる」仕組みで、PHP 8.5 で入ったパイプ演算子は「値を関数へ流す」仕組みです。組み合わせると、小さなクロージャを挟まずに処理の連なりを書けます。
SameSite の Lax と Strict
Lax は、別サイトからのPOSTなどには Cookie を付けない一方、リンク遷移のようなトップレベルの GET では付けます。Strict は遷移でも付けません。今回の既定は Lax です。
strict mode（セッション）
PHP が発行した記録のあるセッションIDだけを受け入れる設定です。発行記録のないIDは、攻撃者が用意したものと区別できないため拒否されます。

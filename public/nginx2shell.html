NGINX2Shell
NGINX HTTP/2 の RCE 脆弱性2件

対象：NGINX Open Source / NGINX Plus の ngx_http_v2_module
公開：2026年11月18日（F5 セキュリティリリースと協調公開）
CVE：CVE-2026-123007 / CVE-2026-123633（いずれも CVSS 4.0 で 9.2）

要点
  1. NGINX の HTTP/2 実装に、リモートからコード実行に至りうる脆弱性が2件見つかり、2026年11月18日に協調公開された。
  2. 影響を受けるのは HTTP/2 を使う構成のみ。修正は Open Source の 1.31.9（mainline）／1.30.7（stable）。当面の緩和は HTTP/2 の無効化。
  3. ALB の後ろでバックエンドが HTTP/1.1 の構成は、インターネット側から脆弱なコードに届かない。ただし迂回経路があると崩れる。

何が公開されたか

2026年11月18日、F5 のセキュリティリリースに合わせて、NGINX の HTTP/2 実装の脆弱性2件が協調公開された。発見は Wiz Research、Ikotas Labs、Metnir、Rapid7、Xint の5チームがそれぞれ独立に行った。Ikotas Labs の Satoki が X で「NGINX2Shell」と名付けて公表し、F5 の公式アドバイザリの謝辞にも Ikotas Labs が明記されている。

Wiz は公式ビルドの最新版（当時の mainline 1.31.7／1.31.8）で、ASLR のバイパスを含めてリモートコード実行を確認したとしている。ASLR は成立に必要な情報読み取りの前段があるため、防御として当てにできない、というのが Wiz の見立てである。

CVE-2026-123633（use-after-free）

HTTP/2 コネクションの処理における use-after-free。混入したのは 1.19.7 で、約6年間存在していた。Wiz によると、リバースプロキシ構成で、アップストリーム側の空きコネクションが逼迫する状況で悪用しやすくなる。深刻度は CVSS 4.0 で 9.2（Critical）。

CVE-2026-123007（整数アンダーフロー）

HTTP/2 のフロー制御ウィンドウ（send_window）の整数アンダーフローで境界チェックが無効になり、不正なメモリコピーに至る。混入したのは 1.9.5（2015年）で、10年以上存在していた。静的ファイル配信のみの NGINX でも HTTPS 経由でリモートコード実行を確認したと Wiz は述べている。深刻度は CVSS 4.0 で 9.2、F5 の CVSS 3.1 評価では 8.1。

Rapid7 の Stephen Fewer は公開当日にこの脆弱性の PoC を GitHub で公開した。Rapid7 は悪用には約128GBの HTTP/2 トラフィックの送信が必要と指摘しており、実環境での悪用は確認されていない。

影響の条件：モジュールではなく「使っているか」

F5 公式アドバイザリの説明は「HTTP/2 を使う構成」が影響を受ける、という書き方である。モジュールがバイナリに含まれている、あるいはロードされているだけでは、攻撃者は HTTP/2 コネクションを張ることができず、脆弱なコードは実行されない。緩和策として HTTP/2 の無効化が成立すること自体が、その裏付けになっている。

一方で、F5 の表では脆弱なコンポーネントが ngx_http_v2_module とされ、対象はバージョン範囲で切られている。このため、バージョンやモジュールの有無で判定するスキャナは、HTTP/1.1 のみで運用している構成でも「該当」と出すことがある。実害の線引きは、スキャナの判定ではなく「http2 を有効にした listen があるか」で見るのが正確である。逆に、どこか1か所でも http2 を有効にした listen があれば、その口からは影響を受ける。

修正版と緩和策

製品CVE-2026-123633 の修正CVE-2026-123007 の修正
NGINX Open Source（mainline）1.31.9
NGINX Open Source（stable）1.30.7
NGINX Plus 37.x37.0.7.1 / 37.2.0.1 以降37.0.8.1 / 37.3.0.1 以降

当面の緩和は HTTP/2 の無効化である。1.25.1 以降は http2 off; と書くか、listen ディレクティブの http2 パラメータを外す。なお F5 のアドバイザリは Mitigation を「None」としており、公式の推奨は修正版への更新である。無効化は更新までのつなぎと位置づけるのがよい。

ALB の後ろにある場合

AWS の Application Load Balancer（ALB）は、クライアント側の HTTP/2 を終端してリクエスト単位に分解し、バックエンドへは新しいコネクションで組み立て直して送る。ターゲットグループのプロトコルバージョンの既定は HTTP1 で、この場合は HTTP/1.1 に変換されて中継される。AWS 公式ドキュメントにも、既定ではターゲットへ HTTP/1.1 で送ると明記されている。

今回の2件はどちらも、攻撃者が NGINX に直接 HTTP/2 フレームを送って初めて成立する。バックエンドが HTTP/1.1 なら脆弱なコードが外部トラフィックで実行されることはなく、この経路については緩和が成立する。CDN や WAF が HTTP/2 を終端してもバックエンドへ HTTP/2 で話す構成と違い、プロトコル自体が届かない形になる。

緩和が崩れる条件

1. ターゲットグループのプロトコルバージョンが HTTP2 または gRPC に設定されている。

2. NLB のパススルー、インスタンスへの直接アクセスなど、ALB を迂回して NGINX に届く経路がある。VPC 内部からの攻撃も同様に防げない。

3. 将来の構成変更で露出が戻る。緩和はパッチの代わりにはならない。

したがって、インターネット向けが ALB 経由のみでプロトコルバージョンが HTTP1 の環境では、緊急度を落として計画的に修正版へ上げる進め方が取れる。それ以外の経路が1つでもある場合は、通常どおり優先的に対応する。

自分の環境の確認観点

  • NGINX のバージョン（1.31.9 / 1.30.7 未満は対象）
  • http2 を有効にした listen の有無（listen ... http2 または http2 on;）
  • インターネットから NGINX へ直接届く経路の有無（ALB 以外の入口、NLB、直接公開）
  • 前面の ALB のターゲットグループのプロトコルバージョン設定
  • スキャナが「該当」と出した場合は、バージョン判定か実構成の判定かを確認する

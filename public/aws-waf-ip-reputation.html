AWS WAF · 調査メモ

不審なアクセス元は、
AWS WAFでどこまで止められる？

該当するのは「Amazon IP reputation list」。
悪性・偵察IPの遮断をAWSの脅威情報に任せられる。ただし、今回公表されたIP・UAへの対策は、別に検討する。

確認日：2026年10月8日 · JPCERT/CC注意喚起の公表日：同日
公開資料による整理。個別環境の設定・ログは未確認。

まず選ぶルール

最初の候補
Amazon IP
reputation list

AWSの脅威情報に基づく悪性IP・偵察IPを対象にする。「不審なアクセス元を止める」目的に最も近い。

グループ名：AWSManagedRulesAmazonIpReputationList

用途を絞って検討
Anonymous IP list

VPN・プロキシ・Tor・ホスティング事業者等のIPが対象。正規のVPN利用者、外部サービスのAPI通信も止まり得るため、特にHostingProviderIPListの一律Blockは慎重に。

グループ名：AWSManagedRulesAnonymousIpList

今回の事案への補助
手動IP set・UA条件

公表IPは期限を決めたIP setで検討。UAは対象パス・HTTPメソッド・頻度と組み合わせる。Chrome、curl、python-requestsという名前だけで全体を遮断しない。

AWSの仕様：IP reputation rule groups。優先候補と運用上の注意は、この仕様に基づく判断。

導入は「観測 → 調整 → 遮断」

  1. 1. Countで観測各ルールのアクションをCountへ上書き
  2. 2. 正規通信を確認ラベル・パス・件数をログと突き合わせる
  3. 3. 必要な範囲をBlock誤検知を調整し、戻す条件も決める

Countは遮断せず後続の評価へ進む。他ルールでは遮断され得る。AWS：ルール単位のCount上書き / アクションの意味

JPCERT/CCの8IPが、AWSのマネージドリストに含まれる保証はない。

公表IP・UAは過去の観測情報。現在は正規利用されている可能性があり、一致しただけで攻撃・被害の確定にはならない。UAだけの遮断も回避されやすい。

JPCERT/CC：2026年10月8日の注意喚起

WAFは補助防御。APIの認証・認可、最小権限、機能別レート制限、修正済みバージョンへの更新は別に必要。マネージドルールだけで情報漏えいを防げるとは言えない。

AWSの正式ルール名・既定アクション

Amazon IP reputation list

AWSManagedIPReputationList：悪性活動IP
Block
AWSManagedReconnaissanceList：AWSへの偵察IP
Block
AWSManagedIPDDoSList：DDoS活動IP
Count

DDoSリストは既定で遮断しない。他の2ルールと同じBlockだと思い込まない。

Anonymous IP list

AnonymousIPList：匿名化サービス等
Block
HostingProviderIPList：ホスティング・クラウド事業者
Block

HostingProviderIPListのリストはAWSのIPを含まない。これはAmazon IP reputation listの対象外であることを意味しない。

両グループとも、判定はAWS WAFが受け取るリクエスト起点の送信元IPに基づく。手前に第三者プロキシ等があると、そのIPを見てしまうことがある。これらのグループを任意のX-Forwarded-For検査に切り替える設定はない。

このカテゴリにはバージョン固定・SNS更新通知の仕組みがない。公開指標との一致を前提にせず、継続的に正規通信への影響を確認する。

設定前の確認点：Count、優先順位、手動対策
  1. Countはルール単位で指定。RuleActionOverridesで各ルールをCountへ上書きする。グループ全体の返り値だけをCountにする方法では、内部の最初のBlock一致でグループ内の評価が止まり、全ルールの観測には不向き。AWS：2種類の上書きの違い
  2. Allowの位置を確認。優先順位の数値が小さい順に評価され、Allow・Blockで終了する。広いAllowが先にあると、後ろの防御ルールを通らない。例外は対象のルール・パス等を絞り、他の検査まで迂回させない。AWS：評価順 / 終了アクション
  3. 公表IPは短期の補助。自環境のアクセス内容と照合してから、必要なら単一IPv4の/32を手動IP setへ。見直し日・解除条件・担当を決める。AWS WAFのIP setに自動失効がある前提で放置しない。
  4. UAは狭い条件で観測。対象API・メソッドとUAの一致、またはその範囲への頻度超過を確認する。レート閾値は正規のバッチ・API利用量を見て決める。汎用UAだけの全サイト遮断は避ける。AWS：レートベースルール / 検査範囲を絞る設定
  5. IPの取得経路を確認。手動IP set・レートベースルールで転送ヘッダーを使う場合、信頼できるプロキシが上書きするヘッダー、欠落時・不正値時の扱いまで確認する。Scope-downの転送IP設定は、外側のマネージドルールへ引き継がれない。AWS：転送IP / 設定の非継承

ログでは送信元IP・URI・メソッド・件数・応答の変化を突き合わせる。HTTP 200だから安全とも、IP一致だから侵害とも判断しない。不審な操作があればログを保全し、アプリ・DB側の記録と確認する。

Amazon Inspector 2026年11月の変更：AMIスキャン、ランタイム到達性分析、Code Securityの拡張

確認日：2026年11月25日
一次資料：AWS公式 What's New（2026年11月1日〜24日の投稿）と、Amazon Inspector User Guideなどの公式ドキュメント。各項目の詳細は公式発表とドキュメントへのリンクつきです。全体の索引はAWS 2026年11月の発表まとめ。

要点
  1. 11月2日、EC2のAMI（マシンイメージ）がInspectorのスキャン対象に加わりました。インスタンスを起動せず、裏付けのEBSスナップショットから検査します。
  2. 11月23日、ECRとEC2の検出結果にランタイム到達性分析が付きました。脆弱なパッケージが実際に使われる場所にあるか、動いているかで優先付けできます。
  3. 11月19日、Inspector Code SecurityがGitHub Enterprise Serverに対応し、GHESとGitLab Self-Managedへのプライベート接続も入りました。自動修正プルリクエストもパブリックプレビューで始まっています。
  4. 11月17日、Security Hubの監視対象がGoogle Cloud Platformへ広がりました。脆弱性管理を担うAmazon Inspectorでも、GCPへの統合を単独で作れます。

概要

Amazon Inspectorは、ワークロードを自動で発見し、ソフトウェアの脆弱性と意図しないネットワーク露出を継続的にスキャンする脆弱性管理サービスです。対象はEC2インスタンス、ECRのコンテナイメージ、Lambda関数などで、検出結果（finding）には、その環境に合わせてNVDのCVSS基本値を調整したInspectorスコアが付きます。

2026年11月のInspector関連の発表は4件です。スキャン対象にAMIが加わり（11月2日）、検出結果の優先付けにランタイム到達性が入り（11月23日）、コード側のCode SecurityがGitHub Enterprise Serverとプライベート接続に対応し（11月19日）、管理面ではSecurity Hubの監視対象がGoogle Cloud Platformへ広がりました（11月17日）。分野別のまとめでは、AMIスキャンと到達性分析はコンピュート・ストレージ記事、残りの2件はセキュリティ記事に分かれて載っていたため、この記事に4件を集約し、公式ドキュメントで補って詳しくします。

AMIスキャン：起動前のイメージを検査する（11月2日）

公式発表。Inspectorの脆弱性スキャンがEC2のAMI（マシンイメージ）へ広がりました。インスタンスを起動しなくても、追加のソフトウェアを入れなくても、AMIの段階でソフトウェアの脆弱性を見つけられます。脆弱なイメージからインスタンスを大量に起動する前に、元側で直すための仕組みです。

仕組みはイメージを裏付けるEBSスナップショットを読む形です。Inspectorは対象イメージのすべてのEBSスナップショットからソフトウェアインベントリを集め、50以上のデータフィードから得た脆弱性データと照合します。検出結果はPackage Vulnerability型で、リソース種別は MACHINE_IMAGE になります。

使い方には2つの方式があります。

継続スキャン（既定）：アカウント単位、または組織全体でAMIスキャンを有効化します。Security Hubの利用者は、アドオンとして組織全体へ有効化でき、検出結果はSecurity Hubにも届きます。有効化すると、対象のイメージを作成・コピー・登録・有効化するたびにスキャンし、そのイメージに関係する新しいCVEがInspectorのデータベースに加わると再スキャンします。範囲はタグで制御でき、除外するイメージにタグを付ける除外モードが既定で、対象にするイメージだけにタグを付ける対象指定モード（inclusion mode）も選べます。

オンデマンドスキャン：EC2コンソールから特定のAMIを指定する単発のスキャンです。Inspectorを有効化していなくても実行でき、同時に進められるのは20件までです。結果の受け取りはEventBridgeだけで、InspectorのコンソールやListFindings APIには出ません。要約と詳細はEC2コンソールのAMIのSecurityタブで見ます。APIでは、要約が describe-images の ScanResults、詳細が get-image-findings で返ります。AMIを共有するとスキャン結果も共有先で見られ、AMIをコピーすると要約と上位50件の検出結果がコピー先へ引き継がれます。

スキャンの対象になるのは、自アカウントが所有するイメージだけです。条件は、裏付けのEBSスナップショットも自アカウントが所有すること、EBS backedで状態が available であること、対応OSであること、単一のOSで構成されること、スナップショットのファイルシステムがext3／ext4／ntfs／xfsのいずれかであることです。LVMを使ったイメージはスキャンできず、状態は UNSUPPORTED_OS になります。共有イメージや公開イメージを調べたい場合は、先に自アカウントへコピーします。

スキャン結果は起動の制御にも使えます。Allowed AMIsの設定にスキャン結果の条件（ScanResultCondition）を入れると、セキュリティ基準を満たすAMIだけをアカウントで使えるようにでき、この設定は宣言型ポリシー（Declarative Policies）で組織全体へ強制できます。AMIを作る側では、EC2 Image Builderのパイプラインにスキャンを組み込み、基準を満たさないAMIの配布を止めることもできます。

料金は継続スキャンとオンデマンドスキャンのどちらも課金対象です（金額はInspectorの料金ページ参照）。提供範囲はInspectorが利用できるすべての商用リージョンです。

ランタイム到達性分析：検出結果の優先付け（11月23日）

公式発表。ECRのコンテナイメージとEC2インスタンスを対象に、検出結果へランタイム到達性分析が付きました。従来は、リソースで見つかった脆弱性をすべて報告していたため、アプリケーションが使っていないパッケージの脆弱性も同じ列に並び、どれが実際に危ないかの見極めは人手でした。今回の分析は、脆弱なパッケージが実行時に届く場所にあるかを自動で判定し、優先付けの材料にします。

判定の根拠は対象ごとに異なります。コンテナイメージでは、脆弱なパッケージのファイルパスと、イメージのDockerfileにある WORKDIR／ENTRYPOINT／CMD が指すディレクトリを比べます。パスの内側にあれば REACHABLE、外側にあれば NOT_REACHABLE です。コンテナを実行して確認するわけではないため、公式ドキュメントは、パス内にあることが実際に読み込まれることの証明にはならないと明記しています。

EC2インスタンスでは、スキャンした時点で、脆弱なパッケージがプロセスまたはサービスとして動いているかを見ます。観測されれば REACHABLE、されなければ NOT_REACHABLE で、判定はスキャンのたびに付け直されるため、値が変わることもあります。この判定を使うには、Inspector VM Scannerによるエージェント型スキャンが必要です。VM ScannerはInspector SBOM Generatorでインベントリを集める方式で、Enhanced EC2 Scanningを有効にするとSystems Manager経由で自動導入され、手動インストールもできます。

結果は検出結果の vulnerablePackages にあるパッケージごとに、状態を示す runtimeReachability（REACHABLE／NOT_REACHABLE／UNKNOWN）と、根拠を示す runtimeReachabilityReason として付きます。同じ検出結果の中でもパッケージごとに値が違うことがあります。両フィールドは検出結果のフィルタと抑制ルールに使えます。ただし評価の仕方は同じではありません。フィルタは1つでも一致するパッケージがあればその検出結果を返しますが、抑制ルールの NOT_REACHABLE は、すべてのパッケージが NOT_REACHABLE のときにだけ抑制します。

公式ドキュメントも、この状態は根拠に基づく目安であり、決定的な信号ではないと注意しています。NOT_REACHABLE でも、そのパッケージが動かないことや、脆弱性が悪用できないことを意味しません。検出結果の重要度そのものも変わりません。

対象は AWS_ECR_CONTAINER_IMAGE と AWS_EC2_INSTANCE の2種だけです。Lambda関数、AMI（MACHINE_IMAGE）、ECRリポジトリ、コードリポジトリ、AzureとGCPのリソースの検出結果には付きません。新しく作られる検出結果には最初から含まれ、既存の検出結果へは時間をかけて順次付きます（バックフィル）。追加料金はなく、Inspectorが利用できるすべてのリージョンで使えます。

Code Security：GHES対応とプライベート接続（11月19日）

公式発表。Inspector Code Securityは、自社（ファーストパーティ）のアプリケーションコード、サードパーティの依存関係、IaCの脆弱性を、コードリポジトリ単位でスキャンする機能です。対応するリポジトリはGitHubとGitLab Self-Managedでしたが、今回GitHub Enterprise Server（GHES）が加わりました。

あわせて、GHESとGitLab Self-Managedへのプライベートネットワーク接続が入りました。プライベートネットワークに置いたGHESやGitLab Self-Managedへ、VPC構成（VPC、サブネット、セキュリティグループ、GHESのURLを指定）またはAWS CodeConnections（CodeConnectionsホストとVPCエンドポイント経由）で接続します。AWSのIPアドレス範囲全体へファイアウォールを開けずにスキャンできる点が、公式の打ち出しです。プライベート接続には、ネットワークリソースとCodeConnectionsを扱う権限を持つ専用のIAMロールが要ります。公式ドキュメントにはCloudFormationテンプレートも用意されています。接続の設定後は、GHES側にGitHub Enterprise Server Appを作成してインストールし、統合を完了させます。

もう1つ、自動修正プルリクエストがパブリックプレビューで始まりました。SAST（静的アプリケーションセキュリティテスト）の検出結果について、Inspectorが提案する修正を、そのままプルリクエストとして作成します。対象は、自分で設定した重大度以上で、信頼度の高い修正だけです。マージするかどうかは開発者がレビューして決めます。

提供範囲はCode Securityが利用できる10リージョンです。米国東部（バージニア、オハイオ）、米国西部（オレゴン）、欧州（フランクフルト、アイルランド、ロンドン、ストックホルム）、アジアパシフィック（東京、シドニー、シンガポール）で、日本からも東京リージョンで使えます。

Security HubのGCP拡張：Inspectorでも単独に統合できる（11月17日）

公式発表。この発表はWhat's NewでInspector側のタグが付いていたもので、内容の主役はAWS Security Hubです。Security HubがGoogle Cloud Platform（GCP）のリソースを監視するようになり、リスク分析、クラウドセキュリティ姿勢管理、脆弱性管理、セキュリティ対応の管理を、AWSとGCPの両方に広げました。すでにあったMicrosoft Azureの監視に続く、マルチクラウド方向の拡張です。

Security HubはGCPのリソースを自動で発見します。対象はGCPのVM、Google Artifact Registryのコンテナイメージ、Cloud Run関数、IDです。設定ミス、インターネットへの露出、ソフトウェアの脆弱性を評価し、CISベンチマーク（Google Cloud Platform Foundations）などのセキュリティ基準で姿勢チェックを行います。検出結果はAWS側と同じ形式と優先付けで同じ画面に並び、EventBridge連携による自動応答の仕組みもそのまま使えます。

Inspectorとの関係は、統合の作り方にあります。GCPへの統合は、姿勢管理チェックを行うSecurity Hub CSPMと、脆弱性管理を行うAmazon Inspectorで、それぞれ単独にも作れます。つまり、Security Hub全体を入れなくても、Inspector側だけの統合でGCPリソースの脆弱性管理を始めることができます。

料金はGCPリソースの監視に30日間の無料トライアルがあり、統合を作ると始まります。終了後は同等のAWSリソースと同じ価格です。統合を作れるのはSecurity Hubが利用できるリージョンのうち、中東（UAE）、中東（バーレーン）、アジアパシフィック（台北）、アジアパシフィック（ニュージーランド）を除く全リージョンです。

Agent Harness とは何か

モデルが一度だけ文章を返す仕組みと、仕事を終えるまで動くエージェントは違う。後者には、状況を読み、ツールを実行し、結果を観測して次の一手を決める実行ループが必要だ。そのループと周辺の制御系が「ハーネス」である。

モデルは推論を担う。しかし、どのファイルが読めるか、操作に承認がいるか、失敗した作業をどこから再開するかは、モデルの知識だけでは決まらない。

プロンプトの外にある設計

コンテキスト圧縮、セッション履歴、Sandbox、ツールの権限、進捗イベント、サブエージェント、検証。これらを組み合わせると、同じモデルでも仕事の進め方が大きく変わる。

つまり「どのAIが賢いか」だけを比べる時代から、「どの環境なら、その賢さを安全に発揮できるか」を問う時代へ移っている。

モデルの推論は「一部」。本当に仕事をするには、ツール実行の結果を再びモデルへ返し、完了を確かめるまで循環させる。下図は一般化した構造で、個別製品の内部実装を厳密に再現したものではない。

用語の整理

似ている言葉を、混ぜない。

MODEL

LLM

推論・文章生成・行動選択を行う「頭脳」。それ自体が外部システムの操作権限を持つとは限らない。

RUNTIME

Harness

モデル呼び出し、ツール実行、状態、承認、再試行を組み合わせる「実行系」。

PROTOCOL

MCP

外部ツールやデータへ接続するためのプロトコル。ハーネス全体の代わりにはならない。

PROCEDURE

Skills

再利用できる専門手順や知識。実行エンジンではなく、エージェントが参照する技能。

POLICY

AGENTS.md 等

リポジトリや作業環境固有の指示。守らせるには権限設定・CI等による実装上の制約も必要。

VERIFICATION

Evals / CI

「言った」ではなく「できた」を確かめる仕組み。実際の副作用や成果物を検証する。

運用者への提言

「実行した」と
「完了した」は違う。

Agent Harnessの本当の価値は、途中の失敗や権限の境界が現れたときにわかる。ハーネス設計では、成果物と環境の状態を検証可能にすることが最優先になる。

CASE FILE / GitHub の不具合修正を依頼したら
01調査仕様・Issue・コード
02修正隔離環境で変更
03検証テスト・lint・build
04PR / CIレビューと承認
05配備本番動作を別確認
中断・失敗時は？現在状態・実行ログ・次の行動・再開条件を保存。承認前の操作や未検証の工程を「完了」に進めない。
壱

記録は外へ

進捗、失敗、成果物、保留理由を会話の外に永続化。コンテキストが消えても再開できるようにする。

弐

権限は狭く

閲覧・編集・公開を分け、秘密情報を実行環境から隔離する。承認ルールは文章だけでなく実行系で強制。

参

検証は外部事実で

PR作成、CI成功、マージ、デプロイ、本番確認を別々に記録する。AIの自己申告だけでは判定しない。

四

回復を設計する

上限付き再試行、冪等な操作、タイムアウト、再開地点を準備。アクセス拒否は障害ではなく境界として扱う。

後記 / HARNESS ENGINEERING

良いプロンプトの次は、
良い作業環境を設計する。

OpenAIのHarness Engineeringは、仕様・ドキュメント・テスト・lint・CI・フィードバックを、エージェントが理解し利用できる形で整える開発思想を示した。目的を明確にし、変更に強い検証ループを作ることが鍵になる。

ハーネスには万能の正解がない。構成可能性を重視するDSH、常駐の使い勝手を重視するHermes、開発作業を研ぎ澄ますCodex。それぞれの選択は「頭脳の賢さ」だけでは決まらない。

GoのLambda、
ZIPとコンテナは
どちらが速い？

ZIPが最速とは限らない。
公式OSイメージでも、同速の保証はない。
配布形式だけでは勝敗は決まらない。Goの同一アプリを同じ条件で測るまでは、「何ms速い」とは言い切れない。

仕組みから分かること

コンテナには専用の最適化

Lambdaはイメージの事前処理・キャッシュ・必要部分の読み込みを活用する。「毎回、巨大なDockerイメージを丸ごと取得する」だけの構造ではない。[3]

実測でまだ言えないこと

Goの普遍的な速度差

今回確認できた資料では、現在のGoを同一条件でZIPと公式OSイメージに分けた、十分な直接比較は見つからなかった。他言語の数値はGoの予測値にしない。

この調査からの判断

速度だけを理由に移行しない

既存の公式コンテナをZIPに戻す根拠は、一般論だけでは弱い。まず応答時間の比較を。厳しい遅延要件なら、配布形式とは別にProvisioned Concurrencyを検討する。[10]

同じGoでも、届き方が違う。

ZIPかコンテナかは「配送方式」。Goの初期化が終わっているかは、別の話。

概念図 / 時間の比較ではありません

公式ベースイメージの利点はある

AWSは公式イメージを積極的にキャッシュすると説明している。ただし元資料は主に配置・更新の最適化の話。「Goの各コールドスタートがZIPと同速」と保証する記述ではない。[2]

小さい独自イメージにも、一律の勝敗はない

イメージ全体のサイズと、起動時に実際に読む量は別。キャッシュの当たり方や初期化処理も関わるため、総MB数だけの比較では不足する。独自イメージもLambda側の読み込み方式の対象になる。[3]

もう一段深く：キャッシュは「Goが起動済み」という意味ではない

色付きのブロックは、その時点で必要な部分のイメージ。割合は模式的で、実測ではありません。

AWSの論文では、配置時にOCIレイヤーをブロック形式のファイルシステムへ平坦化し、重複排除と段階的なキャッシュを使い、必要な部分を要求時に読み込む方式を説明している。通常のDockerホストで起動する処理を、そのまま各Lambda呼び出しに当てはめるのは不正確。[3]

バイト列のキャッシュ、初期化済みのスナップショット、実行待機中の環境は別物。最後のものを用意するのがProvisioned Concurrency。ベースイメージがキャッシュされていても、アプリの初期化やDB接続の待ち時間が消えるとは限らない。[2][5][10]

数字は、比較した条件とセット。

Goの実測がない部分を、RustやNode.jsの数字で埋めない。

Goの直接比較は未確認

「Go / ZIP」と「同じGo / AWS公式OSイメージ」のどちらが何ms速いかは、この調査では確定していません。以下は仕組みの理解に役立つ、別の比較です。

SnapStartは、初期化を
「復元」に置き換える。

元の初期化が軽いと、復元にかかる時間が上回る場合がある。逆に重い初期化では改善が大きくなり得る。[7]

このグラフはGoの性能予測でも、ZIP対コンテナの比較でもありません。Goでの改善率や、「何秒以上なら必ず得」という境界値は、ここからは決められません。

p50は中央値。まれに遅い呼び出しが問題になる用途では、p95・p99などの裾側と、失敗・再試行も別に評価します。

2024年のZIP対コンテナ比較は、Goではない

AJ Stuyvenberg氏の実験はNode.js 18とPython 3.11が対象。同一リージョンでコールド呼び出しの往復時間を測り、追加依存がNode.jsで約30 MB、Pythonで約200 MBを超える条件ではコンテナ優位と報告している。数千回の測定だが、これらの閾値を現在のGoやイメージ全体のサイズに転用することはできない。[4]

この実験が否定するのは「どんな関数でもZIPが必ず速い」という一般化。Goの同速や優劣を直接証明するものではない。

GoのSnapStartは、コンテナで条件付き。

2026年9月2日にコンテナイメージ対応が発表された。OSイメージを選ぶだけで、安全に有効になるわけではない。[5][6]

利用時はSnapStart設定を有効化してバージョンを発行し、そのバージョンまたはエイリアスを呼び出す。$LATESTは対象外。同じバージョンでProvisioned Concurrencyとは併用できない。[15][16]

「DB接続が遅いから、その接続ごと保存」で完了ではない。
初期化で作った一意ID、時刻に依存する状態、認証情報、ネットワーク接続は復元後の扱いを検証する。復元時の再接続や再取得の時間も応答時間に含める。[6][15]
フック・ラベル・料金と、古い資料との読み分け

独自ランタイムで復元前後の処理が必要なら、公式のライフサイクルAPIを実装する。フックが不要だと検証できた場合は、次のラベルで対応を明示できる。ラベルは安全性を自動検証するものではない。[6]

# 復元後の状態の安全性を確認し、フックが不要な場合だけ
LABEL com.amazonaws.lambda.feature.snapstart="Allow"

コンテナのSnapStartにはスナップショットのキャッシュと復元の追加課金がある。料金はメモリ量・バージョン・復元回数などに依存するため、「Javaの一部構成で追加料金なし」をGoコンテナへ一般化しない。正確な対象リージョン・単価は料金表で確認する。[12][16]

資料の鮮度に注意。今回取得できた概要ページには「コンテナ非対応」という旧記載が残る一方、2026年9月2日の発表とコンテナ専用ガイドは対応を明記している。本レポートは新しい発表と専用ガイドを優先した。2026年10月6日は解説記事の公開日であり、対応開始日ではない。実AWSアカウントでの有効化はこの調査では試していない。[5][6][15][16]

Init Durationだけを競わせない。

利用者の待ち時間と、Lambdaの初期化ログは、同じ時計ではない。

まず、往復時間

呼び出し元で応答完了まで計測し、同じ条件で比較する。InitやRestoreは「なぜ遅いか」の切り分けに使う。[4][9]

コールド群を分ける

全体のp99だけでは、頻度が低いコールドを見落とし得る。コールド比率・件数・コールド群のp95/p99を、全体の値と分けて残す。

同じ呼び出しを足す

一般に p95(A) + p95(B) は p95(A+B) ではない。内訳を合算する場合は、呼び出しごとに足してから分位点を取る。

再現できる比較の設計：何を揃え、何を記録するか

第1段階は配布方式だけを変える

比較の提案：同一Goソース・ビルドフラグ・アーキテクチャ・依存関係のバイナリを使い、ZIPと公式OSイメージを用意する。静的リンクなどで実行条件を揃えられることを確認し、SHA-256を記録する。メモリ、リージョン、ネットワーク、拡張機能、トリガー、接続先、入力、タイムアウトも揃える。

Gin/EchoをWeb Adapter経由で動かす構成と、Runtime APIを直接扱うGoハンドラーを混ぜない。アダプターや起動確認の違いまで「ZIP対コンテナ」の差にしない。公式OSイメージと独自イメージの比較は次の段階に分ける。[1]

第2段階でメモリとアーキテクチャを調整

例えば512 / 1,024 / 1,769 MBを別条件として比較する。これは検証候補であって最適値ではない。AWSではメモリに応じてCPU資源が増え、1,769 MBで1 vCPU相当となるが、初期化全体が比例して短くなるとは限らない。arm64とx86_64の差も、配布方式の差から分離する。[11]

コールドの作り方と、測れないものを残す

  • 新規配置直後、しばらく使わなかった後、並列数を増やした時を別ケースにする。新しい環境でも、AWS内部のイメージキャッシュまで空になったとは限らない。[3]
  • 環境変数の変更などで新規環境を促す方法はあるが、オンデマンドでも事前初期化が起こり得る。Initログの存在だけで、その時間を要求が待ったと断定しない。[4][8]
  • 失敗後の再初期化（suppressed init）やタイムアウトを捨てない。通常のInitは10秒を超えると呼び出し時に再試行される場合があるため、極端に重い初期化の倍率には、この挙動が混ざり得る。[8]
  • 提案として各条件100件程度から傾向を見て、p99を重視するなら1,000件以上など追加標本とばらつきを検討する。固定回数で信頼性が保証されるわけではない。n、測定期間、失敗率、分位点の計算法も記録する。

API GatewayのIntegrationLatencyは統合先との往復、Function URLのUrlRequestLatencyはURL側での受信から応答まで。どちらもブラウザーとAWS間の通信をすべて含む指標ではない。[9]

このページではAWS関数の作成・負荷試験・課金を伴う検証は実施していない。ここに書いた測定設計は、公開資料と測定上の考え方からの提案である。

では、どこから手を付ける？

配布方式の引っ越しより先に、遅い部分を切り分ける。

すでに公式コンテナで稼働

構成を維持して、ZIPとのA/Bを先に。

「ZIPは軽いから速いはず」だけでは移行しない。差が実測できなければ、運用・配布のしやすさで選ぶ。これは調査からの判断であり、速度保証ではない。

小さいGo関数を新しく作る

ZIPは単純な出発点。最速の証明ではない。

コンテナが必要なら、最終イメージにビルドツールを残さない。-tags lambda.norpcは不要な旧RPC処理を除き、バイナリを小さくできる。改善幅は実測する。[1][2]

アプリの初期化が重い

初期化を整理し、SnapStart有無を測る。

復元後も安全な状態か確認する。重い処理をハンドラーへ移してInitだけ短くしても、初回応答が短くなるとは限らない。[6]

まれな遅さも厳しく制限

Provisioned Concurrencyを別軸で検討。

初期化済み環境を待機させる選択肢。ただし確保数を超える呼び出し、ハンドラーや接続先の遅延は別途考える。Reserved Concurrencyは同時実行数の制御であり、事前起動ではない。追加料金も比較する。[10][12]

採用しなかった数字・古い前提

「Goコンテナ20 ms」「9 MBなら35〜45 ms」という値は、提示されていた2023年のエムスリー記事から根拠を確認できなかったため、採用していない。同記事のローカルRIE実行ログを、AWS本番のコールド往復時間に置き換えることもできない。[14]

小標本のGoのInitだけを、コンテナの往復時間と並べた順位表は作らない。また、旧ベンチマークの「マネージドZIPのInitは非課金」という費用前提は、2025年8月1日の課金統一後の判断には使わない。[13]

Brotliの脆弱性、
何を確認すればいい？

「圧縮を使っているから、すべて危険？」と慌てる前に。CVE-2026-111497のポイントは、外から届いたデータを、どのソフトが展開するかです。仕組みと確認の順番を、図で整理します。

先に押さえたいこと

問題はBrotliの展開処理にあります。攻撃者が用意した圧縮データを、影響を受ける実装で処理する経路があるかを確認してください。

Node.jsとGoogle Brotliには修正版が公開され、10月26日にはLinux配布元などの更新情報も増えています。「修正待ち」の情報だけを見て判断せず、実際に動いている環境まで更新・確認するのが大切です。

バックエンド／インフラ担当は、何からやる？

影響製品をすべて暗記する必要はありません。「サービスごとに、どのBrotliが、誰のデータを展開するか」を一行ずつ埋めます。以下は公式の成立条件から組み立てた運用上の優先順位です。組織の変更管理・保守手順に合わせて使ってください。

  1. 担当サービスと実行場所を一枚にする

    VMだけでなく、コンテナー、sidecar、バッチ、CI runner、サーバーレスのカスタムイメージを列挙。各行に担当者、OS／ランタイム、イメージdigest、Brotliの供給元、外部通信・アップロードの有無を記録します。全社の調査完了を待たず、分かった行から更新計画を進めます。

  2. 「外から受ける」と「外へ取りに行く」を両方調べる

    APIの圧縮リクエストだけでなく、URLプレビュー、クローラー、画像取得、Webhook後のURL取得、外部API応答、取り込みファイルも対象候補です。公開ポートがないジョブでも外部応答を自動展開していれば確認が必要。機能名だけで到達ありとは断定せず、実際のライブラリ・設定・データ経路で判定します。

  3. 到達性と権限で順番をつける

    優先A：未修正で、攻撃者が内容を制御できるデータを展開する経路が確認できたもの。認証前の入力や任意URL取得、秘密情報や本番権限を持つworkerは特に優先。優先B：未修正だが到達性が未調査のもの。「不明」は「対象外」にせず、担当と確認期限を置きます。優先C：修正済みを証明できるもの／当該デコーダーを使わないと証明できる経路。判断根拠と対象範囲を残します。

  4. 供給元ごとに修正し、小さく展開する

    OSパッケージはディストリビューションの修正リビジョン、同梱ランタイムやwheelはその配布物、コンテナーは修正を含むイメージへ更新します。ステージングで正常なbr／gzip／非圧縮応答と通常のAPIを確認し、少数台から展開。更新失敗時の戻し先が脆弱版なら、戻す際の経路制限もあらかじめ決めます。

  5. 稼働実体の切替まで確認して閉じる

    パッケージ更新だけで終了せず、対象プロセスを通常手順で再起動・再配備。全レプリカ、待機系、CronJobのテンプレート、CIイメージも確認します。新しい起動時刻、実行バイナリー、実際のイメージIDと修正版の証拠、ヘルスチェックを一緒に保存します。疑わしいクラッシュや侵害兆候があればログを保全し、組織のインシデント対応へ切り替えます。

今日のゴールは「全部安全」と言うことではない
各サービスを「対策済み・到達するため優先対応・未調査・当該経路では対象外」に分け、担当と次の行動を決めることです。単にスキャナーの検出数がゼロになった、という記録だけでは不十分です。

そのまま使える確認台帳の項目

サービス／担当者／実行場所／OS・CPU／実行物・image digest／Brotliの供給元（OS共有・同梱・不明）／外部入力の種類／解凍機能・設定／現在版と配布元の修正根拠URL／到達性（あり・未調査・なしとする根拠）／対処と期限／再起動・再配備済みか／全台確認の証拠／残る例外。

認証情報、環境変数の値、Cookie、個人データ、実際の通信本文を貼り付ける必要はありません。パッケージ情報と判断根拠だけで整理してください。

OS・アプリ・イメージの三層で棚卸しする

OSの共有ライブラリ
RPM／debのBrotliを使用する構成。上流の版番号だけでなくパッケージの完全なリビジョンとベンダーの勧告を照合します。古い数字でも修正がバックポートされている場合があります。
アプリへの同梱
Node.js／Bun、自前ビルド、Python wheel、自己完結型.NETなど。OSのBrotliを更新しても別コピーは変わりません。逆にディストリビューション版がOSの共有Brotliを使う場合もあります。同じ製品名でも配布元ごとに確認します。
コンテナー・CI
ホストOSとは別のファイルシステム・実行物です。ベースイメージとアプリ依存の両方を更新し、イメージを再ビルド・再配備します。タグ名が同じでも中身は変わるため、実際のdigestを記録。古いビルドキャッシュや固定digestを見落とさないようにします。[15] [16]
sidecar・管理基盤
プロキシ、サービスメッシュ、エージェントにも独立した配布物があります。アプリだけ更新して終えず、利用製品のセキュリティ勧告を確認します。ただし、製品がインストールされているだけでこの攻撃経路があるとは断定しません。
SaaS・マネージド
提供元管理のランタイムと、利用者が持ち込むコンテナー・レイヤー・依存を分離。提供元の対策告知、利用リージョン／版、利用者側の再配備要否を確認します。「クラウドだから全自動で修正済み」とも「すべて自分で更新」とも決めません。
変更を伴わない棚卸しコマンドの例と、分からないこと

管理権限のある対象環境で、必要なものだけ実行する例です。これらは版・構成の手がかりであり、単独で合否を判定するスキャナーではありません。出力を外部へ共有する前に、社内名や非公開イメージ名を除いてください。

# RPM 系：名前と完全なリビジョン（未導入ならエラーになる）
rpm -q brotli libbrotli curl libcurl nodejs
# Debian / Ubuntu 系：導入パッケージの版
dpkg-query -W -f='${Package}\t${Version}\n' 'libbrotli*' 'brotli*' 'python3-brotli*' 'nodejs'
# curl CLI 自身の機能・リンクされたライブラリ
curl --version
# 指定した Python / venv に登録された配布パッケージ
python -m pip show Brotli brotlicffi
# .NET：framework-dependent アプリが使う候補ランタイム
dotnet --list-runtimes

未導入エラー、コマンド不在、探索権限不足は「全体に影響なし」ではありません。curl --version はPHPや別プロセスがロードするlibcurlまで証明しません。pip show は別venv・コンテナー・同梱ライブラリを網羅せず、.NETの一覧は自己完結型やNativeAOT成果物を網羅しません。SBOM、lockfile、ビルド定義と稼働サービスを対応付けてください。

# Node：アプリが実際に使う Node のパスで確認する
node -p 'JSON.stringify({node:process.version,brotli:process.versions.brotli})'
# Kubernetes：許可された namespace の稼働 image ID を取得
kubectl get pods -n YOUR_NAMESPACE -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.name}{"="}{.imageID}{" "}{end}{"\n"}{end}'

Nodeコマンドは新しく起動したプロセスの情報です。稼働中workerの版は起動情報や既存の管理用診断で別途確認します。Pod一覧の例も通常コンテナーだけで、init container、ephemeral container、未実行ジョブの定義を網羅しません。一般公開の診断エンドポイントを新設する必要はありません。

更新までの暫定策で、間違えやすいこと

  • HTTP/2を無効にしても、このCVEの対策にはならない。名前にHTTP2が含まれますが、問題はBrotliデコーダーです。HTTP/1.1やHTTP以外から渡す圧縮データでも、同じ実装の解凍経路は残り得ます。
  • Webサーバーの「送信圧縮OFF」だけでは、裏のHTTPクライアントの解凍を止められない。Apache標準mod_brotliは出力圧縮です。調べるのはどのプロセスが外部入力を展開するか。[8]
  • Accept-Encodingからbrを消すだけで完了にしない。libcurl公式文書は、要求と異なるContent-Encodingが返る場合も説明しています。実際の自動解凍を無効化する、brを解凍前に拒否するなど、利用ライブラリが提供する制御とアプリへの影響を確認します。手動解凍や別クライアントの経路も別途対象です。[10] [11]
  • WAFやCDNの存在だけで「保護済み」にしない。外向き通信の応答、バックグラウンドジョブ、直接到達する別経路をカバーするかが必要です。外部取得の制限や該当機能の一時停止は補助策であり、更新の代替となるかは経路ごとに判断します。

暫定策は停止影響と残存経路を明記し、解除条件を「修正済みの実行物へ切替・正常動作を確認」とします。本番へ攻撃用の圧縮データを送って確認する必要はありません。

Brotliは「小さくして、元に戻す」仕組み

Brotli（ブロートリ）は、データを小さくする圧縮方式です。元の内容を失わずに戻せる「可逆圧縮」で、Webの文章やプログラムなどを運ぶときにも使われます。圧縮する処理をエンコード、元に戻す処理をデコードと呼びます。[1]

たとえるなら、圧縮は荷物を小さく梱包し、展開は箱を開ける作業です。今回の問題を考えるときは、「箱を送っているか」だけでなく、「誰が送った箱を、どこで開けているか」を見ると整理しやすくなります。

今回は何が壊れたのか

Node.jsの2026年10月21日の公式発表では、組み込まれているBrotliデコーダーに、不正な圧縮入力によって内部バッファーの範囲外へ書き込む問題があると説明されています。識別番号はCVE-2026-111497、Node.jsの評価はHighです。[2]

本来は「形式が壊れている」と停止する場面で、「まだ入力が足りない」と扱ってしまい、処理を続けることが原因です。バッファーとは、処理途中のデータを一時的に置く場所。その境界を越えて書き込むと、別のメモリ領域まで壊すおそれがあります。

公式説明では、アプリが攻撃者の用意したBrotliデータを node:zlib で展開できる場合、クラッシュやプロセスのメモリ内容の漏えい、リモートコード実行につながる可能性があります。「必ず乗っ取られる」とも「クラッシュだけだから大丈夫」とも決めつけないことが重要です。[2]

2026年10月28日 訂正・補足：以前の説明から「POSTリクエストに限る」と受け取れる場合、それは誤りです。このCVEの成立条件はHTTPメソッドではなく、攻撃者が制御できるBrotli圧縮データが脆弱なデコーダーへ届き、実際に展開されることです。GETでも外部HTTP応答や取得ファイルを解凍する経路があれば確認が必要です。反対にPOSTでも解凍しなければ、その経路について本脆弱性の成立条件は満たしません。

送信時のBrotli圧縮と受信時のBrotli解凍は別です。Next.jsもフレームワーク名だけで影響あり・なしを決められません。fetch()などの外部応答取得、next/imageなどの画像取得処理について、実際のHTTPクライアント、Content-Encoding、依存ライブラリ、Brotliデコーダーの使用有無と修正状況を確認してください。機能の存在だけで脆弱な解凍経路があるとは断定できません。Expressのリクエスト本文の自動解凍も、利用するミドルウェアと設定によって異なります。

配信する側と、展開する側を分ける

「サイトがBrotliを使っている」という情報だけでは、サーバーへの影響は判断できません。自分が作ったファイルを圧縮して送り出す処理と、外部から来たデータを展開する処理では、役割が違います。

  1. 何が動いている？
    Node.js、Bun、直接リンクしたBrotliライブラリなど、実装とバージョンを把握します。
  2. どんなデータを展開する？
    外部HTTP応答、アップロード、アプリ間通信などの入力元を確認します。自分で書いた展開コードだけでなく、依存ライブラリが行う処理も対象です。
  3. 攻撃者の入力がそこまで届く？
    入力の制御範囲と、実際に展開される経路を照合します。認証の有無だけで判断せず、機能・構成・公式情報を合わせて見ます。

圧縮して配信しているだけなら？
その事実だけでは、サーバーが攻撃者のデータを展開する経路の存在を示しません。一方、別の機能が外部データを展開している可能性は残るので、それだけで環境全体の「影響なし」とは言えません。

追記：「HTTP2Shell」は何を指す？

Aikidoは2026年10月23日公開・24日更新の記事で、この問題を「Node2Shell」から「HTTP2Shell」へ広がる問題と表現しています。これは同社記事で使われている呼称です。指しているのは同じCVE-2026-111497のBrotli展開処理で、HTTP/2プロトコルに新しい別の脆弱性が見つかった、という意味ではありません。[6]

確認対象をNode.jsだけに絞らないことが大切です。Pythonでも、HTTPクライアントが追加のBrotliライブラリを使って外部応答を自動展開する構成があります。たとえばHTTPXの公式文書は、Brotli対応ライブラリがインストールされている場合の自動展開を説明しています。自分のコードに展開処理が見当たらなくても、依存ライブラリと外部通信の先まで確認してください。[7]

ApacheやNginxという名前だけで判断しない
Aikidoは両者がデフォルトではBrotliを展開しないと補足しています。Apacheの公式文書でも、標準の mod_brotli は送信する内容を圧縮する出力フィルターです。ただし、追加モジュールや背後のアプリまで含めた安全の保証ではありません。[6] [8]

「HTTPを使うものすべてが危険」と拡大解釈せず、各製品に組み込まれたBrotli実装と、その展開経路を確認する、という読み方が適切です。

自分の環境に当てはめる：何を直して、何を確かめる？

以下は該当する構成だけを選ぶ対応例です。サービス停止や更新は組織の変更管理に従い、まず検証環境で実施します。製品名が同じでも配布元が違えば更新対象も異なります。

① Linux上のPHP・curlなど（OSの共有Brotliを使う構成）

  1. 確認：PHP-FPM／Apache／CLI／バッチを分け、実際のlibcurlがBrotliに対応するか、外部HTTP応答の自動展開を使うか確認。CLIのcurl --versionだけでPHPの構成まで判定しない。
  2. 更新対象：利用OSの勧告にあるbrotli／libbrotli等の完全リビジョンへ。独自ビルド・別prefix・コンテナー内のコピーは別確認。上流1.2.1未満という数字だけでバックポート版を未修正扱いしない。
  3. 切替：更新ライブラリを使うPHP-FPM、Apache、常駐worker等を対象ごとの通常手順で再起動・再配備。OS更新だけで既存プロセスへ読み直されたとしない。
  4. 稼働確認：対象サービスの起動時刻、配布パッケージ、参照するライブラリと正常な外部API取得を照合。CLIとWebのPHP設定が異なる場合も記録。
  5. 残る確認：PHPのソース版表示だけではBrotli修正を証明できない。Windows公式版なら10月26日の-1依存再ビルドを別途確認。[9] [10] OS別の修正版

② Node.js・Bun・Python（アプリに同梱されたBrotli）

  1. 確認：サービスが起動する実行ファイル・venv・配布元と、外部応答やファイルを展開する依存ライブラリを対応付ける。HTTPXなどの自動展開も確認。
  2. 更新対象：Node／Bunの修正を含む配布版、Pythonの該当wheel・依存を更新し、lockfile・イメージへ取り込む。OSのBrotli更新だけで同梱コピーを修正したとしない。
  3. 切替：新しい配布物でアプリ・キューワーカー・バッチを再配備し、旧プロセスを通常手順で切り替える。
  4. 稼働確認：既存の管理用診断・起動記録から実サービスのランタイム版と実行物を確認。別シェルでのnode --version、別venvへのpip showは対象プロセスの証拠にしない。
  5. 残る確認：ディストリビューション版はsystem Brotliを使う場合がある。特にDebianはNode source側の未修正表示・追加注意も照合し、共有libの更新だけで完了しない。[2] [7] [13] 配布物別の版

③ .NET・PowerShell（共有ランタイムと自己完結型を分ける）

  1. 確認：.NETアプリが共有ランタイム利用か、自己完結型か、NativeAOTかを確認。BrotliDecoderの直接利用や自動展開の有効化も調べる。
  2. 更新対象：共有ランタイムは修正対応版へ。自己完結型は修正を含むruntimeで再発行、NativeAOTは対応SDK・runtime-packで再ビルド。PowerShellは同製品の修正版へ。
  3. 切替：更新したアプリ／ランタイムを配備し、該当サービスや定期実行の起動先を切り替える。
  4. 稼働確認：実アプリがロードするランタイム、自己完結成果物のbuild ID、実ジョブで起動するPowerShell版を確認。ホストのdotnet --list-runtimesだけでは自己完結型やNativeAOTを網羅しない。
  5. 残る確認：自動展開が既定で無効でも、アプリが明示的に使う経路は別。WindowsだけでなくLinux・macOSの運用ジョブも対象に含める。[22] [23]

④ Envoy・Istio（ゲートウェイとsidecar）

  1. 確認：Brotli decompressorや該当EnvoyFilterが有効か、どの入力を展開するかを調べる。送信する圧縮だけの設定と区別する。
  2. 更新対象：製品の修正リリースと配布イメージへ更新。Istioのcontrol planeの版だけでsidecarの更新を判断しない。
  3. 切替：通常のメッシュ更新手順でゲートウェイ／データプレーンをロールアウトし、旧proxyが残らないか確認。
  4. 稼働確認：全対象proxyの実イメージ・版と通常通信、ヘルスチェックを確認。アプリPodに再配備が必要な構成はそこまで完了させる。
  5. 残る確認：Istio 1.29の修正版はEOL最終版なので、サポート系列への移行も計画。HTTP/2を切るだけでBrotliの別入力経路を直したとはしない。[24] [25]

⑤ コンテナー・Kubernetes・CI・マネージド環境

  1. 確認：上の①〜④をイメージの中にも適用。ベースOS、アプリ依存、sidecar、CI／CronJobのテンプレートを分ける。提供元管理ランタイムと自分が持ち込む依存も分離。
  2. 更新対象：修正済みベースと依存で再ビルドし、配布元の更新を取り込む。固定digestや古いビルドキャッシュを確認。
  3. 切替：更新イメージを通常のローリング手順で展開。未来に起動するジョブや待機系の定義も更新する。
  4. 稼働確認：タグ名ではなく実際のimage ID／digestで全レプリカを照合し、正常なbr・gzip・非圧縮応答と通常機能を確認。マネージド側は提供元の適用範囲・再配備要否も記録。
  5. 残る確認：ホストOS更新、同じタグの再起動、クラウド提供元の一般告知だけでは、自分の全ワークロードへの適用完了は証明できない。[15] [16]

完了条件：「修正版を選んだ」だけでなく、対象の実行物へ反映・旧プロセスの切替・全対象の稼働確認・通常機能の確認が揃ってから対策済みと記録。未調査の経路や未更新の台は、担当・期限・暫定制限を付けて残します。本番に攻撃用データを送るテストは不要です。

Infra担当向けの確認手順を追加しました（2026年10月27日）。
優先順位 → 棚卸し → 配布元別の修正版 → 更新までの暫定策を確認し、以下の手順で稼働中の実体まで反映を確かめてください。PHPに限らず、OS共有ライブラリとアプリ同梱の両方が対象です。

まずは利用中の製品・配布元の案内に沿って更新し、必要なテストと再デプロイを行います。運用環境ごとに手順は異なるため、ここでは確認すべき段階を示します。

  1. 修正が入った版を選ぶ

    公式リリースを確認します。上流のソース修正だけで、配布バイナリーやコンテナーまで更新されたとは扱いません。

  2. 実行環境を更新する

    ローカルの開発環境だけでなく、コンテナーのベースイメージ、CI、サーバーやマネージド実行環境も点検します。アプリの依存ファイル更新だけで、ランタイムが変わるとは限りません。

  3. 再起動・再デプロイする

    更新したファイルを置いただけでは、古いプロセスが動き続ける場合があります。通常の運用手順で再起動・再展開し、複数台構成なら全対象への反映を確認します。

  4. 動いているものを確かめる

    本番プロセスの起動情報、実行バージョン、配布イメージの識別子などを照合します。Node.jsなら process.version などが手がかりです。別のシェルでの node --version だけでは、稼働中のサービスまで同じ版とは証明できません。

  5. 通常機能と記録を確認する

    正規のデータを使う通常の動作確認、ヘルスチェック、ログ確認を行い、対象・版・確認日時を記録します。攻撃用データを本番へ流す必要はありません。

すぐに更新できないときは、影響する展開経路を制限できるか、製品の公式案内と運用担当者に確認してください。圧縮の設定を一か所変えただけで、すべての入力経路を塞げたとは判断しないようにしましょう。

Python：実際のvenv・CPython・pip/CAを確認

確認：対象venvを選んで、そのPythonから実行

# Linux/macOS例。Windowsなら対象venvのScripts\python.exeを使用
PY='/PATH/TO/VENV/bin/python'
"$PY" -c 'import sys,ssl; print(sys.version); print(ssl.OPENSSL_VERSION); print(ssl.get_default_verify_paths())'
"$PY" -m pip --version
# パッケージのコードをimportせず、配布メタデータの版だけ読む
"$PY" -c 'import importlib.metadata as m; names={"pip","certifi","brotli","brotlicffi","uv"}; print("\n".join(sorted(d.metadata["Name"]+"=="+d.version for d in m.distributions() if d.metadata.get("Name", "").lower() in names)))'

既定verify pathsはrequests等の全アプリが実際に使うCAの証明ではありません。アプリのCA指定・独自SSL実装も確認。空の一覧や未導入は、その環境/名前で見つからないだけです。CPython3.10以前はEOL、ソースのみの修正系列はOS/配布元の更新状況も見ます。

変更：対象venvだけ。安全な取得経路・修正済みTLS確認後

# 例：pipとcertifiを使う既存venv。以下の最低条件を満たす最新版が選ばれる
# 再現性が必要な本番では検証済みlockfile・版固定の更新手順を優先
# 古い信頼状態のままこの通常通信を安全と仮定しない
"$PY" -m pip install --upgrade 'pip>=26.2.2' 'certifi>=2026.10.19'
"$PY" -m pip check

変更：Brotliデコーダーを実際に利用する環境のみ、選んだ一方を更新

# 既存lockfileを下記の修正版または検証済み後続版へ更新し、通常の同期手順で反映するのが優先
# pip直接管理の検証用venvで、Brotliを使う場合の固定版例
"$PY" -m pip install --upgrade 'Brotli==1.2.1'
# BrotliCFFIを使う構成なら、上の代わりにこちら（両方を新規追加しない）
"$PY" -m pip install --upgrade 'brotlicffi==1.2.1.0'
"$PY" -m pip check

既にこれより新しい検証済み版ならダウングレードしません。正常データの展開テスト後、同じlockfileを本番のビルドへ取り込み、worker・コンテナを再起動/再配備して稼働版を照合します。

上はCA取得環境のためのvenv変更で、CPython本体もBrotliデコーダーも更新しません。これでBrotli対策を完了にしないでください。古いCA状態からの初回更新はPython公式のハッシュ固定bootstrap手順を確認するか、検証済み経路で修正済みCPythonを配備してから進めます。Brotli/BrotliCFFIは利用している方の修正版をロックファイルに取り込み、通常の再現可能な依存更新手順で更新。pip checkは依存整合だけで脆弱性検査ではありません。既存venvに加え、新規venv用テンプレート・ensurepip・CIも確認し、アプリを再起動します。ssl公式

Docker / Kubernetes：実イメージを確認してから更新

確認：管理権限がある対象だけ。全inspectやSecretのダンプはしない

docker container inspect --format '{{.Image}} {{.State.StartedAt}}' REPLACE_CONTAINER
# Kubernetes利用時だけ：namespaceと対象podを限定
kubectl -n REPLACE_NAMESPACE get pod REPLACE_POD -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.imageID}{"\n"}{end}'

イメージ名/タグではなく稼働image ID/digestとSBOM・ビルド記録を照合します。initContainer、sidecar、Job/CronJobや待機系は別対象。Envoy/Istioはcontrol planeだけでなく実gateway/sidecarも確認します。

変更：修正済みイメージを検証した後の、対象Deployment限定例

kubectl -n REPLACE_NAMESPACE set image deployment/REPLACE_DEPLOYMENT REPLACE_CONTAINER=REPLACE_REGISTRY/REPLACE_IMAGE@sha256:REPLACE_VERIFIED_DIGEST
kubectl -n REPLACE_NAMESPACE rollout status deployment/REPLACE_DEPLOYMENT --timeout=180s

GitOps管理なら直接変更せず、その管理元のmanifestで更新します。取得できないdigestやタイムアウトは完了ではありません。既存の復旧手順に沿って判断し、脆弱な旧版へ戻す場合のリスクも考慮します。成功後も全podのimage IDと正常動作を確認。rollout restartだけで古いイメージを修正済みにできるわけではありません。Docker公式 / kubectl公式

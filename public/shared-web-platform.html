共有Web基盤の設計

S3で静的ページを配り、Node.js®の動的処理を共有する。目指すのは「Functionが1個」ではなく、リポジトリを追加しても配信設定の手作業が増えない構成です。

最小構成は S3＋1つの共有Web Function、2つのorigin。容量が増え、権限や障害範囲を分離したくなったら、用途や信頼境界ごとのFunctionをIaCで自動生成します。アプリごとに分けても、利用者には同じURL体系を見せられます。

この記事は設計案です。AWSの公式上限と、推奨する運用上の余裕を区別します。何リポジトリを収容できるか、費用・性能・実機でのorigin認証は未測定・未検証です。

全体構成と共通化する範囲

中央のmanifestに、パス・静的成果物・動的モジュール・所属グループを宣言します。CIがS3の配置、共有サーバーのregistry、ルート設定、必要なoriginを同じ定義から生成するのが中核です。CloudFront Functionsがリクエストの配送先を選び、業務処理をWeb Functionへ渡します。

静的成果物は1つのS3バケット内のサイト別・リリース別prefixで管理する設計案です。privateなS3 REST originとS3 OACを使い、S3 Website endpointとは区別します。公開可能なブラウザー向けアセットだけを配置し、サーバーコードや秘密情報は公開しません。配備ZIPは別の非公開成果物バケットに保存し、CloudFrontの配信対象から外します。

最小の登録originはS3とsharedWebFnの2つです。グループ分割後はS3＋グループ数となり、アプリ別なら必要なoriginもIaCが自動作成します。リソース数が増えないという意味ではありません。KVSに置くのは小さなルーティング設定だけです。コード、データベース、秘密情報の保管先にはしません。単純に静的領域と/api/*を分けられるなら、固定cache behaviorで足り、KVSなしの構成も選べます。

共有するものと、分割しても残る共有範囲

全統合ではIAM・環境変数・イベントループ・メモリ・配備を共有します。1つの重い処理が別モジュールの応答を遅らせる可能性があるため、両方を同時に動かす負荷試験が必要です。リクエストごとの状態をグローバル変数へ保存せず、永続データとセッションは外部へ置きます。共通の秘密情報やIAM権限はモジュール間の隔離ではありません。

グループ分離はアプリやプロセス由来の障害範囲を狭めますが、AWSアカウント・リージョンのquotaとCloudFront自体は共有します。

パスの振り分けとキャッシュ

公開パス配送先扱い
/hogeS3静的ページ
/hoge/huga とその配下動的モジュールA共有Function内、またはAのグループ
/hoge/hoge とその配下動的モジュールB共有Function内、またはBのグループ

判定はパスの区切りを考慮したlongest prefixです。/hoge/hugaXをAへ誤配送しないこと、末尾スラッシュ・URLエンコード・正規化の扱いをテストします。元の公開パスを保持してアプリを区別し、アプリのbase pathと静的アセットURLも契約に含めます。

originやURIを変更しても、選択済みのcache behaviorは再選択されません。一般的な動的専用behaviorではminimum/default/maximum TTLをすべて0にする方針があります。ただしWeb Function OACでviewerのAuthorizationを渡す場合は、下記の別条件が必要です。アプリはprivate, no-storeを返します。認証済みデータを共有キャッシュへ載せないことが最優先です。静的アセットは別behaviorへ分け、公開アセット用のTTLを設定します。Functionsはrequest bodyを読めないため、認証と業務判断はアプリ側の責務です。[4][13]

認証ヘッダー・エラー・静的／動的混在のキャッシュ条件

動的専用behaviorのCachingDisabled（全TTL 0）という一般方針と、Web Function OACでviewerのAuthorizationを渡す条件は別問題です。managed CachingDisabledにはAuthorizationの項目がありません。Authorizationを含むcustom policyと全TTL 0の組合せは公式に成立を確認できず、推奨しません。Bearer Authorizationを渡す基準案はminimum/default TTLを0、maximum TTLを0より大きくし、Authorizationをcache keyへ含め、全動的レスポンスに共通サーバーでprivate, no-storeを強制する構成です。これは設定単体での完全なキャッシュ無効化ではなく、no-store実装に依存します。Cookie認証も別途検証が必要です。CachingDisabled＋AllViewerExceptHostHeaderだけでWeb Function OACの条件を満たす、とも本稿では断定しません。専用資料がcache policyへのAuthorization追加を求めているため、採用環境での実HTTP確認が必要です。minimum TTLが0より大きいと、private / no-storeでもその間キャッシュされるため採用しません。[10][11][6]

エラーのキャッシュは別設定です。エラーは既定で10秒キャッシュされ、403・5xx等ではno-storeだけでは防げません。キャッシュ対象のstatusごとにError Caching Minimum TTLも0とし、403・5xxがユーザー間で共有されないことを実HTTPで確認します。[12]

静的と動的を同じbehaviorに混在させる場合はminimum/default TTLを0、maximum TTLを0より大きくして、静的応答のCache-Controlを明示し、動的応答はno-storeにできます。ただしヘッダー規約への依存が大きいため、共通assetsパスを別behaviorに分ける案を優先します。Hostで配送先を分岐する場合はcache keyにもtenant / hostの識別が必要です。配送先originは自動でcache keyへ入りません。

origin数・動的origin変更・OACの注意点

CloudFrontのoriginはdistributionあたり標準100、cache behaviorは75で、いずれも増枠可能です。KVSはstore 5MB、key 512B、value 1KB、CloudFront Function 1つに関連付けるstoreは1つです。KVSの1 valueに全サイトの一覧を詰め込まず、ルートを小さなkey/valueへ分けます。CloudFront Functions自体もコード10KB・メモリ2MBなので、巨大なルート一覧の全件走査を前提にしません。[5]

登録済みoriginはviewer-requestのJavaScript runtime 2.0でselectRequestOriginByIdを使って切り替える基準案です。updateRequestOriginは未登録のcustom HTTP endpointも指定できますが、Web Function OACとの組合せは未実機検証です。Functionsのtest APIではorigin変更の実動作を検証できないため、公開経路の実HTTP試験が必要です。

endpointをIamAuth、OACをOriginAccessControlOriginType=lambda・SigningBehavior=always-amz-authに設定します。regional endpointはSigV4、global endpointはSigV4aです。viewer HostはAllViewerExceptHostHeader等で転送せず、Authorizationの扱いは前述のpolicy条件を検証します。resource policyではcloudfront.amazonaws.comにlambda:InvokeWebFunctionEndpointを許可し、AWS:SourceArnで該当distributionへ限定します。これは未認証の直アクセスを拒否する構成であり、ネットワークの非公開化ではありません。endpoint直URLのGETだけでなくPOST・認証あり／なしを確認し、通常のFunction URL用設定と混同しません。[6]

submoduleによるコード統合

親リポジトリは子リポジトリのcommit SHAを固定します。子へpushしただけでは、親のsubmodule pointerは更新されません。子CIが成功したSHAから、親のgitlink更新PR、統合ビルド、配備へつなぎます。親の更新と配備を直列化し、古い候補が新しい配備を上書きしないようにします。初回のCI・アクセス権設定と、共通インターフェースへの適合は必要であり、任意のリポジトリを完全無改修で受け入れる構成ではありません。実行中のgit cloneや、任意URLからのコード読み込みにはしません。[7]

中央registryが各モジュールのcreateRouter(ctx)を登録し、共通サーバーだけがlistenします。個別モジュールのprocess.exit()やグローバルな環境変数の書き換えは禁止。依存バージョン、ログ、認証、タイムアウト、パスの所有者をモジュールの共通仕様にします。

Node.js以外・Next.jsをどう扱うか

現在のWeb Functionランタイムはnodejs24.xで、AWS_LAMBDA_HTTP_ENDPOINTへ10秒以内にlistenします。通常のイベント方式LambdaのFunction URLやWeb Adapterとは異なる実行方式です。ここで共有するWeb FunctionはNode.js対象です。PHPやGoを同じ仕組みに載せられるとは扱いません。Next.jsのstatic exportはS3へ、SSRは親のNext.jsアプリへ機能を統合するか別Functionに分ける案です。親Nextへの機能統合は独立したNext.jsアプリ全体をimportすることではありません。[2][8]

任意の独立Next.jsアプリのstandalone成果物を全て一つのサーバーへ混在できるとは保証しません。Next.jsのmulti-zonesは分離したアプリをまとめる参考になりますが、base path・asset prefix・ナビゲーション等の制約があります。custom serverとstandaloneは公式に併用できません。採用するバージョンでの動作確認が必要です。

パッケージサイズと分割基準

Web Functionの展開後パッケージは最大512MBで、増枠できません。submoduleはコードの管理方法、lazy importは読み込みタイミングの工夫であり、どちらもZIPの展開サイズは減らしません。実際の依存とビルド成果物を測るまで「何repo入るか」は未確認です。[1]

S3へ出すのは公開可能なブラウザー向けアセットだけです。サーバーバンドルや秘密情報を誤公開しません。.git・テスト・ビルドキャッシュ・開発用依存を除外し、実行時の依存だけを含め、minification・bundle・互換バージョンの依存だけを重複排除する方法を検証します。CIでは配備ZIPを展開した実バイト数を合算。例として350MBで警告、450MBで停止する運用予算を置きます。これは独自の安全余裕であり、公式上限でもAWSの推奨値でもありません。上限に達する前にグループを分割します。

重いSSR、ヘッドレスブラウザー、大きなネイティブ依存は、サイズだけでなく起動時間・OS互換性・メモリ・共有障害範囲にも影響します。最初から共有枠へ含めず、実測後に判断します。

大きい場合の代替：コンテナ、ECS、ALB

通常のイベント方式Lambda＋Web Adapter＋コンテナイメージは候補です。コンテナイメージは全レイヤーを展開した合計サイズで10GBが上限です。ECRとベースイメージの保守も必要で、単なる設定の切り替えではありません。[14] Web Functionとは異なる実行方式です。制約や起動・ストリーミングの挙動も別なので、万能な移行先ではありません。非Nodeの常駐サービスや重い依存にはECS＋ALB等も比較します。ECSはこの構成の必須条件ではありません。[1]

ALBへ移しても、target group登録の自動化は必要です。ALBのLambda targetはイベント方式のFunctionであり、Web Function endpointをそのまま登録するものではありません。Lambdaはtarget groupあたり1 Function、ALBあたりtarget groupは100で固定です。Lambda targetのrequest bodyとresponse JSONはそれぞれ1MB上限も考慮します。費用・性能がどちらに有利かは未実測です。[9]

配備とロールバックの手順

S3・Web Function・CloudFront/KVSは3つの別システムです。全システムを同時に反映する切り替えは保証しません。前後の互換性を保ち、旧ルート設定・旧アセット・旧revisionを残したうえで、構成全体を戻せるようにします。

1. 静的成果物versioned S3へ配置。古い参照を壊さない。
2. 新revisionActiveを確認。previewへHTTP smoke test。
3. 本番切替auto deploy無効。updateStatusがSuccessfulか確認。
4. ルート反映必要なorigin / KVSを更新し、公開URLを確認。

基本順序の例。routeとrevisionの互換性条件によって順序を変えるため、固定手順だけで安全とは判断しません。[3]

revisionごとにserviceConfigを明示生成する

新しいWeb revisionは現行の設定を自動継承しません。IAMロール・環境変数・timeout・concurrency等のserviceConfigをmanifest / IaCから毎回明示生成します。省略すると既定値へ戻るため、コード差分だけでなく設定差分も配備前に比較します。[3]

採用前に確認する合格条件

  • パス境界・最長一致・404・静的アセット参照を、manifestから生成したテストで確認する。
  • 展開サイズ、起動10秒、同時実行、依存の衝突とモジュールの共通仕様、重いモジュールが別モジュールの応答へ与える影響を検証する。
  • 認証あり／なし、tenant間、CookieとHost、正常応答・403・5xxのユーザー間キャッシュ非共有を実HTTPで確認する。署名のないendpoint直アクセスの拒否と、公開経路のPOSTも確認する。
  • preview・本番の別々のsmoke testと、旧構成へのrollback試験を行う。
  • PR作成、CI成功、マージ、配備、本番動作確認を別の状態として記録する。

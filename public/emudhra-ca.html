今回の更新は、

と、その確認係に教えるため。

自分のパスワードを変える話でも、世界中の通信の暗号が解けた話でもない。接続先を本物と認めるための判断を、使うソフトごとに直す話。

まずは、身分証とハンコのたとえで

正常 → 偽物が作れる → 更新で拒否する

たとえば「銀行の本物のサイト」に接続したいとする。ソフトは、相手が出してきた電子的な身分証＝証明書を調べる。その身分証を発行する係が認証局（CA）。[1]

画像はAI生成の理解用イラスト。色で真偽を判定するわけではない。実際は電子署名・ドメイン名・信頼のつながりなどを計算で確かめる。対策方法も、問題の中間CAの直接拒否や、そこへつながるルートCAの除外など、製品によって違う。

覚えるのは1つだけ。
壊れたのは「身分証を信用してよいか」の根拠。
更新するのは「その身分証を確認する側」。

ハンコとは、何のこと？

問題は「署名用の秘密鍵」が弱かったこと

認証局が身分証へ押す「ハンコ」にあたるのが、証明書に電子署名をするための秘密鍵。本来は、公開情報から現実的な時間では求められないように選ぶ。

ところがeMudhraの一部の発行係では、その秘密の数値が極端に小さかった。Mozillaは、対象8鍵がすべて256未満だったと確認した。十分に強い方式を使っていても、鍵の作り方がこれでは弱い。[2]

電子的な身分証

「発行係」は、正確にはこの中間CA。ルートCAの秘密鍵そのものが盗まれた、という説明ではない。

今回の鍵

身分証を発行するための署名用の鍵。第三者がそれを使えると、偽証明書を作れる。

混同しない鍵

すべての通信内容を解読する「万能の鍵」ではない。過去の通信が一括で読めるようになった、とは言えない。

詳しい事実はここだけにまとめる
  • 対象は中間CAの8鍵。TLS通信用6つ、コード署名用2つで、用途は分ける。
  • 生成は2025年4月30日。問題は2026年10月17日に報告・検証された。
  • P-384という暗号方式そのものが破られたのではなく、秘密の数値の選び方が極端に弱かった。
  • 「eMudhraの全証明書」「全認証局」「全アプリが改ざん済み」に広げて考えない。

Mozilla公式インシデント記録

だからといって、勝手に全部盗まれるわけではない

偽の相手と通信させられたときに危険

「銀行のサイトだ」と信じて、実は攻撃者の相手へ接続してしまうと、その偽物と暗号化して話しても、相手である攻撃者には中身が分かる。ここが問題。

自分のソフト本物につないだ
つもり
→
攻撃者の相手偽証明書を提示
ここへ誘導・介入
↔
本物のサービス攻撃者が中継する
場合もある

これは攻撃が成立する場合の概念図。全通信が常にこの経路を通る、という図ではない。

危険になるには、条件が重なる

  1. 攻撃者が偽証明書を用意する。
  2. 攻撃者側へ接続を誘導したり、通信経路へ介入したりできる。
  3. ソフトがまだ問題の発行係を信用し、名前など他の検証も通ってしまう。

この条件が重なると → その接続の内容が読まれたり、改ざんされたりする危険。

偽証明書を作れるだけで、自動的に世界中の通信が攻撃者へ流れるわけではない。過去に被害があったかは、CTを強制しないクライアントについては不明。[3]

「ブラウザは守られた」と聞いたけど？

主要ブラウザには緊急の拒否情報や、証明書を公開ログへ記録させるCTなどの仕組みがある。たとえばGoogleは、既定のChromeのCT検証と遮断までのログの状況を根拠に、不正な証明書が信頼されなかったと説明している。[4]

ただし、ブラウザ以外のプログラムが、同じ仕組みを全部使うとは限らない。OSやアプリ、バージョン、設定で違う。だから「Chromeで大丈夫だった」だけでは他のソフトの確認を終えられない。

PHP / Composer

実際に使う「CAの名簿」を確認

eMudhra対策は、PHPの版数だけで判定しない

なぜ？ PHPの通信は、OSのCA一覧や、設定で指定した別のCAファイルを使うことがあるため。

PHP本体を新しくしても、参照先の古い名簿が残っていたら、その部分は更新されない。逆にOS側の一覧を使っていれば、その配布元の対策が重要になる。

  • curl.cainfo：PHPのcURLが使うCAファイルの指定。
  • openssl.cafile / openssl.capath：OpenSSL系の通信で使うCAファイル・ディレクトリの指定。
  • Composerも、自分が見ているCA一覧を確認。公式はcomposer diagnose -vvvの冒頭のCAファイル・ディレクトリ表示を確認する方法を案内している。

まず「どのCA一覧を使っているか」を特定し、その配布元の対策済み一覧へ更新する。cURL公式のCAバンドルは2026-10-20版を確認済み。独自指定・同梱ファイルがあればそこも確認する。

CLIとWebサーバーのPHPでは設定が違う場合がある。診断の生ログを公開する必要はない。証明書検証をオフにして解決しない。

なぜ？ CPython本体のsslによる問題の中間CAの直接拒否と、certifi等のCA一覧更新は別の対策層だから。

10月26日公開の上記CPython修正版は、問題の鍵を直接拒否する（CVE-2026-115557）。3.15.2 / 3.14.10は公式バイナリーあり、3.13.18 / 3.12.16 / 3.11.18はソースのみ。後者は利用するOS・配布元の修正状況を確認する。3.10以前はEOLで修正対象外。公式リリース

修正版CPythonの通常のTLS経路には直接拒否があるが、それを理由に旧pip・CAバンドルを放置せず、以下も公式推奨どおり更新する。

OSの名簿だけ直しても、古いpipが同梱する名簿は残る。Python公式の案内は、pip自体と、使用しているcertifi・uvの更新を求めている。OSや独自指定のCA一覧も、併せて確認する。

  • 仮想環境は「プロジェクトごとの別の道具箱」。道具箱ごとに確認する。
  • コンテナを使っているなら、古い中身のまま再起動するだけではなく、対策を取り込んで作り直す。
  • 使用時のみ：sigstore 4.5.1、conda 26.9.4、pixi 0.82.1、virtualenv 21.14.12以降も確認。
  • 既存venvのpip更新と、新規venvを作るensurepip・テンプレートの確認を分ける。新しく作った環境にも古いpipを戻さない。
  • certifi 2026.10.18にも対策はあるが、無関係な発行元への影響を絞った2026.10.19以降が推奨先。

古い道具で更新する通信そのものも確認が必要。安全な入手・検証方法は、リンク先の公式手順に従う。検証を切らない。

自分の確認は、この順番で

サイト証明書を運用している人は、G3の移行も確認

GoogleはemSign ECC Root CA - G3をChrome Root Storeから除外し、同ストアに依存する端末へ2026年10月27日午前（PDT）に配信予定と案内している。正確な配信時刻と全端末への反映完了は、本確認では確定していない。[4]

10月17日の問題の中間CAに対する直接遮断とは別の措置。正常に発行された証明書でもG3に連鎖していれば、接続できなくなることがある。対象の運営者は、Chrome Root Storeで信頼される別のPKI階層からのTLS証明書を取得・設置し、配信する証明書チェーンと実接続を確認する。全証明書の一律交換や、証明書検証の無効化を勧める話ではない。

発行元の最新案内（10月26日）

eMudhraは10月22日にSectigo発行の代替証明書を全顧客向けに案内。10月26日の声明では、G3の影響顧客とその他のTLS顧客を、費用なしで代替証明書へ移行中と説明している。移行完了の発表ではない。根本原因の正式報告と独立専門家レビューも今後の予定としている。発行元の説明と、各ブラウザーの信頼判断は区別する。[12]

  1. まず、使っている場所を分ける。

    自分のPC・スマホだけか。自作CLI、サーバー、CI、コンテナ、配布済みアプリもあるか。使っていない言語は追加不要。

  2. そのソフトが「相手をどう確認するか」を調べる。

    Goの検証機能か、Nodeの同梱対策か、Pythonパッケージか、OSや独自CAファイルか。PHPなら参照先の設定も見る。

  3. 対策を、本当に動く場所へ届ける。

    Goなら対象バイナリを再ビルド・配布。Nodeなら実際の実行環境も更新。仮想環境やコンテナも、それぞれの中身へ反映。

  4. 更新した事実と、動作を別々に確認する。

    実行中の版数・参照するCA一覧・通常のHTTPS通信を確認。必要なら公式の検証方法で対象の証明書を拒否するか確認する。ブラウザ1本の結果で全ソフトを合格にしない。

結局、何のための更新？
自分がつなぐ相手を、古い判断のまま「本物です」と認めないため。
「確認する係」へ、新しい拒否ルールを届けるため。

やってはいけない対処：警告を無視する、TLS・証明書検証をオフにする、根拠なくCAを大量削除する。つながらなくなったときは、正しい証明書や信頼設定を確認する。

自分のサイトの証明書も、全部交換する？

全部ではない。今回の対策で拒否される証明書のつながりを使っている場合など、対象に該当するときに発行元の案内に従って交換する。GoogleはemSign ECC Root CA - G3へ連なるサイト証明書の運用者に、新しいチェーンの取得を求めている。[4]

パスワードやAPIキーを全部変える必要がある？

この事故の公表だけで、本人の秘密が漏れたと確認されたわけではない。漏えいの兆候・対象接続・サービス側の案内などがあれば、その条件に応じて対処する。まず検証機能を直すことと、実被害の判断を混同しない。

このたとえで、省略したことは？

現実には身分証を目で見るのではなく、公開鍵暗号で署名を計算して確かめる。ドメイン名・期限・用途・制約・証明書のつながりなども調べる。拒否情報の配信とCA一覧の変更も同じものではない。画像のハンコは、これらすべてを完全再現した模型ではなく、「信用の判断を更新する」という関係を理解するためのたとえ。

自サイトのTLS証明書：所有するホストだけに接続して確認

確認：ネットワーク接続あり。Linux + OpenSSL、所有ホストのみ

HOST='REPLACE_OWN_HOSTNAME'
# -showcertsはサーバーが送った証明書列。選ばれた検証チェーンそのものではない
timeout 15s openssl s_client -connect "$HOST:443" -servername "$HOST" -verify_hostname "$HOST" -verify_return_error -showcerts </dev/null
# 通常のHTTPS疎通。認証ヘッダーやCookieは付けない
curl --head --silent --show-error --max-time 15 "https://$HOST/"

サーバーはルート証明書を送らないことが多いため、表示にG3がないだけで非該当とは判定しません。証明書管理画面/発行元のチェーン情報と、各クライアントが構築する信頼経路を照合。OpenSSLの成功はChrome/アプリの別ストアでの成功や拒否情報配信を保証しません。HTTPSのHEADが405等になるサイトもあり、HTTPステータスとTLS検証を区別します。

変更：対象チェーンなら正規の証明書管理・ACME/CDN/LB配備手順で交換。秘密鍵生成や一律証明書削除コマンドはここでは実行例にしません。切替後に同じ検査と各対象クライアントの通常接続を再確認します。OpenSSL公式

確認：PHP CLI。Web/FPMの設定を証明するコマンドではない

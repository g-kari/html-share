1. Rivetは何をするOSSか

RivetはAIモデルではなく状態を持つアプリの実行単位「Actor」を管理する基盤です。利用者、会話セッション、共同編集の部屋などにキーを付け、そのキーに対応するActorへ要求を届けます。Actorはデータ、処理、接続をまとめて扱います。公式README

たとえば「会話ごとの担当係」です。ユーザーが話しかけると履歴を読み、処理して結果を返し、待機中は保存したデータを残して休止できます。ただし人が眠る比喩と違い、実行中のメモリや処理の続きがすべて自動保存される、という意味ではありません。

2. 処理と保存の流れ

クライアント
HTTP / WebSocket
→
Control plane
キーで検索・配置・経路制御
→
Worker内のActor
state / SQLite / action / event

Control planeはActorの配置や通信を管理し、Workerがアプリのコードを実行します。通常のActorは専用VMやコンテナを一つずつ起動する方式ではなくNode.js、Bun、Rustなどの実行プロセス内で動きます。接続先が変わってもキーを使って呼び出せる点が、単なるオブジェクトとの違いです。構成・実行環境

RivetKitはActorを定義するSDKです。actionsで呼び出す処理、broadcastで接続中クライアントへのイベント、stateやSQLiteで保存するデータを扱います。queueと時刻指定・cronも用意されます。複数段階の処理を記録して再実行するWorkflows、生成コードを隔離して動かすagentOS、生成したアプリを扱うDynamic Appsは関連する別の機能です。Actorそのものと全部を同一視しないほうが仕様を追いやすくなります。製品とリポジトリ構成

c.stateの変更は既定で1秒の間隔でまとめて保存されます。c.varsは永続化されず、直前のstate変更が即座に保存済みとは限りません。必要時はawait c.saveState({ immediate: true })で、書き込みの完了を待てます。状態の保存条件

3. 使いどころと合わない用途

会話セッション

会話ごとに履歴と実行状態をまとめ、トークンを接続中の画面へ配信する設計に向きます。

共同編集・部屋

文書や部屋ごとに参加者と状態を持ち、変更を同じ部屋へ配信する構成を作れます。

利用者別バックエンド

ユーザーやテナントごとに状態を分ける設計、長く待つ個人エージェントの構成候補です。

これらは公式が挙げる用途です。公式の利用例 一方、単純な静的サイトや状態を持たないHTTP APIでは、Actorの導入・運用が増えるだけになる可能性があります。これは設計上の評価であり、実測による費用比較ではありません。大きなSQLデータを単一Actorへ集める設計も、後述の制限を先に確認する必要があります。

4. Durable Objectsなどとの違い

RivetのREADMEはDurable Objectsの制約を避けられると説明しますが、その主張を全構成へ広げるのは不正確です。現Rivetのremote SQLはDB単体256MiBで、WASM runtime全般とnativeのremote backendに適用されます。Cloudflare Workers上のRivetにもWorkers側の制約が残ります。Rivet limits / DO limits / Workers limits

5. 性能数字の読み方

READMEの「12.3ms」「72.4KB」は公式の測定値です。12.3msは休止Actorを起こすHTTP往復のp50で、p99は27.7ms。2026年9月にFoundationDBとRust SDKで測定され、当該cold-start測定には実験的機能を使ったと説明されています。72.4KBは稼働Actor追加時のRSS増分です。すべてのアプリの応答時間や総メモリではありません。測定条件

Kubernetesの約6秒・約200MBは同じ条件の対照実験ではなくREADME自身が「典型的な公開値」と断っています。LLM推論、外部API、データ量、Worker環境の差もあるため、この数字だけで何倍安い・速いとは判断できません。本記事では性能を実測していません。

6. 小さく試す導入例

公式Node.js/Bun quickstartのcounter例を短くしたものです。APIの形を理解するための例で、認証や本番構成は含みません。ここでのコード実行・配備は未検証です。READMEは通常のrivetkit、現overviewはrivetkit@nextを案内しているため、実際の導入ではバージョンを固定し、同じバージョンの手順に合わせます。公式quickstart / 現overview

import { actor, setup } from "rivetkit";

const counter = actor({
  state: { count: 0 },
  actions: {
    increment: (c, x: number) => {
      c.state.count += x;
      return c.state.count;
    },
  },
});
const registry = setup({ use: { counter } });
registry.start();

クライアントはcounterという種類とキーを指定し、getOrCreateで対象Actorを呼び出します。キーが異なれば、別のcounterとして扱う設計です。まずは外部送信を行わないカウンターで、同時実行、再起動後の値、休止後の復帰を確かめると、状態の扱いを観察できます。これは検証方法の提案です。

Cloudflare向けにはrivetkitと@rivetkit/cloudflare-workersを入れ、nodejs_compatを有効にする手順があります。アダプターがWASM runtimeを用意しますが、別のcontrol planeとの接続が必要です。「既存のDurable Objectsの中身だけを無変更で置換する」手順ではありません。Cloudflare quickstart

9. 認証と生成コードは別に設計する

ActorのキーをユーザーIDにしただけでは、他人が呼べないことを保証しません。公式PermissionsはJWTなどによるActorへの到達制限と、Actor内のaction・queue・eventに対する業務上の認可を分けています。会話や個人データを扱うなら両方が必要です。公式Permissions

通常のActorを任意コードの安全なsandboxと同一視しないでください。これはNode.js/Bunプロセス内で動くActorと、隔離機能を提供するagentOSが別構成であることからの判断です。agentOSのsecurity modelはbeta・security review中と明記しています。ホストが公開する関数、mount、通信、認証情報の権限設計は別途必要です。任意Linux binary、Docker、GPUなどの対応も一般的なLinux VMと同じではありません。agentOS security model / 制約

10. AI・Cloudflare個人開発なら

今あるCloudflare構成を急いで置き換えるより、Node.js互換性・自己ホスト・VPC内配置が必要になった時の比較候補です。これは本記事の評価です。

WorkersとDurable Objectsで小さな会話アプリが動いているなら、追加control planeや保存・障害対応を増やす利点があるかを先に比べたいところです。一方、同じセッション処理をNode.jsでも運用したい、データの置き場所を選びたい、共同編集やエージェントごとの状態を統一したい場合は検証する理由があります。

試すなら本番データを使わず、カウンターから会話ID別のダミー履歴へ進め、再起動・同時更新・通信断・認可拒否をテストします。その後にLLM APIを接続し、推論料金とRivetの保存・実行料金を分けて測ります。生成コード実行は別の安全性検証として扱います。Cloudflareからの移行判断は、この小さな比較実験の後で十分です。

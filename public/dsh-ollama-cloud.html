先に結論

DSH＋Ollama Cloudは、モデル接続と実行環境を自分で管理したい開発者にとって検討価値がある。ただし、DSHはまだ開発者プレビュー。公式の安全注意は未監査・本番準備未完了を明記している。機密リポジトリをいきなり渡すより、隔離した小さな課題で確認したい。

  • 投稿のDSH：DeepSeek公式のオープンソースエージェント基盤、DeepSeek Harnessと読むのが自然。
  • DSV41F：文脈上、DeepSeek-V4.1-Flashの略と推定。Ollamaでの提供は確認できるが、略称対応を投稿者が明示した資料は確認していない。
  • 「学習の心配がない」：Ollamaはクラウドの入力・出力を学習に使わず、一時処理すると明記。内容のクラウド送信はある。
  • 見落としやすい点：DSHのフィードバック送信、検索用API、ローカルログ、第三者プラグインは、Ollamaのモデル推論とは別の経路。
公式確認：文書・コードに根拠あり推定：文脈や仕様を組み合わせた判断未実測：通信・性能試験はしていない

根拠：DSH README（固定commit）安全注意OllamaモデルページOllamaプライバシーポリシー

DeepSeek-V4.1-Flashは何を軽くしたモデルか

公式の2026年9月10日発表はnative visionと長いcontextを特徴に挙げる。技術報告では、encoder / decoder、疎なattention、KV cacheの共有・圧縮を組み合わせ、入力を読むprefillと一tokenずつ生成するdecodeの負荷を下げる設計を説明する。公表active parameterはそれぞれ8B / 16B。これは自分のrepoでの速度実測ではない。

報告の552Bはbackboneで、196BのEngramを別掲している。Ollamaの上部763B表示とは集計境界が揃わず、厳密な全内訳は今回確定していない。パラメータ数をそのまま端末の必要VRAMへ換算しない。今回の:cloudではモデル全体を手元へdownloadして動かす構成でもない。

根拠：DeepSeek公式発表技術報告 §2.1Ollama表示。提供者のbenchmarkはharnessやtool条件にも依存するため、ここでは順位表へ転用しない。

非学習と、非送信・非保存は別に確認する

Ollamaが明記していること

2026年3月更新のポリシーでは、クラウド入力・出力はリクエストに必要な間だけ一時処理し、モデル学習に使わない。アカウント、請求、サポート、内容を含まない利用メタデータには別の保存方針がある。「サービス側に何の情報も残らない」という意味ではない。

料金FAQは主に米国でホストし、追加容量のため欧州・シンガポールへルーティングする場合を説明している。協業インフラにも非ログ・非学習・ゼロ保持を求める。一方、個々のリクエストの地域固定、全委託先一覧、個別契約の条件は今回の公開資料だけでは確定できない。

根拠：Privacy Policy §2・3・5・6料金ページのPrivacy FAQ。実インフラ監査や契約審査を行ったという意味ではない。

DSHの標準フィードバック経路

モデルをOllamaにしても、DSH自身のフィードバック送信設定は別。確認した標準baseはFEEDBACK_ONLY。新しいテキストフィードバック、評価の作成・編集、ノート編集、撤回を契機に、そのイベントまでの未送信セッションログのprefixを、文脈を含めてDeepSeekのcollectorへ送る仕様。全モデルproviderが対象となる。

普通の会話やモデル呼び出しだけで、このテレメトリのcaptureが始まるわけではない。送信はbest effortで、受付表示はリモート受領の証明ではなく、撤回イベントも遠隔のデータ消去を保証しない。

この経路を使わない評価では、起動前に次のどちらかを設定する。設定変更は今後のこの経路を止めるためのもので、過去に送信済みの情報を削除する操作ではない。

# DSH起動前。どちらか一つでよい
export DSH_TELEMETRY_MODE=DISABLED

# 別の方法：任意の非空値で無効化
export DSH_TELEMETRY_DISABLED=1

DSH_TELEMETRY_DISABLEDは文字列の0やfalseでも非空なら無効化になる。起動した実プロセスの環境・適用profileを確認する。独自profileや今後の版では既定が変わり得る。

固定commitの根拠：対象とモード標準設定・無効化・collector配信と撤回の限界

DSHの中身と、期待しすぎない境界

DSHはCordis上の「すべてをプラグインとして組み立てる」設計。モデルadapter、ツール、承認、保存、Web UIまで交換・構成できる。標準の多provider adapterにはPiのAI層を使う部分があるが、DSHそのものがPi coding agentと同じ製品という意味ではない。

調査の固定点：公式prerelease dsh-v0.2.1-alpha.1、2026年10月3日06:42:19 UTC公開。確認したmasterと同じcommit 5badb15009ae1756c3afe0ae0cef1faafc290cccを参照した。stable releaseとしては扱わない。

根拠：公式prerelease固定commit設計とpreviewの説明

承認と隔離は、異なる層

標準base-backedの新しいsessionはworkspace-write + ask。書込み先をworkspace・temp領域へ限定し、必要な操作では承認を求める。しかしread-only / workspace-writeは秘密の読取りやネットワーク送信を包括的に禁止するモードではない。普段のhomeや本番の鍵を見せない実行環境を先に用意する。

approval=neverは承認要求を自動許可する意味ではなく、要求を拒否する設定。一方、danger-full-accessは通常のconfinementをbypassする。エラー回避のためにこの組合せへ自動で切り替える手順は採用しない。

保存と再開

標準のセッションは$DSH_HOME/sessionsにJSONL形式のイベントを保存し、zstd圧縮する。圧縮は暗号化ではない。message、tool、承認、attempt等が蓄積し、標準の保存provider自身に削除APIはない。バックアップと整理方法を決める必要がある。

再開時は同じログから履歴を復元し、開始されなかったtoolや結果不明のtoolにrepair resultを置く。結果不明の副作用を盲目的に再実行しないための情報はあるが、任意の外部APIのexactly-once保証ではない。強制終了直前の未確定streamまで必ず保存されるとも限らない。

根拠：ログ保存resumeと限界。送信・deploy・購入の結果照合や冪等キーは別設計。

プラグイン、MCP、Web UI、proxyの注意

Plugin Managerでactive profileのbundleを追加・有効化でき、MCPはstdio / Streamable HTTPを扱う。互換version検査はあるが、追加packageやbuild scriptは信頼するコードとして確認する。rollbackが外部副作用まで元に戻すとは限らない。

Web UIの既定は127.0.0.1:3080。起動URLにはprocess credentialを含むため、実URLや画面をそのまま公開しない。遠隔公開は公式reverse-proxy手順に従い、TLS・Host・cookie scope等を設計する。

HTTP proxyは起動時の環境設定を使い、loopback等の例外がある。proxyは全送信の強制遮断装置とは言えない。秘匿評価では環境側のnetwork policyを使う。

根拠：plugin導入の境界MCP公開deploymentproxy

計算例は、性能測定ではない

未キャッシュ入力100,000token、課金対象の出力総量2,000tokenを仮定すると、ピーク時は0.30×0.1 + 1.20×0.002 = $0.0324。オフピークは$0.0162。複数リクエストの累計で入力1,000,000＋出力10,000なら、それぞれ$0.312と$0.156となる。

  • 含有usageは契約開始日と同じ日で毎月更新し、未使用分は繰り越さない。Freeは登録日基準。

DSHからOllamaへつなぐ手順

これは手順の紹介。ユーザーの端末へのインストール、APIキー発行、購入、実際の推論は行っていない。DSHには汎用OpenAI-compatible接続があり、Ollamaには対応APIがある。その組合せを示しているが、DSH専用のOllama動作保証を公式資料で確認したわけではない。

先に実行環境を固定する

この版のsource workspaceはNode ^22.19.0 || >=24.0.0、pnpm 11.7.0を指定。Node 23はこの範囲に含まれない。latest任せのpreview導入より、版・lockfile・実行場所を固定する。公式導入のsource経路は後の試験欄に示す。

空の専用workspaceと専用のDSH_HOMEを使い、telemetryを止め、DSH_PERMISSION_MODE=read-onlyから始める。それでも読取り・networkは別境界なので、秘密を含まないVM / containerを使う。

npmの確認時点では0.2.1-alpha.1はalphaタグ、latest / nextは0.2.0-rc.2。固定調査と同じ版で試すなら、版を省略しない。

# 隔離した非機密の作業環境で利用者が実行する紹介例
export DSH_TELEMETRY_MODE=DISABLED
export DSH_PERMISSION_MODE=read-only
# DSH_HOMEも普段の履歴・資格情報とは別の専用領域にする
npx @deepseek-ai/dsh@0.2.1-alpha.1 web --no-open

根拠：公式npm Versions。ここで示す起動は未実行。初回はpackage取得が発生する。

Settings → Modelsで登録する

  1. Add model provider → Custom model APIを開く。
  2. Provider ID例はollama-cloud、表示名はOllama Cloud。保存後のIDは恒久参照として扱われ、気軽なrenameはできない。
  3. Base URLはhttps://ollama.com/v1、protocolはOpenAI Chat Completions。末尾に/chat/completionsを手で足さない。
  4. API key欄には公式Ollamaで用意したキーをホスト側で入力する。UIのこの欄は環境変数名を入れる欄ではない。キーを記事・チャット・Git・スクリーンショットへ貼らない。
  5. Fetch available models、または手動でdeepseek-v4.1-flashを登録。取得成功は一覧・認証の確認で、推論やtool callの合格証明ではない。
  6. model pickerで選び、新しいsessionで確認する。既に呼び出したsessionはログに保存したモデル選択を持つため、default変更だけで全部移行したと考えない。

環境変数参照を使う高度設定例

次はDSHが受理する設定項目を使った、初回用の接続設計例。実推論未検証。profile patchでは対象rowのconfigが丸ごと置き換わるため、既存providerを消さないよう全設定を確認する。APIキーそのものは書かず、起動時に渡したOLLAMA_API_KEYを参照する。

- id: llm-pi-ai
  config:
    providers:
      ollama-cloud:
        displayName: Ollama Cloud
        apiKeyEnv: OLLAMA_API_KEY
        api: openai-completions
        baseURL: https://ollama.com/v1
        compat:
          supportsDeveloperRole: false
          maxTokensField: max_tokens
        retryPolicy:
          mode: normal
          maxRetries: 0
        models:
          - id: deepseek-v4.1-flash
            input: [text]
            maxTokens: 512

compatの二項目は保守的な初回候補で、Ollamaで必須と実測したものではない。maxTokens: 512は初回のrequest出力上限候補。短すぎて完了しない場合もある。maxRetries: 0はこのadapterの自動retryを抑えるだけで、agent全体を一回の推論に制限しない。最初は画像・特殊reasoningを宣言せず、対応を確かめてから追加する。

capacityを省略したcustom modelは、DSH側でcontext 262,144 / output 32,768の仮定になる。この容量metadataはrequestごとの出力上限設定とは別で、Ollamaの公称値とも同一ではない。実提供上限を確かめて設定し、設定値だけでサーバーの容量が増えたと考えない。

根拠：adapter設定compat設定capacity既定

資格情報は同じOSユーザーから隔離されない

資格情報の解決順は、起動環境 → $DSH_HOME/.credentials.yaml → 起動cwdの.env → DSH homeの.env。設定には参照名を保存するが、資格情報ファイルは暗号化金庫ではなく、同じOSユーザーで動くtool processが読める。POSIXのowner-only permissionだけを全秘密の隔離と見なさない。

不足した参照はMISSING_CREDENTIALで失敗する。起動後に別shellでexportしても既存プロセスの起動時snapshotは変わらない。平文のheaders.Authorizationを設定ファイルに埋め込む方法は避ける。

根拠：資格情報の保存・優先順位・限界Ollama APIキー。OllamaのAPIキーは自然失効しないため、不要になったら公式画面で失効させる。

互換APIで確認すべき項目

Ollamaの互換APIはOpenAI APIの一部を提供する。DSHではopenai-completionsを選び、まず通常のテキスト、stream、tool call、tool結果の返送、thinkingの扱いを小さく確認する。OpenAIのstateful Responses、組み込みweb search、custom/freeform tool-call replayがすべてそのまま使えるとは考えない。

モデルの公称contextは1Mtoken。DSHのcontext設定、実際の入力・出力予約、要約の閾値、応答速度まで含めて1Mを常に使えるという保証ではない。DeepSeekの技術報告とOllamaの表示にはパラメータの数え方の差が見えるため、サイズ表示だけでメモリ量や性能を推定しない。

根拠：互換APIの対応範囲提供モデル・contextDeepSeek-V4.1技術報告。公称値と導入先の実測値を分けて記録する。

Piの現行mainにはこの新しい公開API経路の実装があり、旧OpenAI Codex (legacy)とは区別される。導入配布版への収録、アカウント条件、認証成功は実環境で確認する。DSH内部にPiのAI層があることだけで、同じ版・同じログイン経路がそのまま使えると推定しない。

低リスク・低費用で判断する順番

最初の目的は「どのmodelが勝つか」より、指定した範囲だけを触り、中断・拒否・失敗を説明できるかを確認すること。以下は提案する評価計画で、モデル試験の合格報告ではない。

  1. 固定する：harness版、モデル名、endpoint、permission mode、ツール集合、予算、試験時刻を記録。使い捨てworkspaceと専用DSH homeを用意し、実アカウントの鍵・履歴は入れない。
  2. まずオフライン：模型のrepositoryとfakeのmodel endpointで、テキスト・stream・tool call・拒否・復元を確認。DeepSeekのfeedback collectorも必要ならローカルfixtureへ向ける。外部ネットワークは遮断する。
  3. 公開・非機密の小課題：通信を許可する段階で、予算を決め、一回ずつ実行。入力・生成token、cache、費用、失敗・再試行をusage画面と照合する。
  4. 比較する：同じ課題を少なくとも数回、同じ合格条件で試す。モデルとharnessを同時に変えた結果を、片方の効果として説明しない。
  5. 運用へ進む：差分レビュー、CI、権限失効、通知・課金停止を確認してから対象を広げる。本番の鍵、購入、公開・送信は別の承認対象にする。

  • DSH＋Ollama：previewの変化を追い、plugin・model route・権限・ログ設定を自分で確認できる。providerと推論予算を分けて持ちたい。
  • Pi：providerをまたぎ、小さなコーディングエージェントを自分の開発手順へ拡張したい。実行隔離も自分で設計する。

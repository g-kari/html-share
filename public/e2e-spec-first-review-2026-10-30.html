01 / Decision brief

結論：E2Eの数より、正解の出所を見直す

まず問うべきことは「何件のE2Eがあるか」ではなく、「そのテストは実装を見ずに正解を判定できるか」である。

① 仕様を独立させる

要求・権限・イベント・状態変化を実装前に定義。実装の現在の振る舞いを期待値としてコピーしない。

② 論理はモデル検査へ

到達可能性、不変条件、デッドロック、ライブネスを可能な範囲で早期に確認する。

③ E2Eは実システムの照合へ

ユーザー操作からAPI・DB・画面まで、仕様と現実のずれを少数の価値あるシナリオで検出する。

推奨する役割分担

仕様の正しさを「仕様レビューとモデル検査」で、実装の内部整合性を「Unit / Integration / Contract」で、実環境での振る舞いを「E2E」で確認する。E2Eの失敗調査は証拠収集とAIトリアージで短縮する。提案

この文書は特定リポジトリの実測・実装済み設計を示すものではない。導入可否とテスト数は対象コードの調査後に決める。

X投稿には「モデル検査はE2Eの1,000倍以上速い」という主張もある。ただし対象・状態空間・マシン・テスト内容を揃えた一般ベンチマークではない。モデル検査で探索する状態とE2Eのケース数は同じ単位ではなく、単純比較できない。 数字は導入効果の保証に使わない。[S1]

資料の詳細と、混同しやすい点
  • 仕様起点のアプローチ：状態遷移モデルは実装ではなく要求から作る。仕様アニメーションで関係者が意図を確認し、モデル検査はモデル上の性質を検証する。仕様そのものの妥当性まで自動保証されるわけではない。
  • Zenn事例：19領域・842シナリオ中、実装済み784・未実装58。AI探索の26指摘は不具合3、仕様確認7、誤検知16。単なる件数を品質指標にせず、対象の網羅とassertionの意味を別途レビューしている。[S2]
  • Speaker Deck事例：FlutterのPatrolとDevinによるワークフローで、失敗をtest_bug / production_bug / infra_failure / flakyに分類し、修正後には実機Test Labの証拠をPRへ添付する。Webアプリへ同じツールを機械的に移植する話ではない。[S3]
  • ビジュアル品質：投稿はgolden画像を使わない機能E2Eの事例だが、表示崩れの検出は別問題。視覚差分、デバイス別レイアウト、アクセシビリティは独立した検証観点として残す。

安全性（Safety）の例

  • 申請者は自分の申請を承認できない。
  • 未提出の申請は承認済みにできない。
  • 承認済みが差し戻し状態へ勝手に戻らない。
  • 同じ承認イベントを重複受信しても二重処理にならない。

進行性（Liveness）の例

  • 審査中が無限に放置されない、という要件を置くなら期限とエスカレーション経路が必要。
  • 外部処理の失敗が永久の「処理中」にならず、失敗・再試行・保留などへ遷移できる。
  • 進行性の検査には環境・担当者・公平性の仮定を明示する。
状態遷移の契約例（設計用JSON・実行可能な形式仕様ではない）
{
  "specId": "APPROVAL-001",
  "version": "1.0",
  "initial": "draft",
  "transitions": [
    {"id":"T-SUBMIT","from":"draft","event":"submit",
     "actor":"owner","guard":"inputValid","to":"reviewing",
     "observe":{"statusText":"審査中"}},
    {"id":"T-APPROVE","from":"reviewing","event":"approve",
     "actor":"reviewer","to":"approved",
     "observe":{"statusText":"承認済み"}},
    {"id":"T-REJECT","from":"reviewing","event":"reject",
     "actor":"reviewer","to":"rejected",
     "observe":{"statusText":"差し戻し"}}
  ],
  "invariants": ["onlyReviewerCanApprove", "noDoubleApproval"],
  "assumptions": ["reviewerAccountAvailable"]
}

禁止されたイベント（申請者によるapprove、重複approveなど）は、状態が変わらないことと拒否理由が見えることを別途明示する。これをTLA+/PlusCal等で形式化し、検査条件を定義するのは次工程。

画面提示を「観測可能な出力」にする

モデルと画面実装を直接結合させず、transition → expected observation を定義する。例えば T-APPROVE に対し「承認済みと表示」「再読み込み後も承認済み」「申請者には承認ボタンを表示しない」を期待値にする。

入力イベント／API応答／DB永続化／ユーザー可視の表示をチャネルやアダプタで結びつける。UIのラベルやDOMセレクタが変わっても、業務状態の正しさの定義は変えない。提案

05 / Oracle and traceability

「仕様 → 実装 → E2E → 証拠」を追跡する

独立した仕様があっても、実装と対応付けられなければ更新漏れが起きる。Zenn事例のように検証対象・シナリオ・実テストの対応を機械的に照合し、期待値の意味は仕様側から供給する。[S2]

追跡キー持つ情報更新時の検査
specId要求／トップレベル仕様とバージョン要求変更のレビュー記録があるか
transitionId状態、イベント、ガード、期待する観測未カバーの遷移・不変条件がないか
implementationRefs画面・API・権限・イベント処理新規・削除・改名で台帳が古くなっていないか
testIdsUnit／統合／E2Eのテスト実体宣言だけでテストが存在しない状態を検出
evidence実行環境、結果、trace、未実施範囲skip／未実行を成功として扱っていないか
オラクル独立性を守るルール

実装の現在の画面やAPI応答をスナップショットして、そのまま正解とみなさない。差異が出たら、要求・仕様・実装のどこが間違っているかレビューする。テストを通すためだけに仕様を実装へ合わせる自動修正は禁止する。

推奨ディレクトリ構造とテストの概念例
spec/
  approval/requirements.md       # 人がレビューした要求
  approval/model.*               # 形式仕様（ツールは要選定）
  approval/properties.*          # 不変条件・進行性
  approval/observations.json     # チャネル／UIの期待値
tests/
  ledger/scenarios.json          # specId / transitionId / testIds / refs
  e2e/approval.spec.ts           # Playwright等による実ブラウザ照合
  reports/                       # CI artifact（通常はGit管理しない）
scripts/
  check-traceability.*           # 不整合ゲート（案）
// 疑似コード：実プロジェクトのAPIに合わせて実装する
const expected = spec.step("T-APPROVE", { actor: "reviewer" });
await ui.loginAs("reviewer");
await ui.approveRequest();
expect(await ui.visibleStatus()).toEqual(expected.observe.statusText);

expect(await ui.visibleStatus()).toEqual(expected.observe.statusText);

上記は設計の関係を示す疑似コード。ブラウザテストでは許可されない内部状態を使って操作を省略せず、ユーザー経路と整合する検証点を選ぶ。

どのE2Eを走らせるか
  1. 変更した実装から台帳で関連シナリオを引く。
  2. 共有ロジック／権限／API契約の変更は利用先へ影響を伝播させる。
  3. 高リスク変更や大規模リファクタは全体回帰の対象を拡大する。
  4. PRには選択理由、実行したブラウザ・表示幅、skipped／未実行領域を記録する。
  5. ランナーの自動フィルタは「何を実行するか」の補助であり、仕様・実装・シナリオの対応管理そのものを代替しない。

Zenn事例では通常は関連E2Eだけを実行し、大きなリファクタでは全体実行している。[S2]

06 / Quality gates

CIは「テストを走らせる」以上の仕事をする

Gate A · 仕様の変更管理

要求・状態遷移・不変条件の変更を記録し、仕様アニメーション／形式検査の結果を紐付ける。

Gate B · 対応漏れ検査

対象の追加・削除・改名・テスト消失・ID不整合・理由のないpending増加を失敗にする。

Gate C · 動作確認

Unit／統合／契約＋変更関連E2E。重要導線の最小smokeはCIでも独立再現する。

Gate D · 証拠と結果の厳密化

pass / fail / flaky / skipped / not-runを区別。失敗時のtraceや画面・ログ・環境情報を保存する。

Playwright公式はTrace Viewer、CIでのtrace記録、タグ、projects、リトライ等を提供する。全テストの常時traceはコストに注意。[S5] [S6]

失敗した場合の4分類

分類判断に使う証拠次の行動
production_bug仕様との差異、再現手順、画面・API・DBの事実実装を最小修正して再検証
test_bugセレクタの破損、テスト前提、古いセットアップ仕様を変えずテスト側を修正
infra_failure端末・ブラウザ・ネットワーク・テスト環境の異常環境を修復し同条件で再実行
flaky同一コード・条件で結果が揺れる履歴とコンテキスト原因を特定。リトライだけで合格扱いしない
見かけの緑を作らない

「失敗したのでassertionを削除」「skipしたのでCI成功」「リトライで一度通ったので根本原因未確認のまま完了」は避ける。AIは修正候補を作れても、仕様変更・不具合修正の採否は証拠付きでレビューする。[S3]

隔離環境・外部送信・視覚検証の補足
  • 並列エージェントごとにDB・ストレージ・認証ユーザー・ポートを分離する。後片付け時もテスト証拠は残す。
  • 本番への書き込み・メール送信・課金API呼び出しをE2Eが起こさないよう、接続先と実行権限を限定する。
  • 表示崩れは機能オラクルでは見落とすため、必要なページにVisual Regressionを別途導入する。端末ごとのアクセシビリティチェックも分離する。
  • リトライ時も初回失敗の証拠を保存する。Playwrightのtrace設定は retain-on-failure または on-first-retry など要件に応じて決める。
07 / Adoption path

まず1つの重要フローでPoCする

PHASE 0 · INVENTORY

現状の見える化

既存E2Eの件数・実行時間・flaky率・仕様の出所・業務リスクを棚卸し。最重要の1フローを選ぶ。

PHASE 1 · SPEC PILOT

独立したモデルを作る

状態・遷移・ガード・不変条件をレビューし、モデル検査。仕様からオラクルと1〜数本のE2Eを構築。

PHASE 2 · CONTROL

漏れと失敗を制御

台帳ゲート・選択実行・隔離環境・証拠収集・トリアージを導入。効果を測ってから広げる。

設計見直しの合格条件

  • 独立性 PoCフローの期待値が実装の現状ではなく、合意された要求・仕様から導かれている。
  • 形式検査 不変条件と少なくとも1つの進行性の検討があり、探索条件・制約・反例の有無を記録する。
  • 検出力 意図的な不正遷移・権限違反を注入した際に、モデル検査または適切な下層／E2Eが落ちることを確認する。
  • 追跡性 specId → transitionId → testIds → execution evidence が辿れ、削除・新規追加の不整合を検知できる。
  • 実行の厳密性 クリーンな隔離環境で実行でき、未実行・skip・再試行は明示される。PRに証拠と限界が残る。
  • 責任範囲 画面崩れ、外部認証、外部サービス依存など、モデルE2Eで未保証の箇所が一覧化されている。
  • 運用効果 変更当たりのE2E時間、失敗調査時間、flaky率、重大な漏れを導入前後で比較できる。

どの形式仕様言語・ランナーを採用するかは既存言語・CI・アプリ特性に依存。TLA+/PlusCal、Playwright Test、tester-army/e2e、Patrolは候補・参考であり、一括導入を推奨していない。

08 / Handoff prompt

このHTMLと一緒に渡す設計レビュー指示

まず変更前の監査と提案を求める。現状の技術スタックを決めつけず、既存テスト資産を残して移行するための指示。

Codex等へ渡すプロンプト
このHTMLをE2E再設計の検討資料として読み、対象リポジトリの
現行E2E設計を監査して、仕様起点への改善案を作成してください。

目的：実装の現状追認ではないテストオラクルを持ち、
モデル検査・Unit/Integration/Contract・E2Eの責務を分けること。

最初に最新のREADME、AGENTS.md等の指示、コード、テスト、
Issue/PR、CI、既存の実行結果を調査してください。
作業中の既存タスク・未マージDraft PRを無視した重複着手は禁止。

以下を報告してください。
1. 現行のテスト層と機能別シナリオ対応表。既存の良い設計も残す。
2. 実装をそのまま正解としてしまっているアサーションの一覧。
3. トップレベル状態遷移仕様を置く価値が高いフロー候補と理由。
4. モデル検査で確認する不変条件、進行性、並行性、境界と仮定。
5. 独立した仕様からE2Eオラクルを供給する構成案。
6. API・DB・UI・外部サービス・視覚品質の適切なテスト責務。
7. 実装とシナリオの台帳、CIの検査、変更時の選択実行案。
8. flaky/環境障害/実装バグ/テストバグのトリアージ案。
9. 小規模PoCの対象、合格条件、コスト、移行順、ロールバック。

安全・品質条件：
- 仕様の変更は「テストを通すため」という理由だけで行わない。
- モデル検査とE2Eの性能比較は同条件・同単位と誤認しない。
- skipped / not-run / retry-passを無条件の成功と扱わない。
- 本番データや外部送信を用いた実験はしない。
- まず監査結果と設計案を提出する。実装・PR・CI・マージ・配備
  は段階を分けて報告し、未実行の段階を完了と書かない。
- 既存のテストを一括削除・置換しない。

成果物：現状評価、Before/After図、責務マトリクス、
優先度付き改善計画、PoC合格条件、未確認事項の一覧。

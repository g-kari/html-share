Goコード検証の全体像

  • 必須の土台：go build・go vet・go test・-race・govulncheck。
  • 品質を拡張：golangci-lint / Staticcheck、カバレッジ、ファジング、ベンチマーク。
  • 用途に応じて追加：API契約テスト、E2E、DAST、ミューテーションテスト、形式手法。

01. 静的検証（6項目）

検証項目Goでの実装・確認内容
01 型チェック標準go build ./...型の整合性、ジェネリクス制約、関数引数などはコンパイラが確認。Goでは型推論もコンパイル時に扱う。
02 構文チェック標準go build / gofmt構文エラーはコンパイルで検出。gofmtは主にソース整形・構文解析を行うツール。
03 意味解析標準Goコンパイラ / go vet未定義の識別子、スコープ、シグネチャ不整合。vetはコンパイル可能でも疑わしいコードを追加検査。
04 静的解析標準go vet 追加Staticcheck / golangci-lint未使用・疑わしい処理、エラーハンドリング、コード品質。複雑度や規約は有効化したルールに依存。
05 SAST追加gosec / Semgrep / CodeQL危険なAPI使用、ハードコードされた秘密情報などを検出。静的スキャンで全脆弱性が見つかるわけではない。
06 形式的検証追加Gobra、TLA+などGobraはGoコード向けの形式的検証、TLA+は並行動作・状態遷移などの仕様モデル検証。対象が異なる。

02. 動的検証（11項目）

検証項目Goでの実装・確認内容
01 単体テスト標準testing / go test ./...関数・パッケージ単位の振る舞い。テーブル駆動テストと相性がよい。
02 結合テスト標準httptest 追加TestcontainersAPIとDBなどの連携。実DBを使うテストは分離した環境で実行する。
03 E2Eテスト追加Playwright / chromedpブラウザや利用者視点でシステムの最終結果を検証。PlaywrightはGoプロセス内で動かす必要はない。
04 契約テスト追加Pact Go / OpenAPIスキーマ検証APIの提供側と利用側の約束を検査。仕様に対する妥当性と実装の整合性を分ける。
05 プロパティベーステスト標準testing/quick 追加Rapid多様な入力に対して性質が保たれるかを検証。testing/quickは機能追加が凍結されている。
06 ファジング標準go test -fuzz境界値・異常入力・クラッシュを探索。Go 1.18以降の標準機能。OSS-Fuzzとの連携も可能。
07 ミューテーションテスト追加Gremlins / go-mutestingコードを小さく変え、既存テストが欠陥を検出するかを評価。ツールの保守状況と対象演算子は導入前に確認。
08 実行時チェック標準境界検査 / nil参照時のpanic / 明示的な検証Goランタイムが一部を検査。業務上の不変条件や入力妥当性はアプリケーションで定義する。
09 DAST追加OWASP ZAP / Burp Suite起動中のWeb APIを外部から調べる。対象・認証・テスト環境を制限して実施する。
10 性能テスト標準go test -bench / pprof処理時間、割当、CPU・メモリ使用量。システム負荷試験には別途負荷生成ツールを使う。
11 メモリ安全性標準go test -race / pprofデータ競合の検出とメモリ診断。cgo・unsafe使用時は追加の検証が必要。raceとpprofだけでメモリ安全性の全体を証明できない。

03. 横断的な検証（4項目）

検証項目Goでの実装・確認内容
01 カバレッジ標準go test -coverprofile / go tool cover主にステートメント網羅を測定。分岐条件・MC/DCを同等に計測するものではない。
02 保守性・SCA追加Staticcheck / golangci-lint / govulncheck / Dependabotコードレビュー、規約・ドキュメント、依存モジュールの既知脆弱性を点検。
03 コンプライアンス追加go-licenses / 組織のポリシーチェックOSSライセンス、配布物に含まれる依存関係、組織・業界固有の規約を検査。
04 AI/ML検証標準testing / Fuzzing 追加専用評価基盤入力スキーマ、モデル出力・公平性・頑健性。Go固有ツールだけで十分とは限らない。

CIでの実行順序

PR時コンパイル・静的解析・テスト・race・SCA
統合・公開前API契約・重要なE2E・DAST
夜間・定期Fuzzing・性能比較・ミューテーション

最初から全項目を毎PRで回す必要はない。速い検証を早い段階に置き、時間と環境を要する検証を分ける。

PRで使う基本コマンド 
# 静的検証
go build ./...
go vet ./...
golangci-lint run ./...

# 実行時検証
go test ./...
go test -race ./...

# テスト到達範囲
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out

# 既知脆弱性がある依存関係
govulncheck ./...

golangci-lintとgovulncheckは別途導入する。Staticcheckを単体で使う場合は staticcheck ./...。同じ解析器を重複実行する必要はない。

夜間・定期ジョブの例 
# ベンチマーク。結果の比較には実行環境を揃える
go test -run '^$' -bench . -benchmem ./...

# FuzzParseを定義したパッケージで30秒実行
go test -fuzz '^FuzzParse$' \
  -fuzztime=30s ./internal/parser

# 必要に応じたCPU/メモリプロファイル
go test -run '^$' -bench . \
  -cpuprofile=cpu.out -memprofile=mem.out ./internal/parser
go tool pprof cpu.out

FuzzParseやパッケージ名は例。ファジングは対象を絞って実行する。ベンチマークの推移を評価する際は、マシン差・負荷差・Goバージョン差を管理する。

実施基準と検証の限界
  • カバレッジ100%でも正しさは証明できない。仕様に照らしたテストオラクル、境界条件、ミューテーションテストが補完する。
  • race detectorは実行した経路のみ検出。非実行経路の競合は未検証となる。-raceは追加負荷も発生する。
  • pprofは診断ツール。メモリ使用量・goroutineの滞留を分析できても、リークや全メモリ不正アクセスの不存在は証明しない。
  • govulncheckは既知の脆弱性を対象。到達可能性の解析は有用だが、動的呼び出し等の限界や、OS・コンテナイメージなどGoモジュール外の検査は別途考える。
  • 契約テストと形式手法の役割は異なる。契約は提供者と利用者の境界、TLA+は仕様上の状態遷移などを確認する。Goソースを直接実行して検証するものとは限らない。
  • cgo / unsafeは別扱い。Goランタイムの保護だけに依存しない。対象プラットフォームで追加の検査・テストを実施する。

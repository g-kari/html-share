  3. 今すぐやることは、使っている PHP のブランチとバージョンの確認、修正版への更新、更新後の PHP-FPM / Web サーバーの再起動である。更新できない場合は、脆弱性ごとの緩和策（セッションアップロード進捗の無効化、FPM 接続再利用の無効化など）を節ごとに記載した。

コード実行に至りうる脆弱性

CVE-2026-115560（GHSA-658j-r8rw-q6mx）— セッションのシリアライザ不一致による RCE

内容：セッションアップロード進捗の機能が、あるシリアル化形式で攻撃者のデータを書き込み、別の形式で読み戻すことがある。不一致のデコーダがセッションキーの一部をシリアル化されたオブジェクトデータとして解釈し、アプリケーションに利用可能なオブジェクトガジェットチェーンがあると、PHP ワーカーの権限でコード実行に至る。

発動条件：デフォルトでは届かない。次の組み合わせが必要である。(1) セッションアップロード進捗が有効で、攻撃者が php_binary または php_serialize を使う文脈へ multipart アップロードを送れる。(2) 同じセッション ID の保存済みセッションを、後から php シリアライザで読む処理がある。不一致は、アプリケーションが実行時に session.serialize_handler を php へ切り替える場合のほか、別アプリケーション・別プール・別バーチャルホスト・コマンドライン処理が同じセッション保存先を共有し、形式が食い違う場合にも起きる。実行時切替をしないアプリケーションでも、他方が不一致データを書き込めば影響を受ける。

実証：PHP 8.2.35、8.3.36、8.4.27、8.5.12 上で Guzzle のガジェットによるコマンド実行が報告されている。Monolog 2.11.1 のガジェットでも再現されている。この問題は 2026年10月23日に情報アドバイザリとして先行公表され、今回正式に修正された。

修正の内容：セッションアップロード進捗がデフォルトで無効になり、有効な間は session.serialize_handler を含むセッション設定の実行時変更が拒否される。ただし明示的に有効化している設定は新しいデフォルトより優先される。また、修正後も、アップロード進捗を明示的に有効にする場合は、そのセッションデータに触れる全ての読み書き側でシリアライザを揃える必要がある（修正は別設定間の一致までは強制しない）。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-129289（GHSA-qc49-hpvq-g2w6）— PHP-FPM のリクエストスマグリング

内容：PHP が HTTP リクエストボディの未読バイトを破棄しないまま、持続的な PHP-FPM / LSAPI 接続を再利用することがある。FPM では、残ったバイトが別の FastCGI リクエストとして解釈され、フロントエンドのルーティングを迂回して、攻撃者が選んだ PHP コードをワーカー権限で実行できる。偽造リクエストは SCRIPT_FILENAME や PHP_ADMIN_VALUE も制御でき、管理者設定の変更が同じワーカーの後続リクエストに残る場合がある。

発動条件：フロントエンドがバックエンド接続の再利用を有効にしていること（nginx の fastcgi_keep_conn on、Apache mod_proxy_fcgi の enablereuse=on、HAProxy の FastCGI 接続保持など）と、アプリケーションが php://input を開いて最後まで読まない経路があること。リクエストごとに接続を閉じる標準的な nginx / Apache 構成は、実証された FPM 攻撃の影響を受けない。メモリ破壊やアドレス知識は不要で、単一リクエストで成立する。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-129496（GHSA-gr4f-wgx5-jpfv）— タイムゾーンキャッシュの use-after-free

内容：プロセス起動中に PHP のエラーログファイルへ診断が書かれると、解放済みのタイムゾーンキャッシュへの参照が残ることがある。初回リクエストの早い段階で別の診断が出ると、解放済みメモリへアクセスし、メモリ破壊、ワークラッシュ、条件が揃えばワーカー権限でのコード実行に至る。

発動条件：デフォルトだけでは届かない。起動時の診断（不正な date.timezone、セッション設定による警告・非推奨など）が PHP のファイル形式 error_log 経路で実際に書かれること、対象が非スレッドセーフ（NTS）ビルドであること、新規または再利用されたワーカーの初回リクエストで早い段階の診断（max_input_vars 超過の警告など）が出ることが重なる必要がある。FPM 自体のエラーログだけでは条件を満たさない。FPM と Apache mod_php でワークラッシュが確認され、コード実行は追加条件付きのローカル実証にとどまる（リモートでの ASLR バイパスは示唆されているが、完全な独立実証はない）。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-129474（GHSA-8mjj-2r7p-4hg2）— マジックメソッドのバックトレースにおける use-after-free（PHP 8.5 のみ）

内容：__call() / __callStatic() で処理されるメソッドの引数をバックトレース用に集める際、解放済みメモリへアクセスすることがある。PHP 8.5 以降では、細工したリクエストで致命的エラーを起こし、未認証でワーカー権限のコード実行に至る可能性がある。

発動条件：実証されたリモート攻撃には fatal_error_backtraces=1（PHP 8.5 のデフォルトで有効）と zend.exception_ignore_args=0 が必要である。php.ini-production は zend.exception_ignore_args=1 を設定するため、その構成ではこの攻撃経路は成立しない。加えて、到達可能なマジックメソッド呼び出し、タイミングの合った致命的エラー、メモリ配置への影響力が必要である。PHP 8.2〜8.4 にも土台の不具合はあるが、リモートから攻撃者が制御できるトリガーは確認されておらず、対象範囲外とされている。

影響 / 修正：PHP 8.5 のみ。8.5.13 で修正。

CVE-2026-129182（GHSA-2fjv-p558-g82m）— 終了処理後の fatal エラーバックトレース再投入による use-after-free（PHP 8.5 のみ）

内容：10月の CVE-2026-109619 への修正で、実行終了時に last_fatal_error_backtrace は消去されるようになったが、終了処理の後段で致命的診断が出ると再び投入され、解放後のメモリを次リクエストが使うことがある。

発動条件：特定の INI 復元パターンが必要である。例として、グローバルとパス別設定の両方に max_memory_limit がある場合の復元失敗、グローバルで zlib.output_compression=1、パス別で 0 と出力ハンドラを併記した場合の競合エラーがある。さらに、同じワーカーの後続リクエストで実行初期化前の診断が必要である。この入口からのコード実行自体は実証されていない（ヒープ use-after-free とワークラッシュまで確認）。

影響 / 修正：PHP 8.5 のみ。8.5.13 で修正。

CVE-2026-126714（GHSA-fm2m-fjf5-v3cp）— 部分的に上書きされたセッションファイルによる RCE

内容：ファイルベースのセッションハンドラが、書き込みの中断により、新旧2つのシリアル化セッションの一部ずつを含むファイルを残すことがある。攻撃者がセッション内容に影響を与え、置換書き込みを中断できると、次回セッション開始時に攻撃者のオブジェクトがデシリアル化され、ガジェットチェーンがあればコード実行に至る。

発動条件：デフォルトの files ハンドラが対象である点は広いが、成立には、攻撃者がセッションデータに影響できること、有用な位置で書き込みが中断すること、利用可能なガジェットチェーンがあることが必要である。セッションアップロード進捗は入力経路の一つであり、この問題自体はそれに限定されない。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-129291（GHSA-jm4m-qfqx-967m）— PHP-FPM の epoll use-after-free によるローカル権限昇格

内容：ワーカー出力キャプチャが有効な場合、FPM マスターが解放済みワーカー記録への epoll イベントを処理し、use-after-free が起きる。非特権の FPM ワーカーで PHP コードを実行できる攻撃者が、マスター権限（通常 root）でコマンド実行に至る可能性がある。

発動条件：リモート単独では届かない。ワーカー内でのコード実行が前提で、対象プールで catch_workers_output が有効（デフォルトは無効。公式 PHP-FPM Docker イメージは有効化している）、epoll バックエンド、ワーカーの寿命や継承したパイプ記述子を操作できることが必要である。実証は PHP 8.5.12 の Docker イメージ（arm64 / x86-64）で行われた。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-129538（GHSA-5j3f-64r7-f564）— PHP-CGI の PATH_INFO 補正における境界外読み書き

内容：php-cgi が、Web サーバーから渡されたスクリプトとパスの値の不整合により、バッファ外へ読み書きすることがある。未認証でプロセスのクラッシュ、メモリ情報の露出、メモリ破壊が起こりうる。コード実行は主張があるが確認されていない。

発動条件：対象は php-cgi の CGI / FastCGI モードで、cgi.fix_pathinfo=1（デフォルト）であること。ただしそれだけでは足りず、除去される接尾辞より短い、または空の PATH_INFO が生じる特定の Web サーバーマッピングが必要である。通常の Apache の Action 構成や通常のリライトでは再現しなかったとアドバイザリは述べている。PHP-FPM と Apache モジュール版は影響を受けない。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-128090（GHSA-68fq-fh7h-f8gr）— PHAR の OpenSSL 署名バイパス（アルゴリズムダウングレード）

内容：OpenSSL 署名付き Phar の署名種別を、鍵なしハッシュ（SHA-256 等）へ差し替えることで、秘密鍵なしに改変したアーカイブを PHP に受け入れさせることができる。アプリケーションがそのアーカイブを実行すると、攻撃者の PHP コードが実行される。

発動条件：アプリケーションが OpenSSL 署名付き Phar と信頼経路で入れた .pubkey に依存していること、攻撃者が公開鍵ではなくアーカイブ側を改変・差し替えできること、その後にアーカイブが読み込まれることが必要である。

影響 / 修正：全ブランチ。8.2.36 / 8.3.37 / 8.4.28 / 8.5.13 で修正。

CVE-2026-129481（GHSA-g3vh-838c-65v7）— 中断されたセッション終了処理後の use-after-free（PHP 8.3 以降）

内容：セッション終了処理がコールバック内の致命的エラーで中断されると、スクリプトファイル名への古いポインタが残り、同じワーカーの後続リクエストが解放済みメモリを触る。10月の CVE-2026-109619 への不完全な修正として位置づけられている。この入口からのコード実行は実証されておらず、メモリ破壊とワークラッシュが確認範囲である。

発動条件：セッション変数の破棄時に呼ばれるコールバック（ユーザー定義ストリームラッパの stream_close() など）で致命的エラーを起こせること、同じワーカーで後続リクエストが処理されることが必要である。実証構成は PHP-FPM で OPcache 無効であった。PHP 8.2 には対象のフィールドがないため影響を受けない。

影響 / 修正：PHP 8.3 / 8.4 / 8.5。8.3.37 / 8.4.28 / 8.5.13 で修正。

パッチ・パッケージの提供状況

提供元状況（2026年11月19日確認時点）
PHP 公式（ソース / Windows バイナリ）提供済み。8.5.13、8.4.28、8.3.37、8.2.36 が php.net のダウンロードページで公開されている
Debian / Ubuntu の公式パッケージ未確認。このページの確認時点（公開当日）で、今回の CVE 群に対する Debian / Ubuntu のセキュリティ告知を確認できなかった。ディストリビューションは修正をバックポートし、php -v の表示バージョンが上がらないことがあるため、判定はパッケージバージョンと changelog で行う
Docker 公式イメージ（php）未確認。タグの再ビルド後に取得し直す必要がある。FPM イメージは CVE-2026-129291 の条件（catch_workers_output 有効）に該当する点にも注意する
その他のディストリビューション / ホスティング事業者未確認。各ベンダーの告知を確認すること

10月のリリース（8.5.12 / 8.4.27 / 8.3.36 / 8.2.35）で修正された CVE-2026-109618 と CVE-2026-109619 は、悪用が確認され CISA の Known Exploited Vulnerabilities にも載っている。10月以降更新していない環境は、今回の更新でそれらもまとめて解消される。

更新できない場合の緩和策（まとめ）

完全な対策は更新だけである。以下は更新までのつなぎとして各 GHSA が挙げる措置である。

  • セッション（CVE-2026-115560 / CVE-2026-126714）：session.upload_progress.enabled=0 を、リクエスト入力が処理される前に効く管理者設定（php.ini、FPM プール、サーバー設定）で指定し、全ワーカーを再起動する。ini_set() や .user.ini では遅すぎる。アップロード進捗を使う場合は、同じセッション保存先に触れる全構成で session.serialize_handler を揃え、形式の異なるアプリケーション同士で保存先を共有しない。セッションに保存する信頼できないデータの量も抑える。
  • PHP-FPM スムグリング（CVE-2026-129289）：フロントエンドのバックエンド接続再利用を無効にする（nginx は fastcgi_keep_conn を無効のまま、Apache は enablereuse を無効にする）。FPM / LSAPI のリスナを信頼できないネットワークへ直接公開しない。
  • PHP-FPM 権限昇格（CVE-2026-129291）：対象プールの catch_workers_output を無効にする。マスターを root で動かさないことは取れる権限を下げるが、修正にはならない。
  • PHP-FPM ステータス XSS（CVE-2026-129292）：ステータスエンドポイントを無効にするか、フル HTML 出力を止める。アクセス制限だけでは、通常リクエスト経由で仕込まれるため完全な対策にならない。
  • タイムゾーンキャッシュ（CVE-2026-129496）：起動時診断の原因（不正な date.timezone、非推奨設定など）を直し、マスターと全ワーカーを再起動する。PHP のエラーを syslog などファイル形式タイムスタンプ経路を使わない宛先へ送ることでも、実証されたトリガーを避けられる。
  • PHP 8.5 のバックトレース系（CVE-2026-129474 / CVE-2026-129182）：zend.exception_ignore_args=1、または fatal_error_backtraces=0 をワーカー側の管理者設定で指定し再起動する。display_errors=0 では防げない。
  • セッション終了後 UAF（CVE-2026-129481）：セッションクリーンアップ時のコールバックで致命的エラーを出さない。FPM では pm.max_requests=1 が実証経路を断つが、性能への影響がある。
  • PHP-CGI（CVE-2026-129538）：cgi.fix_pathinfo=0 に設定し、ルーティングが動くことを確認する。または Web サーバーのマッピングを、実在スクリプトと追加パス情報が整合する形に直す。FastCGI リスナへの直接アクセスは信頼できるフロントエンドだけに制限する。
  • PHAR（CVE-2026-128090）：公開鍵を認証済み経路で入手し、<archive>.pubkey をアーカイブの更新・ダウンロード経路から書き換えられない権限で置く。それができない場合は、PHP が読む前に信頼する鍵で検証する別の仕組みを使う。
  • 平文送信（CVE-2026-128064）：ストリーム関数へ渡す HTTPS / FTPS のスキームを小文字に統一する。リダイレクトを許可する場合は自動追従を止め、遷移先ごとに検証と正規化を行う。
  • 折り畳みヘッダ DoS（CVE-2026-127960）：外部リクエストの宛先とリダイレクト先を信頼できる先に制限する。出口プロキシで応答ヘッダのサイズと件数を制限することも有効である。
  • DOM（CVE-2026-129501）：攻撃者の文書に対して saveXml() を呼ばない。XML 出力が不要な HTML 文書では saveHtml() を使う。
  • SOAP（CVE-2026-129506）：影響を受けるエンドポイントへのアクセスを制限し、WSDL とスキーマは信頼できる入手元だけから読む。DTD を含む文書を SOAP 拡張の前段で弾く場合は、文字コードや変換を正しく扱う必要があり、単純な文字列検索では不十分である。

自分の環境の確認観点

  • PHP のブランチとバージョン（8.5.13 / 8.4.28 / 8.3.37 / 8.2.36 未満は対象）。ディストリビューションのパッケージでは php -v ではなくパッケージバージョンと changelog で判定する
  • 更新後に PHP-FPM / Apache などワーカーを再起動したか（パッケージを入れただけでは旧コードが動き続ける）
  • session.upload_progress.enabled の実効値と、セッション保存先を共有する構成同士で session.serialize_handler が揃っているか
  • FPM の前面で接続再利用が有効か（nginx fastcgi_keep_conn、Apache enablereuse など）、プールの catch_workers_output とステータスエンドポイントの有効状態
  • PHP 8.5 では fatal_error_backtraces と zend.exception_ignore_args の実効値（php.ini-production かどうか）
  • php-cgi を使っている場合は cgi.fix_pathinfo と Web サーバーのマッピング
  • 起動時に PHP のエラーログファイルへ診断が出ていないか（不正な date.timezone 等）、エラーログの宛先
  • PHP 8.1 以前を使っている場合は、ベンダーのバックポート有無か、サポート中ブランチへの移行計画

Cloudflare Code Mode：2,500超のAPIを2つのツールに畳むMCPの設計

確認日：2026年11月25日
一次資料はCloudflare公式ブログ、cloudflare/mcp リポジトリのREADME、Cloudflare開発者ドキュメント、@cloudflare/codemode パッケージのREADMEです。発端となったX投稿は出典に挙げますが、主張の根拠は公式資料で確認しました。

要点
  1. MCPでツールを増やすと、その定義がモデルの文脈を常駐して食います。Cloudflare APIの2,594エンドポイントを通常のツールとして載せると定義だけで1,170,523トークン（Cloudflareの実測）になり、多くのモデルの文脈枠を超えます。
  2. Code Modeはツールを search と execute に絞ります。仕様はサーバー側に置き、モデルはJavaScriptを書いて必要なエンドポイントだけを検索し、API呼び出しの連鎖もコードとして1回で実行します。常駐コストは約1,000トークンで、エンドポイントが増えてもほぼ固定です。
  3. コードはDynamic Workerの隔離環境で実行されます。ファイルシステムと環境変数はなく、外向き通信は既定で無効です。ただし隔離が防ぐのは通信と秘密の漏えいで、コードの正しさまでは保証しません。
  4. 効果が出るのは、エンドポイントが多い大きなAPIと、多段の編排がある作業です。ツールが数個の小さいサーバーや1回だけの呼び出しでは、通常のツール呼び出しと大差ありません。

数字の内訳：117万トークンは何を測ったものか

MCPは、エージェントに外部ツールを接続する標準の仕組みです。接続したツールの定義（名前、説明、引数のスキーマ）はモデルの文脈に入り、会話の間ずっと残ります。ツールが数個なら問題になりませんが、APIのエンドポイントを1つずつツール化すると、定義の合計がそのまま常駐コストになります。

Cloudflare APIは2,500を超えるエンドポイントを持ちます。cloudflare/mcp のREADMEに載る比較表では、見せ方によって次のように変わります。

見せ方ツール数トークン何を測ったものか
生のOpenAPI仕様をそのまま渡す―約2,000,000仕様文書そのものの大きさ
ネイティブMCP（完全なスキーマ）2,5941,170,523全エンドポイントを完全なスキーマ付きツールとして定義した場合。公式ブログでは tiktoken で計数したと明記
ネイティブMCP（最小スキーマ）2,594244,047スキーマを必須パラメータだけに削った場合
Code Mode3約1,100search / execute 等のツール定義のみ。公式ブログの表現では「約1,000トークン」

「117万トークンが1,000トークンに」という見出しの数字は、この表の2行目と4行目の比較です。削減率は99.9%とされます。200万という数字は仕様そのものの大きさで、ツール定義の数字とは別物です。混ぜて読むと過大にも過小にも見えるため、この記事では分けて書きます。

もう1つ大事なのは、この約1,000が「固定」だという点です。エンドポイントが増えても、モデルが常駐で持つのは search と execute の定義だけなので、コストはAPIの規模に比例しません。比例するのは、後述する検索と実行の往復の分だけです。

仕組み：仕様と実行をサーバー側に置く

Code Modeの考え方は、2025年9月26日のCloudflare公式ブログ「Code Mode: the better way to use MCP」で提示されました。MCPツールをTypeScriptのAPIに変換し、モデルにはツールを直接呼ばせず、そのAPIを呼ぶコードを書かせます。根拠として挙げられているのは、モデルは学習で大量の実コードを見ている一方、ツール呼び出しの例は作り物が中心で、コードを書く方が得意だという点です。Anthropicも独立に同じ型を「Code execution with MCP」として提示しました。

2026年2月20日の公式ブログで、Cloudflareはこの型をサーバー側に置いた公式MCPサーバーを公開しました。接続先は https://mcp.cloudflare.com/mcp です。サーバー側に置く利点は、エージェント側に特別な仕組みが要らないことです。通常のMCPクライアントから接続でき、コードの実行環境はサーバーが用意します。

公開されるツールの中核は2つです。search は、サーバーが保持するOpenAPI仕様（参照は解決済み）に対してモデルが書いたJavaScriptを実行し、一致したエンドポイントだけを返します。execute は、cloudflare.request() を使うJavaScriptを実行し、実際のAPIを呼びます。現行のREADMEでは、この2つに開発者ドキュメント検索の docs と、接続中アカウントを返す whoami が加わります。コスト表の「3ツール」はこの構成を数えたものです。

動き：searchで絞り、executeで連鎖させる

実際の使い方は、検索と実行の2段です。公式ブログの例（ゾーンをDDoS攻撃から守る）では、まず search でパスやタグを条件に仕様を絞り、WAFとルールセットのエンドポイントだけを取り出します。次に特定エンドポイントのスキーマをコードで掘り、使えるフェーズの値を確認します。その後 execute に移り、既存ルールセットの一覧取得、DDoS用とWAF用エントリポイントの取得を1回の実行の中で連鎖させます。ブログによれば、この一連は4回のツール呼び出しで完了しました。

従来方式との違いは、中間結果がモデルを経由しないことです。通常のツール呼び出しでは、呼び出しごとに結果がモデルへ戻り、モデルが次の呼び出しを決めます。ページング、絞り込み、集計のような機械的な連鎖までモデルを経由すると、その分だけ往復とトークンが増えます。Code Modeでは連鎖はコードの中に書き、モデルへ戻るのは最終結果だけです。

結果の側にも上限があります。READMEによれば、search と execute の結果はそれぞれ約6,000トークンで切断され、切断箇所にはその旨が表示されます。結果をファイルなどへ流してモデルに読ませない場合に限り、全量を返す指定もできます。

サンドボックス：隔離で防げること、防げないこと

モデルが書いたコードをそのまま実行する設計なので、実行環境の隔離が前提になります。公式ブログによれば、コードはDynamic Workerのisolate（V8のサンドボックス）で実行され、ファイルシステムはなく、漏れる環境変数も置かれず、外向きのfetchは既定で無効です。必要な場合だけ、外向き通信をハンドラで明示的に制御できます。

認証も境界の内側で処理されます。サンドボックスには認証付きの cloudflare.request() クライアントが渡り、APIトークン自体はモデルのコードに渡りません。接続はOAuth 2.1に対応し、権限は接続時に利用者が承認した範囲へ絞られます（ダウンスコープ）。READMEには、APIトークンで接続する場合の注意として、Client IP Address Filteringが有効なトークンは現在未対応であることも明記されています。

一方で、隔離が保証するのは「勝手な通信をしない」「秘密が漏れない」という境界の話です。コードが意図どおりのエンドポイントを正しい引数で呼ぶかは、モデルの書くコード次第です。何を実行したかを後から追える記録や、変更前の承認をどう挟むかは、この仕組みの外側、利用側の設計に残ります。

自分のサーバーに使う：@cloudflare/codemode

この型は、Cloudflareの公式サーバー専用の話ではありません。X投稿で紹介されていた「底層ライブラリのオープンソース化」も事実で、パッケージ @cloudflare/codemode が cloudflare/agents リポジトリで公開され、npmから導入できます。公式ブログ（Dynamic Workersの記事）によれば、SDKには2つの入口があります。既存のMCPサーバーのツール面を単一の code() ツールへ置き換える codeMcpServer() と、OpenAPI仕様から search / execute 型のサーバーを組み立てる openApiMcpServer() です。後者が公式Cloudflare APIサーバーと同型です。

注意は、パッケージのREADME冒頭に「Experimental（実験的）。破壊的変更があり得る。本番では注意」と明記されていることです。実行の土台としてDynamic Worker Loaderも必要になります。設計の方向性は公式サーバーで実運用されていますが、SDK自体はまだ変わり得る段階だと分けて読むのが正確です。

なお、公式サーバー側にはCode Modeを外す選択肢もあります。URLに ?codemode=false を付けると、各エンドポイントが個別ツールとして登録されます（READMEでは約3,000ツール、生成はforge）。自分のクライアント側でCode Modeを実装している場合の合成用ですが、トークンコストは約24.4万の水準に戻るとREADMEが警告しています。

向き不向き

効果が出る条件は、APIが大きいことと、作業に連鎖があることの2つです。エンドポイントが数千規模なら、定義の常駐コストだけで通常方式は成り立ちません。検索して、絞り込んで、まとめて変更するような多段の作業では、中間結果をモデルに経由させない分も効きます。

逆に、ツールが数個から十数個の小さいサーバーでは、定義の常駐コスト自体が小さいため、削減できる量も小さくなります。1回だけの単純な呼び出しでは、検索の往復が増える分だけ通常方式より遅くなる場面もあります。往復ごとに人の承認を挟む運用や、モデルにコードを書かせる前提が置けない環境とも相性がよくありません。

注意点と限界

  • 数字はCloudflare自身の計数です。1,170,523トークンは「全エンドポイントを完全スキーマでツール化した場合」の定義量で、作業全体の消費量ではありません。実作業では検索と実行の往復が別に発生します。
  • 結果は約6,000トークンで切断されます。広い条件で検索すると先頭だけが返るため、条件の絞り方が結果の質を左右します。
  • 正しさはモデルが書くコードに依存します。スキーマを掘ってから呼ぶ手順は用意されていますが、誤ったエンドポイントや引数を選ぶ可能性は残ります。
  • SDK（@cloudflare/codemode）は実験的と明記されています。公式サーバーの利用と、SDKでの自作では、安定性の前提が違います。
  • Client IP Address Filteringが有効なAPIトークンは、公式サーバーへの接続に現在使えません（README）。

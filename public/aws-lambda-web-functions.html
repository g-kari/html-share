「速い・安い」は設計の狙い。条件を確認する

Web FunctionsはWeb向けに配布・配送・実行モデルをまとめたサービスです。全アプリで低遅延が安定する、費用を自動最適化する、といった保証ではありません。

1環境128件は、最大設定値

maxConcurrencyPerEnvironmentは1–128、既定64。実際に受け入れる同時処理数はCPU・memoryなどの状態で動的に調整され、設定値より低くなります。128倍の性能・128分の1の料金を意味しません。[6]

設定範囲の図。実効並列度は測定が必要です。

世界向けroutingに、保証は足さない

MultiRegionはコード・設定の複製とlatency-based routingを簡略化します。routingはbest-effortで、常に最短遅延のRegionを選ぶわけではなく、health-based failoverでもありません。DB・session・dataの複製や障害時の整合性は別設計。cold startやtail latencyの改善もアプリごとに検証します。[7] [6]

DB・LLM待ちで減るのはCPU消費

何も計算していないI/O待ちそのものにactive CPU料金はかかりません。一方、環境が生きている間の消費memory、起動・background処理のCPU、request料金は残ります。並列化も総CPU秒を自動で減らすものではありません。[26]

CPU処理DB / 外部API待ちCPU処理
環境の生存中：消費memoryのGB秒を課金

AI streamingのモデル料金は別

LLM gatewayやSSEで応答を待つアプリは、I/O中心のCPU課金と相性がよい可能性があります。ただし外部AIのtoken・推論料金、DB、転送、前段サービスの費用まで減るとは言えません。SSRでもCPU中心なら高くなる場合があり、下のグラフは仮想入力です。

throttling・WAF・streamingの注意点
  • API keyは認証ではありません。REST usage planのquota/throttleもbest-effortで、厳密な利用量・請求上限の保証には使えません。[36]
  • Webにもnativeな制限はあります。rateLimit / maxEnvironmentsは任意設定、既定は未設定。rateLimitは環境到達前のendpoint全体RPSで、継続超過は429ですが短いburstを受け入れる場合があります。maxEnvironmentsもrevision切替等で一時超過があり得ます。利用者ごとのquotaとは違います。[6]
  • Private integrationとPrivate APIは別です。HTTP APIがVPC内backendへ接続できることは、client-facing入口がprivateになることを意味しません。RESTのPrivate APIを要件別に比較します。[31] [37]
  • WAF直接連携はREST API stage。HTTP API・Function URL・WebではCloudFront等の前段を含めて構成・料金を検討します。[38] [9]
  • REST STREAMは専用条件です。Regional/Privateのidle timeoutは5分、edgeは30秒。request streamingは非対応。STREAMではendpoint cache・content encoding・VTL response transformationが使えません。RESTのbody変換機能も通常LWAのAWS_PROXYへ自動的に適用されるものではありません。[24]

損益分岐点は「条件付き」で計算する

月何件から安くなる、という共通の閾値はありません。active CPU・消費メモリ・総環境生存時間・Eventの設定メモリと課金durationが必要です。

Eventの課金秒/件をtE、WebのCPU秒/件をc、消費GBをmW、全環境生存秒をHとします。起動等の追加CPUをU0とすると、U＝N×c＋U0、B≈mW×H。周辺費を両側で除いた簡易モデルは次の通りです。

d = pE × mE × tE − pC × c − (rW − rE)

N* = (pM × mW × H + pC × U0) / d

  • d > 0：Hを固定できるtraffic範囲ならN > N*でWebが安い
  • d ≤ 0：非負のmemory/追加CPU費なら、Webが安くなる正の交点はない
  • 実際のHは負荷分布・scale・headroom・地域等で変わるため、この交点を全trafficへ外挿しない

Web Functionsを試す理由

  • Node.js HTTP API / SSR / LLM gatewayでI/O待ちが長い
  • warm環境で複数requestを重ねられる
  • 2 GB / 2 Arm64 vCPU・対応regionで足りる
  • Adapter保守や複数regionのコード配布を軽くしたい

LWAを残す理由

  • 多言語、既存OCI image、x86専用依存、2 GB超のmemory
  • 少量traffic・小メモリ構成が実測で十分
  • PCや既存API Gatewayの認証・管理機能が重要
  • private資源・複数region・非HTTP処理を独自構成で統合している

本番移行前のチェック

  1. Node.js 24 / Linux Arm64依存、起動10秒以内、entry file、AWS_LAMBDA_HTTP_ENDPOINTでのlistenを確認。[4]
  2. request固有状態をglobalに置かない。awaitを跨ぐmutable state、/tmpの名前、DB pool・接続数を検証。重要なbackground workはdurable queueへ。shutdownは全故障モードでの完了保証ではありません。[12]
  3. idle後初回・通常・段階増加・burst・SSEを同じアプリ/route/依存先/サイズで負荷テスト。p50/p95/p99、TTFB、429/5xx、stream完了率、CPU・memory・環境時間を記録。
  4. Host/forwarded header・cookie・redirect、trusted proxy設定を確認。未検証のX-Forwarded-Hostを認証判断へ無条件に使わない。[10]
  5. DB/secret/sessionのregion配置とdata整合性を別設計。endpoint/revisionのActive表示だけで終えず、HTTP smoke testと各regionの反映を確認。[7] [13]

費用比較から抜けやすいもの

  • API Gateway：既存で使う場合のみ種類・件数・転送を加算。Function URLのbaselineへ勝手に足さない。URL自体の追加料金はありません。[21] [30]
  • CloudFront / WAF：custom domain・WAF等の前段、viewer/origin件数・cache hit・転送を両側で比較。
  • 転送 / logging / storage / VPC：Internet out・region間・NAT等は該当構成で追加。VPC対応だけでNATが必須とはしない。
  • Provisioned Concurrency：requests＋予約GB秒＋PC実行GB秒＋spillover。過剰予約との差額をAdapter自身の費用と呼ばず、同じ遅延目標を満たすか確認。[25] [26]

無料枠は別に確認。主表は無料枠なしです。Eventには公表月間100万requests/400,000 GB秒がありますが、適用資格・アカウント全体の残量が必要。Webの適用量・共有条件は本調査で確認できていません。Web無料枠がゼロと断定せず、両側の実請求条件で再計算してください。新規account向けcreditも継続的な無料容量ではありません。[26] [29]

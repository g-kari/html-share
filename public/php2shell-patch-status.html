公式資料から確認できる背景と、今回の判断

PHP公式マニュアルでは、アップロード進捗機能はスクリプトの実行前にセッションへ情報を書き込むと説明されています。セッション設定では、session.serialize_handlerの既定値はphp、session.upload_progress.enabledは既定で有効です。[15][16]

serializerの切り替えと既存セッションの問題は、2015年のPHP Bug #71101でも議論されています。同記録はDoc Bug / Analyzed、CVEはNoneです。この過去の記録は背景の説明に限り、2026年の個別のRCE主張を確認・否定する根拠には使いません。[14]

本記事の判断：公式の既知2CVE修正と追加記事の評価は分けます。新しい公開主張がある以上、更新済みという理由だけで個別構成の安全を保証できません。一方、記事の自己検証だけで全構成・全版への影響やroot権限取得まで確定したとは扱いません。対応する公式告知・追加CVE・追加リリースは今回確認できていません。[17]

2件の原因と、Webサーバー構成について

CVE-2026-109618は、メモリ不足（OOM）時に内部状態が壊れる問題です。CVE-2026-109619は、リクエストをまたいで残る古いグローバル状態により、解放済みメモリを使用する問題（Use-After-Free / UAF）です。詳細な成立条件はPHP公式のセキュリティアドバイザリを参照してください。[2][3]

調査対象はWebリクエストを処理するPHPです。公開研究では、mod_phpでアプリケーションの処理開始前にRCEへ到達する実証が示され、PHP-FPMについても条件付きの実証が説明されています。「nginxとPHP-FPMの組み合わせだから無関係」とは判断できません。構成名だけではなく、公式アドバイザリと実際に稼働するPHPを確認する必要があります。[8]

ここでは攻撃コードや再現手順を転載せず、更新判断に必要な原因と状態を整理しています。

修正版について確認した公開Issue3件

以下は2026年10月22日18:41 JSTの確認時点の公開Issue・PRの状態です。後続のコメント、マージ、リリースで変わるため、判断時にはリンク先も確認してください。

SimpleXMLの二重解放

再現・検証あり #24488：Open / Verified

PHP 8.4.27・8.5.12で、SimpleXMLと循環参照のガベージコレクション（GC）に関わる二重解放が報告されています。当初Issueはメモリ破損・クラッシュを示します。追加記事のHTTP DoSに関する主張は、上の追加レポート節に分けました。[4]

条件・原因・修正候補の状況

報告では、get_object_varsなどでSimpleXMLオブジェクトのproperties表を実体化し、循環参照をGCが処理する条件が関わります。SimpleXMLを利用しているだけで、すべての処理に同じ影響が出るとまでは言えません。アプリケーションがこの条件へ到達するかを確認します。[4]

原因として関連付けられているのはGH-24050の修正です。既知のPHP2Shell 2CVEの修正が破られたという説明ではありません。修正候補PR #24494はレビュー承認済みですが、調査時点ではOpen・未マージです。レビュー承認、マージ、修正版の公開、個別環境への適用は、それぞれ別の状態です。[5]

hard OOM時のプロセス終了

トリアージ待ち #24492：Open / Needs Triage

PHP 8.4.27・8.5.12で、sprintf・pack・bin2hexなどのhard OOM時に、プロセスが終了する回帰が報告されています。これを「RCE修正を回避できる」という意味には読み替えません。[6]

回帰報告としての位置付け

ここでの争点は、メモリ不足時の終了挙動が従来と変わるという報告です。稼働への影響を確認する価値はありますが、調査時点ではNeeds Triageであり、公式に認定済みの新たなセキュリティ脆弱性とは断定できません。公開Issueが存在することだけから、攻撃者による到達性やRCE成立までを推定しないようにします。[6]

upload-progress処理でのセッション破棄

トリアージ待ち #24493：Open / Needs Triage

PHP 8.5.12で、特定の予約済みプロパティ名を持つ保存オブジェクトとupload-progress handlerの組み合わせにより、セッション全体が破棄される報告があります。この報告も、調査時点では公式認定済みの新たなセキュリティ脆弱性とは断言できません。[7]

確認する処理と、一般化できない範囲

確認対象は、報告にある保存オブジェクト、予約名、アップロード進捗処理が関わる条件です。通常のセッション処理すべてが必ず破棄されるという報告としては扱いません。アップロードとセッション継続を通常のアプリケーション操作で確認し、該当条件を使う場合はIssueの調査経過を追います。[7]

追加の不具合は存在します。ただし、「メモリ破損の再現」「回帰の報告」「PHP2Shellの認証不要RCEの再成立」は同義ではありません。既知の修正を適用する判断と、追加報告の影響を調べる判断を分けて進めます。

ほかの公開情報を読むときの注意

「別のvariant」「ほかにも修正中」「5つのchain」といった言葉も、修正版に未修正RCEが5件残っているという根拠にはなりません。情報の対象と、修正状態を確認します。

Wizの「ほかのvariant」は、根本修正と併せて読む

Wizの解説はほかのvariantにも言及していますが、根本のパッチで解消されると説明しています。「variantがある」という部分だけを抜き出し、公式修正版でも同じ攻撃が成立するという意味にはしません。[8]

OpenAIの「ほかにも重大な脆弱性を修正中」は、PHPと特定されていない

OpenAIの公開記事にある、ほかにも重大な脆弱性の修正を進めている旨の記述は、その対象をPHPと特定していません。この文章だけから「PHP2Shellの修正版に、別の重大なPHP脆弱性が残っている」と結論付けることはできません。[9]

mbstringの修正欠落報告は、開発masterが対象

Issue #24489のmbstringに関する報告は、開発用masterの修正欠落を対象としています。そのままPHP 8.2.35・8.3.36・8.4.27・8.5.12の安定版4つへ一般化する根拠にはできません。ブランチと対象コミットを分けて読む必要があります。[10]

公開PoCの「5 chains」は、未修正RCEが5件という意味ではない

ikow/php2shell-pocのREADMEも、上記4修正版を対策済みと記載しています。攻撃chainの数と、独立した未修正脆弱性の数は一致するものではありません。「5 chains」を「5件の新しい未修正RCE」と読み替えないようにします。[11]

利用者は更新と動作確認を進める

今回の追加報告は、更新を延期したり、旧脆弱版へ一律に戻したりする根拠にはしません。導入元の修正版を稼働プロセスへ反映し、利用する処理の動作を確認します。

  1. 導入元と修正状態を確認する。
    利用中のPHP系列、パッケージの提供元、ベンダーの告知を確認します。独自のバックポートを行う配布元では、上流の番号だけで修正の有無を決めません。
  2. 動いているPHPへ反映する。
    FPMやApacheの既存workerが古い実体を使い続けていないか確認します。構成に応じて再起動やコンテナの再作成を行い、新しい実体でリクエストを処理させます。
  3. 通常の利用経路をスモーク確認する。
    通常処理、アップロード、セッションの維持を確認します。該当するSimpleXMLの使い方がある場合は、その処理も重点的に確認します。
  4. 追加Issueと後続リリースを追う。
    影響が疑われる場合は、報告の条件と自分のアプリケーションを照合し、修正PRのマージ・リリース・ベンダー提供を確認します。

php -vの結果やパッケージの導入完了だけでは、Webリクエストを処理しているPHPの実体確認にはなりません。設定による緩和やWAFも、それだけで完全に対処できたとは扱いません。

セッションとアップロード進捗の設定確認

PHP公式の機能説明と設定項目を基に、読み書きでセッションのシリアライズ形式が食い違う設定がないか確認します。同じセッション保存先を共有するアプリケーションや処理系がある場合も、形式と設定を照合してください。これは構成確認の提案であり、個別環境の攻撃成立を判定するものではありません。[15][16]

アップロード進捗機能が不要なら、依存する機能を確かめたうえで無効化を検討します。公式にも不要な場合の無効化に関する注意があります。files方式のセッション保存先はWebから公開しない場所に置き、アクセス権も確認します。これらを行っただけで、あらゆる問題への完全対処と判断しません。[15][16]

Amazon Linux 2のPHP 8.2 Extraを使う場合

AWS公式のALASには、両CVEの修正パッケージとして8.2.35-1.amzn2.0.1が掲載されています。対象アーキテクチャはaarch64とx86_64です。Amazon Linux 2のPHP 8.2 Extraを利用している場合の確認材料であり、ほかのOSやPHP提供元へそのまま当てはめる情報ではありません。[12]

実際の更新では、導入済みパッケージとAWSの最新告知を照合したうえで、稼働するFPM・Apache workerへの反映とアプリケーションの動作を確認してください。

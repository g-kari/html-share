AWS ElastiCache 技術メモ　確認日：2026年10月15日

Redis 6 → Valkeyで、
エンドポイントは変わる？

既存クラスターをインプレース更新するなら、
エンドポイントのDNS名は変わらない。[1]

ノードベースでは、変わるのは裏側のノードIP。
「別のValkeyクラスターを新規作成して移す」場合とは違います。[1][3]

本稿はAWSの公開仕様を整理したものです。個別環境の構成・移行可否・停止時間は検証していません。AWSリソースの変更手順を実行した報告ではありません。

AWSは「DNS名は維持」と明記

ここでいうインプレース更新は、既存のElastiCacheのエンジンを変更する操作です。新しい移行先クラスターを作る操作ではありません。[3]

変わるかどうかは「移行方法」で分ける

既存クラスターの更新

今あるリソースで、エンジンをRedis OSSからValkeyへ変更。

DNS名を維持

既存のエンドポイントを使用して、更新後の接続を確認します。[3]

別クラスターへ移行

例えば、スナップショットから新しいValkeyクラスターを作成。

新しい接続先へ切り替え

AWSの手順でも、アプリの設定を新クラスターのエンドポイントへ変更します。[3]

「接続先を変えたくない」だけが理由なら、
Valkeyを候補から外す必要はありません。

上の公式仕様からの判断です。利用中のクライアントや構成が、目的の更新先に対応するかどうかは別途確認します。

ただし、「同じDNS名」≠「完全無停止」

書き込みの瞬断に備える

AWSはRedis OSS 5.0.6以降からの更新を、最小限の停止で行うと説明しています。一方で、数秒のフェイルオーバー中は書き込みが利用できないとも明記しています。Redis OSS 6は、このバージョン条件を満たします。[1]

この「数秒」は更新作業全体の所要時間ではなく、切り替え時の説明です。個別アプリの復旧時間を保証する値ではありません。

実務上の推奨：IPを固定せずDNS名で接続し、DNSの再解決、接続プールの再接続、タイムアウトとリトライを事前に検証します。書き込みの再試行では、重複実行の影響も確認します。

Redis OSSを続ける場合の「最新」は？

7.1

ElastiCacheのRedis OSS提供版で最新の系列
2026年10月15日のAWS公式一覧で確認。[2]

Redis本体の最新安定版とは別です。AWSはElastiCacheの7.1をRedis OSS 7.0互換と説明しています。「Redisを最新にする」という場合は、ElastiCacheの提供版と区別して指定します。[2]

移行前に確認すること

構成や戻し方の注意点は、必要な項目だけ開いて確認できます。

単一ノード・パラメーターグループ

単一ノード（cluster mode disabled）でレプリケーショングループに未所属なら、先にグループへ追加する手順を確認します。[1]

カスタムパラメーターグループには、静的パラメーター値を合わせたValkey用のものが必要です。[1]

戻せるバージョンには制限がある

インプレースで戻せるのは、Valkey 7.2 → Redis OSS 7.1。Redis OSS 6や、任意のValkeyバージョンからの復帰は対象ではありません。[3]

更新先を決める前に、バックアップ、復元先、データの扱いまで含めて復旧方針を決めることを推奨します。別クラスターへ復元する場合の接続先切り替えも、計画に含めます。[3]

環境固有の互換性と検証

以下は本稿で確認していない、環境ごとの確認項目です。

  • 正確なRedis OSSバージョン、ノード構成、Multi-AZ、クラスターモード、対象リージョンで選択可能な更新先。
  • クライアントライブラリー、接続プール、認証・TLS、ACL、Luaスクリプト、使用コマンドの互換性。
  • 検証環境での更新前後の読み書き、TTL、接続復旧、レイテンシー・エラー率、および必要なメンテナンス時間。

本番変更の可否は、上記の確認結果で判断します。DNS名が維持されるという一般仕様だけで、無検証の更新を推奨するものではありません。

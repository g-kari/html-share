Redis 6 → Valkeyで、
エンドポイントは変わる？

既存クラスターをインプレース更新するなら、
エンドポイントのDNS名は変わらない。[1]

ノードベースでは、変わるのは裏側のノードIP。
「別のValkeyクラスターを新規作成して移す」場合とは違います。[1][3]

本稿は公開仕様の整理です。個別環境の構成・移行可否・停止時間は検証していません。AWSリソースは変更していません。

DNS名とIPの図解Redis 6 → Valkey 9.1の変更点互換性の注意点

AWSは「DNS名は維持」と明記

ここでいうインプレース更新は、既存のElastiCacheのエンジンを変更する操作です。新しい移行先クラスターを作る操作ではありません。[3]

変わるかどうかは「移行方法」で分ける

既存クラスターの更新

今あるリソースで、エンジンをRedis OSSからValkeyへ変更。

DNS名を維持

既存のエンドポイントを使用して、更新後の接続を確認します。[3]

別クラスターへ移行

例えば、スナップショットから新しいValkeyクラスターを作成。

新しい接続先へ切り替え

AWSの手順でも、アプリの設定を新クラスターのエンドポイントへ変更します。[3]

「接続先を変えたくない」だけが理由なら、
Valkeyを候補から外す必要はありません。

上の公式仕様からの判断です。クライアントや構成が、目的の更新先に対応するかどうかは別途確認します。

ただし、「同じDNS名」≠「完全無停止」

書き込みの瞬断に備える

AWSはRedis OSS 5.0.6以降からの更新を、最小限の停止で行うと説明しています。一方で、数秒のフェイルオーバー中は書き込みが利用できないとも明記しています。Redis OSS 6は、このバージョン条件を満たします。[1]

この「数秒」は更新作業全体の所要時間ではなく、切り替え時の説明です。個別アプリの復旧時間を保証する値ではありません。

実務上の推奨：IPを固定せずDNS名で接続し、DNSの再解決、接続プールの再接続、タイムアウトとリトライを事前に検証します。書き込みの再試行では、重複実行の影響も確認します。

Redis OSSを続ける場合の「最新」は？

7.1

ElastiCacheのRedis OSS提供版で最新の系列
2026年10月15日のAWS公式一覧で確認。[2]

Redis本体の最新安定版とは別です。AWSはElastiCacheの7.1をRedis OSS 7.0互換と説明しています。「Redisを最新にする」という場合は、ElastiCacheの提供版と区別して指定します。[2]

Redis OSS 6 → Valkey 9.1：何が変わる？

大きい差は、I/O処理とメモリ効率の改善、そして新しいTTL・検索・アクセス制御です。以下はElastiCacheで利用する際の主要差分です。[7][8][10][11]

既存のキャッシュ用途：I/O・メモリ改善の恩恵を検証する。
アプリを改修する用途：新コマンドやフィールド単位TTLを活用する。
特に再確認：Lua、ACL、クライアントの応答解析。

6.0と6.2では出発点が違います。すでに6.2なら、6.2で追加された機能は新規の差分ではありません。これは変更履歴であり、すべての中間版を順に通す手順ではありません。実際の更新先と利用可否は構成・リージョンで確認してください。

Redis OSS 6.2TTL操作・複数要素の問い合わせを簡素化

GETEXで値取得とTTL更新を一度に実行。SMISMEMBER、ZMSCORE、COPY、GEOSEARCHなども追加されました。TLS処理のオフロードによる改善もありますが、対象ノード条件があります。[4]

使いどころ：アクセス時に有効期限を延ばすセッションや、複数メンバーの確認。6.2で使っている場合は既存機能です。

Redis OSS 7.0Functions・ACL強化・Sharded Pub/Sub

Luaロジックをサーバーに保持するFunctions、複数の権限セットを扱うACL、シャード単位で配信するPub/Subを追加。Sharded Pub/Subはcluster mode enabled向けで、従来のPub/Subから自動的に切り替わるわけではありません。[5]

ElastiCache側ではEnhanced I/O multiplexingも導入。多数の同時接続を扱う際の、メインスレッドの処理効率を改善します。[6]

ElastiCache 7.1Redis 7.0互換のAWS性能強化版

I/Oスレッドへコマンド解析や応答整形を移し、メモリアクセスも最適化。主な追加性能強化は8物理コア以上が条件です。小さなノードで同じ効果が出るとは限りません。[6]

7.1はこのAWS提供版の番号であり、Redis OSS 7.0互換です。Redis本体の別の安定版を指すものではありません。[2]

Valkey 7.2Redis互換を引き継ぎ、構造とコマンドを改善

ElastiCacheのValkey 7.2はRedis OSS 7.2.4までの変更を含みます。List・Setのメモリ、Sorted SetやSCAN系の処理を最適化。ZRANK / ZREVRANK WITHSCORE、CLIENT NO-TOUCH、CLUSTER MYSHARDIDなどが加わります。[2]

Valkey 8.0I/O並列化とキー管理の省メモリ化

上流ValkeyでI/Oスレッド設計を改善。ElastiCacheではServerlessの高速スケーリングと、ノードベースのメモリ効率改善に反映されています。クラスターモードのキー管理を「スロットごとの辞書」に変え、キーごとの管理領域を削減しました。[7]

コマンド本体が何でも並列実行になる、という意味ではありません。通常のノードベース更新とServerlessへの構成変更も別です。

Valkey 8.1新ハッシュテーブル・Bloom filter・COMMANDLOG

ハッシュテーブルを刷新して省メモリ化。集合への所属判定に使うBloom filterと、大きなリクエスト・応答の把握に使うCOMMANDLOGを導入。パイプライン利用時のスループットも改善しています。[8]

Bloom filterは偽陽性を許容する確率的な判定です。厳密なSetの完全な代替として、無条件に置き換えるものではありません。[16]

ElastiCache 8.2Valkey 8.1互換にベクトル検索を追加

ノードベースクラスターでベクトル検索を利用可能に。類似検索やセマンティックキャッシュに使えます。8.2はElastiCacheの提供版で、Valkey 8.1互換です。上流Valkey本体にも同名のリリース系列があると混同しないでください。[9][2]

Valkey 9.0ハッシュのフィールドTTL・複数DB・検索拡張

Hash内のフィールド単位の有効期限、cluster mode enabledでの複数の番号付きDB、パイプライン処理の性能改善を追加。Hash全体を消さず、一部の項目だけ期限切れにできます。[10]

ElastiCacheの検索機能も、全文検索・集約・ベクトルとのハイブリッド検索へ拡張されています。これはAWSが提供する検索機能の説明です。[10]

Valkey 9.1DB単位ACL・新コマンド・小さい値の効率化

DB単位のACLを追加。新コマンドはHGETDEL（Hashフィールドの取得＋削除）、MSETEX（複数キーの設定＋共通TTL）、CLUSTERSCAN（クラスター全体のキー走査）。複数回のクライアント処理を簡素化します。[11]

128バイト未満のStringやSorted Setのメモリ効率、I/O処理、リハッシュ時の遅延を改善。メイン/I/Oスレッドの使用状況やJSON形式ログも追加されました。[12]

ElastiCacheでの9.1対応は、2026年6月23日にノードベースクラスター向けとして発表されています。Serverlessも同一のマイナー版・機能と決めつけないでください。[11]

性能の「最大○%」は、そのままRedis 6比にできない
Redis OSS 7.1：7.0比で最大2倍のスループット
8物理コア以上が対象。AWSの検証は500クライアント、GET 80% / SET 20%、16バイトキー、512バイト値、同一AZなどの条件です。[6]
Valkey 8.0：7.2比で約20%のメモリ減の例
クラスターモードで16バイトキー・100バイト値を使った、AWSの特定ワークロードの結果です。[7]
Valkey 8.1：一般的なキー/値パターンで最大20%省メモリ
新ハッシュテーブルによる追加の改善です。データ型・キー長・値長に依存します。[8]
Valkey 9.1：I/O改善で最大17%のスループット増
AWSが紹介する上流Valkeyでの検証結果であり、Redis 6→9.1の同一条件比較ではありません。9.0からのメモリ改善は、128バイト未満のStringで最大20%、Sorted Setで最大10%と説明されています。[12][2]

比較元・指標・条件が違うため、数値を足して「Redis 6より○%速い」とは計算しません。実際のノード・データ・TLS・接続数で、変更前後を同条件で測ることを推奨します。

移行で確認したい互換性の変更

「Redis互換」は、バージョン間の動作差までゼロという意味ではありません。特にRedis 6からは、Redis 7で変わった挙動も確認対象です。

Lua・ACL・Streamsの具体的なチェック

Lua：Redis 7ではスクリプト内のprint()が使えなくなり、読み取り専用スクリプトでのPFCOUNT / PUBLISHにも制約があります。自作Luaやライブラリー内蔵スクリプトを再実行して確認します。[13]

ACL / Pub/Sub：上流Redis 7はPub/Subチャンネルのデフォルト権限を制限する方向へ変更。既存権限が必ず壊れると断定せず、移行後のユーザー・チャンネル許可と購読を確認します。[13]

Streams / クライアント：XAUTOCLAIMの応答には削除済みIDの要素が追加されています。COMMAND系の応答も拡張されています。応答の固定長・固定形式を前提にした古いクライアントや独自パーサーを確認します。[13]

上流OSSの変更と、ElastiCacheの操作を混同しない

上流Valkey 9.1にはLuaエンジンのモジュール分離やTLS周辺の改善もあります。ただし、上流のvalkey.conf編集やモジュール管理手順を、そのままElastiCacheの操作手順にはできません。ElastiCache側の対応コマンド・管理API・パラメーターを確認します。[14][15]

特にServerlessは、ノードベースと対応コマンドや機能の範囲が異なります。新機能を使う際は、エンジン版だけでなく、利用形態も合わせて確認してください。[15]

更新だけで既存の設計が自動的に置き換わるわけではない

新しいHashフィールドTTLやDB単位ACLは、明示的に利用して効果を得る機能です。既存のキーTTLや権限設計を、自動的に移し替えるものとして扱わないでください。[10][11]

検証の推奨順：既存コマンドの結果とTTL → Lua/ACL → フェイルオーバー後の再接続 → 同条件の性能比較。ノードの縮小や新機能の採用は、エンジン更新と切り分けて判断すると原因を追いやすくなります。

移行前に確認すること

構成や戻し方の注意点は、必要な項目だけ開いて確認できます。

単一ノード・パラメーターグループ

単一ノード（cluster mode disabled）でレプリケーショングループに未所属なら、先にグループへ追加する手順を確認します。[1]

カスタムパラメーターグループには、静的パラメーター値を合わせたValkey用のものが必要です。[1]

Valkey 9.1からRedis OSS 6へ、そのまま戻せるとは考えない

AWSが記載するインプレースでの復帰は、Valkey 7.2 → Redis OSS 7.1。Valkey 9.1からRedis OSS 6へ戻す手順ではありません。[3]

更新先を決める前に、バックアップ、復元先、データの扱いまで含めて復旧方針を決めることを推奨します。別クラスターへ復元する場合の接続先切り替えも、計画に含めます。[3]

環境固有の互換性と検証

以下は本稿で確認していない、環境ごとの確認項目です。

  • 正確なRedis OSSバージョン、ノード構成、Multi-AZ、クラスターモード、対象リージョンで選択可能な更新先。
  • クライアントライブラリー、接続プール、認証・TLS、ACL、Luaスクリプト、使用コマンドの互換性。
  • 検証環境での更新前後の読み書き、TTL、接続復旧、レイテンシー・エラー率、および必要なメンテナンス時間。

本番変更の可否は、上記の確認結果で判断します。DNS名が維持されるという一般仕様だけで、無検証の更新を推奨するものではありません。

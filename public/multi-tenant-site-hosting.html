企業が自分の特設サイトを公開できる基盤を、どう設計する？

CloudFront + S3 はよい出発点。ただし「自分が複数サイトを置く」と「複数企業が任意のHTML・JavaScript・サーバーコードを持ち込む」は、セキュリティ要件がまったく違う。

結論：実現可能。ただし「パスだけで企業を分離」は避けたい

企業自身が好きなサイトをアップロードするサービスを目指すなら、共通の管理画面と配信基盤を持ちつつ、公開サイトのブラウザーオリジンと、動的コードの実行権限を企業ごとに分ける設計を推奨する。

推奨：企業別サブドメイン

company-a.sites.example.com、company-b.sites.example.com。CloudFront/S3の共通運用は維持し、企業ごとに独立した公開オリジンを持たせる。

注意：同じホストのパス分割

example.com/a/、example.com/b/はブラウザー上で同一オリジン。企業が任意のJSを配置できるなら、localStorageや同一オリジンAPIの安全な分離にならない。[1][2]

共通ドメインの「配下」はサブドメインで実現パス分割だけでは企業間のセキュリティ境界にならない

※ 公開先ドメインは例示。特定のAWSアカウントや既存環境への適用・料金試算・構築はまだ行っていない。

全体構成：管理系と配信系を分離する

企業が操作するコントロールプレーンと、訪問者にコンテンツを届けるデータプレーンを分けると、静的サイトから動的サイトへ機能を増やしやすい。

例：a.sites.example.com/ で静的LPを表示し、同じホストの /api/entry だけバックエンドに送る。フルSSRが必要なサイトは、該当サイトのWebアプリへ振り分ける。

最初に決めたいこと：1ホストか、1つの親ドメインか

案A：1ホストにパスを並べる

example.com/company-a/
example.com/company-b/
任意JSを持ち込む外部企業には非推奨

初期費用やCDN設定は小さくできるが、両サイトはブラウザー上で同じオリジン。パスやCookieのPathだけを企業境界と考えてはいけない。

案B：1つの親ドメインにサブドメインを作る

company-a.sites.example.com
company-b.sites.example.com
複数企業の自由なサイト公開に推奨

会社ごとに異なるオリジンを持てる。ワイルドカードDNS/TLSやCloudFront SaaS Managerを使って共通設定を運用できる。サーバー側の認可・Cookie設計は別途必要。

ここが最重要： /company-a のJSは、同じオリジンの /company-b とlocalStorageを共有する。独立企業の任意HTML/JSを同一ホストに載せると、別企業のブラウザー側状態や同一オリジンAPIへのアクセスを前提とした攻撃が成立しやすくなる。サブドメイン化した場合も、ワイルドカードCookie・認証・CORS・CSRFを適切に制御する。[1][2][5]

厳密に example.com/企業名/ を要求するなら、運営側が検証済みテンプレートだけを配信する、または独立したオリジンのsandbox iframeで表示するなど、掲載できるコードと権限に制約を設ける必要がある。

構成初期・運用コスト企業の自由度評価

CloudFront + S3 を最小構成で始める設定例

運営が管理する静的な特設サイトだけなら、まずはS3の1バケットにサイト別プレフィックスを置く。公開URLを /campaign-a/、/campaign-b/ とし、CloudFrontのS3オリジンにはOACを設定する。S3の公開アクセスはブロックする。

配置とURLを対応させる

public.example.com/campaign-a/
  → s3://site-assets/campaign-a/index.html
public.example.com/campaign-b/
  → s3://site-assets/campaign-b/index.html

サイト内のリンク・画像参照は、各プレフィックスを基準に構築する。異なる企業が任意のJavaScriptを公開できる共有ホストにはしない。

必要な設定

  • CloudFrontの代替ドメインとACM証明書を設定
  • S3 RESTオリジン + OAC、S3公開アクセスを遮断
  • /campaign-a → /campaign-a/index.html などをViewer Requestで補正
  • 更新時はハッシュ付きアセットを推奨。HTMLのキャッシュ期間・無効化を管理
設定上の注意：CloudFront Functionsでできること・できないこと

CloudFront FunctionsはViewer RequestでURIを書き換えられるが、選択済みCache Behaviorやオリジンの再選択を行う仕組みではない。パスごとに別S3バケットやAPIへ送るなら、事前にCache Behaviorとオリジンを構成する。[4][6][9]

Default root object = index.html は配下の全ディレクトリの index.html を自動で返す設定ではない。サブディレクトリの末尾スラッシュや拡張子なしURLを扱う場合は、URI補正の規則を明示し、存在しないファイル・APIパスへの誤適用をテストする。

運営管理のサイトが少数なら単一バケットが簡単。企業別のアップロード権限・監査・保存期間・削除単位が異なるならバケット分割、任意の動的コードを許可するなら分離実行を優先する。

動的サイトは「何を動かすか」で提供方法を分ける

用途候補提供時の注意
URL変換・リダイレクトCloudFront Functions高速・小規模。外部ネットワークアクセスやリクエスト本文の参照には使えない。[6]
応募・投票・Webhook・データ操作API Gateway HTTP API + Lambda認証・入力検証・レート制御・DBの企業境界を実装。企業を呼び出しURLだけで判定しない。
軽いAPIを低構成でLambda Function URLエンドポイント料金は追加されないが機能は限定的。OAC経由のPOSTは本文ハッシュ要件に注意。[7]
Node.jsのSSR・WebアプリLambda Web FunctionsSSR・APIルート・ストリーミングに対応。実行コードと権限のテナント分離が必要。[8]
独自サーバー・重いワーカーECS Fargate等企業別のコンテナ・ロール・資源制限・ログ・課金を設計。運用負荷は増える。
CloudFrontのパス振り分けだけでは完成しない： /api/* は動的オリジンへ、静的ファイルはS3へ。API側は CachingDisabled、必要なHTTPメソッドとCookie・ヘッダー・クエリの転送を適切に設定する。CloudFrontのBehaviorはプレフィックスを自動削除せず、URIだけ書き換えてもBehaviorを再評価しない。[9]
もっと詳しく：企業が任意のNode.jsコードをアップロードする場合

「HTMLを保管して配信」と「第三者のサーバーコードを実行」は別サービスとして考える。アップロードされたコードを、運営ポータルと同じLambdaや、秘密情報にアクセスできる共有プロセスでそのまま実行しない。ビルドも隔離し、公開時は企業別の実行ロール・CPU/メモリ・同時実行・ネットワーク・ログ・シークレット・データアクセスを制御する。

AWS Lambdaにはテナント別の実行環境を作る「Tenant isolation mode」がある。ただしこれは実行環境の分離を助ける機能で、企業単位のデータ認可やアプリの脆弱性対策を自動で保証するものではない。実際の対応ランタイム・リージョン・制限・料金を確認して採用する。[10]

企業自身が「アップロード→公開」できる運用の流れ

  1. 企業を登録・認証する組織ID・役割・サイト所有者・公開権限を確定。権限はサーバーで検証。
  2. サイト種別を選択する静的ZIP、管理済みテンプレート、API付き、SSR/独自コードの提供範囲を分ける。
  3. アップロードを隔離する一時領域へ保存し、拡張子・サイズ・展開パス・ファイル数・依存関係を検証。
  4. ビルドとレビューを実施隔離ビルド、悪性コード・依存脆弱性チェック、プレビュー、必要な承認。
  5. 企業別の公開先へ切替S3成果物または動的実行先を、サイトIDに対応する公開URLへ紐付ける。
  6. 監視・ロールバック公開世代を保存し、404/5xx・コスト・使用量・WAF・ログをテナント単位で確認。

静的サイトの配置例

s3://tenant-sites/
  tenants/
    company-a/
      launch/
        index.html
        assets/...
    company-b/
      event/
        index.html
        assets/...

1バケットでもプレフィックス単位のIAM権限は設定できる。企業によってバージョニングやデータ保管方針が違う場合は、バケット分割を検討。[11]

サイト別公開URLの例

console.example.com
  → 企業用の管理画面

company-a.sites.example.com
  → 静的LP + /api/ で動的処理

company-b.sites.example.com
  → SSRアプリ

custom-domain.example
  → 所有権を確認した企業独自ドメイン

CloudFront SaaS Managerは企業ごとのドメイン、証明書、共通配信設定の管理に向く。サイトの生成・認可・実行環境は別途必要。[3]

公開サービスにするなら外せない安全条件

  • 公開サイトは企業ごとに別オリジン（推奨：サブドメイン）
  • 管理画面は配信サイトと別オリジンにする
  • アップロード権限を会社・サイトの範囲へ限定する
  • 直接AWSの恒久的な認証情報を利用者に配布しない
  • 任意コードのビルド・実行は隔離する
  • API/DBは認証済みの企業IDで必ず認可する
  • 企業間でCookie・秘密情報・実行ロールを共有しない
  • 容量・リクエスト・実行時間・予算に上限を設ける
  • 公開ドメインの所有権を検証する
  • WAF、監査ログ、通報・公開停止、ロールバックを用意する
もっと詳しく：S3のOAC・キャッシュ・認可

S3オリジンは通常のS3エンドポイントとCloudFront OACを利用し、S3公開アクセスを遮断する。公開コンテンツの読み取り権限と、企業のアップロード権限は分ける。署名付きアップロードURLや短命の限定権限を使い、アップロード先のキーが会社の領域から逸脱しないようサーバーで固定する。

動的・個人化された応答は安易にキャッシュせず、認証情報やCookieの転送・キャッシュキーを確認する。企業IDをクエリ文字列や任意ヘッダーだけから信用しない。[9][12]

もっと詳しく：同一親ドメインでも認証は別途設計

a.sites.example.com と b.sites.example.com は別オリジンだが、ブラウザーCookieのDomainやSameSiteの設定次第で企業間の影響が生じる。ホスト限定Cookie、適切なCSRF対策、CORS制限、CSP、認証サーバーの分離が必要。アプリのSSOと企業サイトの任意JavaScriptを同じ信頼領域に置かない。

最小構成から育てるなら、この順番

Phase 1｜運営が公開する特設サイト

CloudFront × 1 + S3 × 1 + URL補正用CFFn。プレフィックスごとに静的ファイルを置く。内部運営で権限が共通なら、今までの案で十分。

低コストで先行可能

Phase 2｜企業セルフサービス

企業アカウント、アップロード・検証、プレビュー、企業別サブドメイン、サイト管理・ロールバックを追加。ここで「ホスト名と企業ID」の結び付けを確実にする。

Phase 3｜動的API・管理済みSSR

共通API入口を増設し、認可済みテンプレートや管理された実行環境から動的処理を提供する。全企業に任意のサーバーコードを許可する必要はない。

Phase 4｜企業独自のコード実行

ビルド・実行サンドボックス、企業別ロール、資源制限、課金、悪用対応まで設計。これは単なる「S3ホスティング」ではなく、PaaS/ホスティングサービスの構築になる。

最終判断： 会社が違っても運営側が制作・審査する特設サイトなら「1 S3 + 1 CloudFront」が運用最小。会社が任意のHTML/JS/SSRを自己公開するなら「共通管理 + 企業別サブドメイン + 静的/動的の分離実行」を最初から前提にする。

出典（一次資料・公式ドキュメント）

仕様・価格は変更され得る。以下は2026年10月30日時点に参照した資料。サービスへの実装・セキュリティ検証・見積もりは未実施。

  1. MDN — Same-origin policy：オリジンはスキーム・ホスト・ポートで判定され、パス差異は分離にならない。
  2. MDN — Web Storage API：localStorageは同一オリジンの文書間で共有される。
  3. AWS — CloudFront multi-tenant distributions：共通の配信設定・企業別ドメインの仕組み。
  4. AWS — CloudFront Cache Behavior：パス別オリジンとキャッシュ設定。
  5. AWS — Wildcard alternate domain names：サブドメインと証明書の範囲。
  6. AWS — CloudFront Functions restrictions：ネットワーク・リクエスト本文などの制約。
  7. AWS — OAC for Lambda function URLs：IAM・POSTハッシュ要件。
  8. AWS — Lambda Web Functions：Node.js Webアプリ・SSR。
  9. AWS — CloudFront Functions event structure：URI変更時のBehavior不変。
  10. AWS — Lambda Tenant isolation：企業別実行環境の隔離機能。
  11. AWS — S3 bucket-per-use / multi-tenant patterns：プレフィックス共有とバケット分割の判断。
  12. AWS — CloudFront OAC for S3：非公開S3オリジンの設定。
CloudFront・S3・Lambdaを用いた複数企業向けサイト公開基盤の設計メモ。事実は出典へ、推奨構成・段階分け・相対的な運用評価は本記事の設計判断。

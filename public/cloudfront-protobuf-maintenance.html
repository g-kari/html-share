CloudFrontでprotobufの
ハードメンテナンス応答を返す設計

同じAPI入口からprotobufのメンテナンス応答を返し、指定パスは通常経路へ通す。関数内のBase64変換を避ける条件で、AWSの選択肢と落とし穴を整理しました。

調査日: 2026年10月7日 UTC ／ 設計調査。AWS環境への変更・実機デプロイは行っていません。

目次結論と選び方指定パスを通常経路へ通す最初に決める応答契約構成比較GET: S3とFunctionsPOST: カスタムエラー別メンテナンスorigingRPC / gRPC-Webキャッシュと本文の保証ヘッダー・認証・CORS切替と復旧採用前の検証費用と残る不確実性一次資料

結論: バイト列はS3か専用originから出す

通常HTTPのGETなら、S3に事前生成したprotobufを置き、CloudFront Functionsでルーティングと503への変更だけ行う案が最小です。 POSTを含む場合は、ALBの固定503とCloudFrontカスタムエラーを組み合わせる案を検証するか、POSTを受けられる専用メンテナンスoriginへ切り替えます。ネイティブgRPCは別設計です。
  • 固定protobuf + GET: Functionsのviewer-requestでS3 originと専用URIを選び、S3の200本文をviewer-responseで503にする。本文は関数に入れない。
  • 固定protobuf + 通常HTTP POST: 既存ALBがあれば、最優先fixed-response 503 → CloudFront CustomErrorResponse → 別S3 originを候補にする。POSTでの実挙動を採用前に確認する。
  • POSTを含む複数methodで確実な制御が必要: 専用HTTP originがraw protobufと503を直接返す。通常アプリへの経路を使わず、リクエストmethodを変える必要もない。
  • ネイティブgRPC: gRPC対応originへ切替。通常のprotobufファイル＋HTTP503を正しいgRPC応答として扱わない。

どの案も「切替が全エッジへ反映済み」「通常キャッシュを返さない」「既存の処理中リクエストを扱う」「CloudFront以外の入口を塞ぐ」がそろって初めて、遮断対象への到達を止められます。指定パスを通常経路へ通す要件は次節で扱い、その場合の停止対象は非例外の機能・backendに限定します。

根拠: Functionsイベント仕様、origin変更、ALB fixed-response、CloudFront gRPC。これらを組み合わせた構成は設計提案であり、特定環境での動作保証ではありません。

指定パスだけ、メンテナンス中も通常経路へ通す

指定したパスを除外し、それ以外にprotobufメンテナンス応答を返す構成にできます。 ここでは「任意パスの貫通」を、あらかじめ指定したpathのメンテナンス除外という意味で扱います。利用者が任意の宛先originを選べる仕組みや、全pathの無条件開放ではありません。
元のpath・methodを確認→例外一致: 通常origin／非一致: メンテナンスorigin

第一候補: 通常経路とメンテナンス経路を先に分ける

  • CloudFront behaviorで分離: 例外のexact pathや境界付きprefixを、広い対象path・default behaviorより前へ置く。例外behaviorは通常origin・従来の認証等を維持し、maintenance書換関数を関連付けない。最初の一致が優先される。
  • 同一behavior内のFunctionsで分岐: viewer-requestの冒頭で、URIを書き換える前に例外を判定する。例外は通常originを選び、元のURI・method・query・必要な認証情報を維持する。非例外だけ前述のS3または専用HTTP/gRPC originへ送る。
  • return requestだけで十分とは限らない: そのbehaviorのorigin自体をメンテナンス用へ変更しているなら、例外側も selectRequestOriginById('normal-app-origin') 等で通常originを明示する。origin IDは固定の設定値とし、clientのqueryや任意headerから宛先を作らない。
  • FunctionsのURI変更ではbehaviorを切り替えられない: pathを例外用に書き換えて別behaviorへ移したつもりにせず、適用されるcache/auth/header policyを確認する。

根拠: CloudFront behaviorの順序・path条件、FunctionsのURI仕様、origin選択。組合せは設計提案です。

CloudFront behaviorの選択はpathベースであり、method別のroutingではありません。 「GET /healthzは通常経路、POST /healthzはメンテ応答」にしたい場合、behavior分離だけでは足りず、Functionsまたはoriginでmethod別の分岐が必要です。AllowedMethodsでPOSTを禁止することは、POSTをメンテナンスoriginへ送ることとは異なります。全methodを除外するpathと、特定methodだけを除外するpathを分けて設計します。

exactとprefixの境界を明示する

例外ルールの例。実際の許可pathやmethodを決めたものではありません。
例除外する範囲除外しない例
GET / HEAD + /healthzpathの完全一致。queryを条件にしない場合は /healthz?detail=1 も同じpath。/healthz-admin、/healthz/、POST /healthz。
POST + /webhooks/provider指定methodとpathだけ。既存のwebhook署名検証は維持。/webhooks/provider-test、GET /webhooks/provider。

startsWith('/api') や /api* は /api-admin 等まで広がり得ます。methodも含めて条件を定義し、OPTIONSが必要なら別途扱います。必要に応じhostnameも条件にし、同じdistributionの別aliasで意図せず例外にならないようにします。gRPCなら /package.Service/Method などRPC path単位で通常gRPC originへ通す設計が候補です。

Functionsでの例外判定例（判定だけの例）
function isExempt(request) {
  var path = request.uri;
  // 例では単純なcanonical pathだけを除外対象にする。
  // エンコード・曖昧な区切りは例外を広げず非例外扱い。
  if (/[%;\\]/.test(path) || /[\x00-\x20\x7f]/.test(path) ||
      path.indexOf('//') !== -1 || /(^|\/)\.{1,2}(\/|$)/.test(path)) {
    return false;
  }
  var read = request.method === 'GET' || request.method === 'HEAD';
  return (read && path === '/healthz') ||
    (request.method === 'POST' && path === '/webhooks/provider') ||
    (read && path.indexOf('/assets/') === 0);
}

// viewer-request内で、メンテナンス用URIへの書換より先に判定。
// isExempt(request)なら固定設定の通常originを選択し、requestを返す。
// 非例外だけ、method/protocolに適したメンテナンス経路へ送る。

この関数はpath正規化・認証・origin選択を完結させた本番コードではありません。例ではpercent encoding等を例外にしませんが、すでに正規化されたURIでは元の曖昧な表現を検知できない場合があります。各層で判定されるURI表現を確認し、次の境界・エンコード試験を行います。

path正規化とpercent encodingをまたいだ誤判定を防ぐ

CloudFrontはRFC 3986に沿ってpathを正規化してbehaviorを選び、その後originへraw URI pathを送ると説明されています。queryやcookieはbehaviorのpath pattern判定に含まれません。ALBのpath条件もURI normalization後に評価され、queryは別条件です。各層の見え方が同じとは仮定しません。

大文字・小文字、末尾slash、//、.、..、%2f、%2e、二重エンコード、backslash、path parameter等を試験します。decodeURIComponent() の追加だけで全層の解釈を統一したつもりにせず、decode回数・不正encodingの扱いを仕様化します。WAFのURL_DECODEやNORMALIZE_PATH等は検査文字列の変換なので、originへ渡るrequest自体の書換と混同しないこと。曖昧な表現は例外を広げず、既存API契約と整合した拒否・非例外扱いを設計します。

根拠: CloudFront path normalization、ALB条件、WAF text transformations。各encoding例の採用環境での結果は未実証です。

ALBとWAFにもメンテナンス遮断がある場合

ALB: 例外path＋必要methodのforward ruleを、残りをfixed-response 503にするruleより小さいpriority番号へ置く構成です。default ruleは最後。path条件と認証action・target groupを整合させ、例外forwardのために既存認証を落とさないようにします。CloudFront側でも遮断しているなら、両層で同じ例外が必要です。

ALBの概念例（priority番号は例）
10: 例外path + method → 従来の認証 + 通常targetへforward
20: それ以外のメンテ対象 → fixed-response 503
default: 従来の方針を監査して設定

WAFの概念条件
MaintenanceBlock = メンテ対象条件 AND NOT（例外path + method条件）

WAF: 「例外pathを先頭Allowにする」案は、Allowが終端actionで後続のSQLi・rate limit等のrule評価も止めるため注意が必要です。通常security ruleを保つには、メンテナンスBlockそのものの条件から例外を除外する設計を優先します。メンテナンス除外は最終的な許可ではなく、例外requestも従来のsecurity rule・default action・認証に従います。

既存のAllowがメンテナンスBlockより先に終端すると、非例外requestまでBlockを迂回し得ます。rule順序とdefault actionを監査し、security ruleを勝手に無効化したりdefault Allowへ変えたりしないこと。WAF、Functions、ALBでどの時点のpathを判定するかも実イベントで確認します。

根拠: ALB priorityとdefault rule、path/method条件、WAF終端action、WAF評価順、WAF AND、WAF NOT。

別behaviorにしても、globalカスタムエラーからは自動で独立しません。 CloudFrontのCustomErrorResponsesはdistributionの設定です。503を全体でメンテprotobufへ置換していると、例外の通常originが本来の503を返した場合も本文が置換され得ます。例外のstatus/bodyまで透過させるには、global503置換に依存しないFunctions＋専用maintenance origin、またはdistribution分離を検討します。behavior分離だけで解決したとは言えません。

根拠: DistributionConfigのCustomErrorResponses、カスタムエラー処理。

キャッシュと停止対象を、例外込みで定義する

  • 貫通の定義: 通常behaviorへ戻すだけなら既存cache hitを返す場合がある。毎回実originへ到達させる要件なら、例外APIのCachingDisabled等を個別に検討する。
  • 状態を混ぜない: 例外pathをメンテ用共通URIへ書き換えない。非例外は専用maintenance keyに分離し、warm/stale cache、例外リストの追加・削除、復旧時の残留を試す。
  • 全停止との関係: 例外を同じ通常アプリへforwardするなら、その機能が動くbackendは稼働させる必要がある。アプリ全停止と動的例外の成功応答は両立しないため、停止範囲を限定するか例外backendを分ける。
  • health check: ALBのtarget health checkはtarget group設定に従うtarget向けrequestで、viewer向けpath例外とは別に管理する。health endpointを公開例外にする必要性や、livenessとreadinessの意味も確認する。
  • 検証の合格条件: 非例外から停止対象への新規到達はゼロ、例外は指定path・methodだけ通常経路へ到達。例外originの200/4xx/503、認証失敗、WAF悪性request、prefixに似たpathも試す。

根拠: cacheとstale応答、TTL、ALB target health checks。停止範囲・追加試験はこの要件からの設計上の推論です。実際の例外pathは未指定であり、AWS設定は変更していません。

「関数内でBase64変換しない」と「通信上Base64にしない」は別です。 Lambda@EdgeやFunctionsで bodyEncoding/encoding=base64 を使う場合、設定・返却オブジェクトはBase64でも、クライアント向け本文はデコードされたバイナリにできます。今回の主案はその変換自体を避け、originの本文を通します。

根拠: Functionsのbody encoding、Lambda@Edge応答、gRPC HTTP/2 protocol、gRPC-Web protocol。クライアント側の挙動は利用ライブラリで要検証。

根拠と採用条件は以下の各案に併記。既存構成、認証方式、clientの応答契約を未確認のため、特定案を一律に断定しません。

GET: S3の本文をFunctionsでそのまま通す

GET /api/...→viewer-request: S3と専用URI→S3: 200 + raw .pb→viewer-response: 503
  1. メンテナンス用messageを一度だけシリアライズし、__maintenance/v1.pb などバージョン付きkeyでS3へ保存する。
  2. 非公開S3 originを既存distributionへ設定。OACでCloudFrontからのみ取得できるようにする。
  3. Functions runtime 2.0のviewer-requestで、selectRequestOriginById() と request.uri の両方を変更する。
  4. 同じbehaviorのviewer-responseで、メンテナンス用URIかつS3成功応答を確認して503と必要なヘッダーへ変更。body を設定しない。

現在のFunctionsはviewer-responseのstatus変更が可能です。Lambda@Edgeのviewer-responseには同じ権限がなく、混同しないこと。Lambda@Edgeを使うならorigin-responseでstatusだけを変え、本文を未変更で通す方法が別候補になります。

本文に触らないviewer-responseの最小例（構成説明用） 
function handler(event) {
  var req = event.request;
  var res = event.response;
  if (req.uri !== '/__maintenance/v1.pb' || res.statusCode !== 200) {
    return res;
  }
  res.statusCode = 503;
  res.statusDescription = 'Service Unavailable';
  res.headers['content-type'] = { value: 'application/x-protobuf' };
  res.headers['cache-control'] = { value: 'no-store' };
  res.headers['retry-after'] = { value: '60' };
  // bodyは設定しない。60秒は例で、運用方針に合わせる。
  return res;
}

本番でそのまま使う完結した設定ではありません。viewer-requestのorigin/URI切替、対象path、通常時条件、認証、CORS、Range・条件付きrequest、失敗時動作を別途構成・検証します。特にviewer-requestで変更したURIがviewer-responseのrequest.uriに現れることを実イベントで確認し、この判定条件が正しく動くことを試験します。

S3が200を返すことが前提です。 206の部分本文や304の本文なし応答を503の「完全なprotobuf」として返してはいけません。メンテナンスrequestでRange、If-Range、If-None-Match、If-Modified-Since、If-Match、If-Unmodified-Since等をどう扱うか決め、不要なものをviewer-request段階で除外する設計を検証します。S3の403/404/5xxはこのviewer-responseでは救済できません。

URIを変えてもbehaviorは再選択されません。S3へ切り替えても元API behaviorのcache policy・origin request policy・response headers policyが残るため、それらを監査します。またoriginだけを変えて同じcache keyを使うと、既存アプリの本文が返る可能性があります。

根拠: Functionsイベント仕様、origin helper、Lambda@Edge本文保持、Lambda@Edge制約、S3 GetObjectの条件付き取得、OAC。

POST: ALB固定503とCloudFrontカスタムエラー

通常HTTP POST→ALB fixed-response 503→CF CustomErrorResponse→別S3 .pb→viewerへ503

ALBの最優先メンテナンスルールを fixed-response にすると、ALBはclient requestをdropして固定応答を返し、アプリtargetへforwardしません。CloudFront側は次の設定を候補にします。

ErrorCode: 503
ResponsePagePath: /__maintenance/v1.pb
ResponseCode: 503
ErrorCachingMinTTL: 0

専用behavior /__maintenance/* のorigin: 非公開S3
対象API behavior: 通常キャッシュを使わない設定を検証

カスタムエラーはHTML専用の機能として定義されておらず、指定したobjectを別behaviorのoriginから取得して返す仕組みです。S3 objectにprotobufの生bytesと正しいContent-Typeを持たせます。ALBの固定応答自身は文字列本文・限られたContent-Typeに制限されるので、ALB単独で任意protobufを返す案にはしません。ALBのprotocol versionがgRPCまたはHTTP/2の場合、公式にはforward actionだけが対応するとされるため、fixed-response案の適用条件を確認します。

POSTについての確度: AWS公式の一般的なカスタムエラー仕様に通常HTTP POSTの除外は見つかりませんでした。ただし、元のPOSTに対してカスタムエラーobjectを取得する際の内部methodやヘッダー詳細は明示されていません。従って、この組合せを「POSTで実証済み」とは言えません。対象POSTで503・Content-Type・本文のbytes一致・アプリ到達ゼロを確認してから採用します。

WAFを使う場合

CloudFront側WAFの標準Block 403と、CloudFrontカスタムエラーによる別object返却はAWS公式で説明されています。ResponseCodeを503にすればメンテナンスstatusにできます。しかし、origin由来403も同じ置換の対象となります。WAFのCustomResponseを設定するとCloudFront側の置換より優先され、両者を合成できません。

  • WAFはキャッシュの前で遮断する使い方を検証できる一方、全403の意味を変える副作用に注意する。
  • CloudFrontのcustom error設定はdistribution単位。複数アプリを共有している場合は影響範囲を確認する。
  • ALB案ではCloudFrontのcache hitがALBへ行かない。固定503だけではメンテナンス応答の一律化にならない。

根拠: カスタムエラーの処理、カスタムエラー設定、ALB routing actions、ALB本文・Content-Type制限、WAFとの組合せ、WAF custom response優先順位。

別メンテナンスorigin: methodを変えずに応答する

GETとPOSTを同じ仕組みで扱う必要があるなら、専用originがraw protobufと503を直接返す設計が最も説明しやすい代案です。 既存のreverse proxy、独立した小さなHTTPサービス、あるいは以下のAWSサービスを使います。通常アプリ、DB、通常アプリの認証サービスに依存させないことが重要です。

CloudFront Functions→専用HTTP origin→503 + raw bytes + 全ヘッダー

Functionsでoriginを選び、origin側が受けたPOSTに対してそのまま固定応答を返せば、read-onlyのrequest.methodを変更する必要はありません。S3の静的object取得をPOSTで直接代用するのとは異なる構成です。originが503を返す場合、viewer-response関数は実行されないため、必要ヘッダーはoriginまたは検証済みのresponse headers policyで付けます。

通常Lambdaのresponse streaming

Lambda Function URLを RESPONSE_STREAM にし、HttpResponseStream.from() で503とヘッダーを指定して、事前生成protobufのBufferやファイルstreamを書き出す候補です。本文をJSONの body stringに包まないため、関数内でのBase64変換を避けられます。これは通常Lambdaの機能で、Lambda@Edgeには持ち込めません。

小さな専用処理のコードは必要です。managed Node.js runtime、対応Region、Function URLの認可とCloudFront OAC、アクセスログ、timeoutを確認します。OACで保護したFunction URLへPOST/PUTを送る場合、AWS公式はclientに本文のSHA-256計算と x-amz-content-sha256 ヘッダーを要求しています。 既存clientを変えず単純にoriginを差し替えられるとは限りません。Lambda公式はstreaming時の費用と、client切断後も実行時間が課金される点も注意事項として挙げています。ネイティブgRPCを返す用途としては扱いません。

API Gateway RESTのS3 service integration

frontendのPOST等を、AWS service integrationのS3 GET に接続する候補もあります。S3成功をmethod responseの503へ対応させ、binary media types・Accept・contentHandling・ヘッダーmappingを設定します。Lambdaを使わない構成ですが、追加のAPI Gateway、IAM role、料金・設定・デプロイ管理が必要です。

AWSにはS3からraw bytesを返す公式例と、binary payloadの変換表、integration responseのstatus mappingの仕様があります。これらを合わせたメンテナンス構成は未実機検証です。特に複数Acceptでは先頭のmedia typeが使われるため、*/* やブラウザのAcceptも試します。本文にJSON/VTLテンプレートを適用してbytesを壊さないこと。

根拠: viewer-responseの実行条件、任意HTTP origin選択、Lambda streaming仕様、streaming tutorial、Function URL OAC、API Gateway + S3 binary、binary変換表、integration response。

避けたい近道

  • edge関数から空503を返してCFカスタムエラーに任せる: Functionsが返した400以上には同statusのcustom error pageが適用されないと公式に明記されている。
  • origin failoverでメンテナンスへ移す: primaryへ先にアクセスし、POSTにはfailoverしない。ハードメンテナンスの遮断スイッチにならない。
  • 302等でS3へredirect: 同じAPIの503本文という契約から外れ、method・認証・CORSも変わり得る。
  • S3 metadataだけで503にする: Content-TypeやCache-Controlは設定できるが、通常の成功GetObjectのstatusをmetadataだけで503にできない。
  • Lambda@EdgeでS3をSDK取得しBufferをbodyに入れる: 応答モデルはtext/base64。任意bytesをそのまま返す型ではない。

もし条件が「リクエストごとにエンコードしない」だけなら、ビルド時のBase64定数をedge関数へ埋め込む別案はあります。ただし関数の応答オブジェクトにはBase64が残るため、今回の主案には含めません。

根拠: Functions直返しエラー、Lambda@Edge応答モデル、origin failover制約、S3 metadata。

gRPCとgRPC-Webは、別の応答を作る

ネイティブgRPC

CloudFrontはHTTPSのgRPC originへリクエストをproxyします。HTTP/2とPOSTの許可、およびgRPC有効化が必要です。gRPCリクエストはキャッシュ設定の影響を受けず、CloudFront Functionsは利用できます。一方、CustomErrorResponse、origin failover、Lambda@Edge、Origin Shieldは非対応です。

メンテナンス用gRPC originを用意し、Functionsでそちらへ切り替える候補です。gRPC frameworkで UNAVAILABLE（grpc-status 14）等の適切なRPCエラーを返します。即時失敗ならtrailers-only応答もprotocol上可能です。HTTP503を返すだけでは、clientがtransport errorを合成する結果になり、用意した裸protobufを通常のRPC messageとして読むとは限りません。

protobufの詳細エラーを grpc-status-details-bin へ入れる場合は、protocol上のbinary metadataとしてBase64が必要になります。「どの層でもBase64を使わない」という条件なら、その詳細の伝え方まで再設計が必要です。RPC応答messageの生protobufとは異なる位置の情報です。

gRPC-Web

binary modeでもmessage frameと末尾のstatus/trailersフレームが必要です。text modeはBase64を使います。したがってS3に裸の .pb を置いてContent-TypeだけgRPC-Webへ変えても、正しい応答にはなりません。

専用gRPC-Web対応originまたはproxyがエラー応答とCORSを返す案を優先します。binaryで事前生成した「完全なgRPC-Web応答」を静的に返す可能性はありますが、利用client・mode・trailers-only処理・HTTP statusの挙動を実証する必要があります。今回確認したAWS公式gRPCページはネイティブgRPCについての説明であり、gRPC-Webに同じ機能・制約が適用される保証としては使いません。

根拠: AWS CloudFront gRPC、gRPC公式HTTP/2仕様、gRPC-Web公式仕様。gRPC-WebのAWSでの経路判定は未実証。

キャッシュが最大の落とし穴

ALBを503にしても、CloudFrontに通常200が残っていればメンテナンス本文へ切り替わりません。 fresh cache hitはALBを迂回します。期限切れの通常objectでも、originが5xxを返すと古いobjectを返す挙動があります。
  • GETのFunctions案: viewer-requestでキャッシュ検索より前にメンテナンス専用URIへ変更し、通常keyと分離する。origin変更だけで済ませない。
  • APIをキャッシュしない設計: 対象behaviorのCachingDisabledを検討。既存object、設定の反映、invalidationsの扱いまで検証する。
  • カスタムエラー案: error TTLとobjectのcache TTLは別。ErrorCachingMinTTL=0、専用error behavior、既存キャッシュの排除をセットで考える。
  • 503のno-store: 通常のerror cachingではno-storeだけでTTL0を保証しない。S3 originでキャッシュ有効の場合、error TTL0でも最低1秒の例外がある。CachingDisabledを使う場合は、公式の非キャッシュ扱いと実構成を確認する。
  • response headers policyのno-store: viewer向けヘッダーだけ。CloudFront自身のcacheを制御するものではない。
  • cache policyのMinimum TTL: 正の値ならno-store等を無視して最低その期間保持する。正常APIにも漏れないか確認する。

「bytes一致」の意味も決める

JSON、UTF-8再符号化、不要なBase64、圧縮、レスポンステンプレートによる変換を避けます。HTTPのchunked transferやHTTP/2 framingは本文の転送形式でありprotobufへの追加データではありません。gzip等のContent-Encodingを許可するなら、復号後の本文一致とwire上の完全一致を区別します。厳密なwire-body一致を求める検証では自動圧縮を無効にし、Accept-Encoding: identity を使います。

Range・条件付き取得、ETag、Content-Length、Content-Encodingも整合させます。手で元のContent-Lengthを流用したり、S3のXMLエラーにprotobuf Content-Typeを付けたりしないこと。複数schema・言語・バージョンを返す場合は、その選択もcache keyに含めます。

根拠: fresh/staleと5xxの処理・CachingDisabled、error cache TTL、通常objectのTTL、response headers policy、S3 GetObject。

通常APIの認証がALBやアプリで動くなら、メンテナンスoriginへ切替するとその処理は通りません。汎用的な「メンテナンス中」という本文だけを未認証で返してよいか、認証済みの場合だけ返すかを決めます。情報を最小限にし、ユーザー名・内部状態・復旧作業の秘密を固定本文へ入れません。

S3はOACで非公開を維持し、必要なobjectのGetObjectだけを許可する設計にします。origin request policyとOAC signing modeを監査し、ユーザーのAuthorization、Cookie、query情報を静的originへ不用意に流さないこと。署名付きURL/cookieや認証を使う場合は、その判定を壊すような一律のヘッダー・cookie削除を行わず、評価順序と要件を実測します。

ブラウザではOPTIONS preflightが成功しないと、本リクエストや503本文をJavaScriptが読めない場合があります。許可済みOrigin・method・headerに対して、アプリへ行かず204等のpreflight応答を返す別分岐を作る設計が候補です。Cookie付きCORSでwildcard originを安易に使わず、Retry-AfterをJSから読むならExpose-Headersも確認します。

根拠: S3 metadata、OAC、response headers policy、policyのCORS設定。認証・ブラウザclientの適合性は個別検証対象。

切替と復旧の順序

  1. 準備: protobuf fixtureとSHA-256、専用origin、必要policy、ルール、通常時に無効な切替分岐を先に準備する。復旧時の元設定も保存する。
  2. 事前試験: 非本番または限定した検証経路でcache hit/miss、POST、CORS、認証、異常系を確認する。
  3. 遮断を有効化: edge routingまたはALB/WAFルールを切替。必要なcache invalidation等も実施する。
  4. 反映待ち: distributionはDeployedを確認。WAFは数秒〜数分の一時的な不整合があり得る。複数地点からの実応答とアクセスログを確認する。
  5. drainと停止: 新規アプリ到達が止まったことを確認して、処理中HTTP request・既存gRPC stream・background jobを適切にdrain。必要なら別途停止する。
  6. 復旧: アプリの準備・health checkが整ってから通常経路へ戻す。反映完了、通常200、残ったメンテナンスcache、CORS・認証を確認する。

routingの変更は、既にoriginへ送った処理や開いているstreamを取り消しません。CloudFront以外の直ALB URL、別distribution、内部API、ジョブ、webhookも別の入口です。DB変更を伴う停止ならそれらも対象にし、maintenance originから通常アプリへ自動failoverしない構成にします。

無停止・即時・全世界同時のスイッチとして扱わず、切替窓と復旧窓を運用手順に入れます。KeyValueStore等を切替に使う場合も、同期反映を前提にせず、障害時の既定動作を定義・検証します。

根拠: CloudFront Deployedの意味、WAF更新時の伝播。drainと別入口の監査はハードメンテナンス要件からの設計上の推論です。

費用と残る不確実性

  • Functions + S3: Functions呼出し、CloudFront配信、S3保管・GET等が費用要素。request/responseの両方を使う場合の呼出し量を見積もる。
  • ALB/WAF: 既存資源の利用と、新規追加を分ける。ALBの時間・LCU、WAFのACL/rule/request等、S3とCloudFrontの費用を確認。
  • Lambda streaming: request・実行時間・streaming等の費用。短い固定本文のためだけなら、運用の簡素さと比較する。
  • API Gateway / 専用origin: API requestやサーバーの費用、IAM、ログ、デプロイ管理が増える。

金額はRegion、プラン、既存契約、request量、cache hit率で変わるため、ここでは総額や「無料」を断定しません。CloudFront、S3、ALB、WAF、Lambda、API Gatewayの公式料金を実構成で確認します。

今回の到達点: 現行の一次資料から実現方式・禁止される近道・検証条件を整理しました。実際のdistribution、ALB、APIのmethod、protobuf schema、認証、clientを調べた結果ではありません。特に通常HTTP POSTのCustomErrorResponse、error pathのpolicy適用、gRPC-WebのCloudFront経路、API Gateway案の統合挙動は実機確認が残ります。

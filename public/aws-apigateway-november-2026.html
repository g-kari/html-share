Amazon API Gateway 2026年11月の発表まとめ：REST APIのJWTオーソライザーとAPI Portal

確認日：2026年11月25日
一次資料：AWS公式 What's New（2026年11月1日〜24日の投稿）と、Amazon API Gateway開発者ガイドなどの公式ドキュメント。各項目の詳細は公式発表とドキュメントへのリンクつきです。全体の索引はAWS 2026年11月の発表まとめ。

要点
  1. 11月17日、REST APIにネイティブのJWTオーソライザーが追加されました。Cognito以外のOIDC／OAuth 2.0のIdPのトークン検証が、Lambdaオーソライザーを書かずに設定だけでできるようになりました。

概要

Amazon API Gatewayは、REST API、HTTP API、WebSocket APIを作成・公開・運用するためのマネージドサービスです。2026年11月のAPI Gateway関連の発表は、認可と棚卸しの2方向でした。認可では、REST APIがトークン検証の新しいオーソライザータイプ「JWT」を得ました。棚卸しでは、組織内のAPIを自動で見つけ出す新機能「API Portal」がAPI Gatewayの機能として追加されました。API Portalが見つける対象はAPI Gateway自身のAPIだけではなく、Application Load BalancerとCloudFrontの背後にあるAPIも含みます。

分野別のまとめでは、JWTオーソライザーはネットワーク・CDN記事に、API Portalを含む2件はWAF記事に分かれて載っていたため、この記事に集約し、公式ドキュメントで補って詳しくします。

REST APIのJWTオーソライザー（11月17日）

公式発表。REST APIに、JSON Web Token（JWT）をゲートウェイ自体が検証するネイティブのJWTオーソライザーが追加されました。これまでREST APIの組み込みオーソライザーが受け付けたのはAmazon Cognitoのトークンだけで、それ以外のOpenID Connect（OIDC）やOAuth 2.0のIDプロバイダ（IdP）のトークンを検証するには、署名鍵の取得と検証、IAMポリシーの返却を行うLambdaオーソライザーを自分で書いて運用する必要がありました。今回の追加で、トークン検証はコードではなく設定で宣言する形になりました。

検証の手順は公式ドキュメントに明記されています。API Gatewayは、設定したアイデンティティソース（通常は Authorization ヘッダー）からトークンを読み、まず iss クレームが設定済みの発行者と一致するかを見ます。未知の発行者のトークンは、ネットワーク呼び出しの前に拒否されます。次に、許可した署名アルゴリズムかどうかを確認し、発行者の公開鍵で署名を検証します。公開鍵は、発行者が /.well-known/openid-configuration に公開するOIDC発見文書（ディスカバリドキュメント）経由で取得し、最大1時間キャッシュします。見たことのない kid の鍵で署名されたトークンが来たら、鍵セットを取り直します。続いて aud（Cognitoのアクセストークンでは代わりに client_id）と、exp／nbf／iat の時刻クレームを検証します。時刻のずれは60秒まで許容されます。その後、発行者ごとに設定した追加クレームのルールを評価し、メソッドが要求するスコープがトークンの scope または scp クレームに1つでも含まれているかを確認します。検証済みのクレームは $context.authorizer.claims で統合へ渡ります。

失敗時の応答も分かれています。トークンがない、形式が不正、期限切れ、信頼できない発行者といった場合は 401 Unauthorized です。トークン自体は有効でも、必要なスコープを持たない、または追加クレームのルールに合わない場合は 403 Forbidden になります。発行者の鍵エンドポイントに到達できず、キャッシュ済みの鍵もない場合は、リクエストを通さず 5xx を返します（公式ブログの説明）。

設定の上限と規則も公式ドキュメントで確認できます。信頼する発行者は1つのオーソライザーに最大10件まで登録でき、IdPの移行期間に旧・新の発行者を併用するような使い方ができます。発行者ごとに、受け付けるaudienceは最大100件、追加クレームのルールは最大10件まで設定できます。クレームルールは SINGLE_STRING 形式で、期待値は1つだけ、完全一致（大文字・小文字も区別）で評価します。トークン側のクレーム値が配列だとルールに一致せず 403 になります。対象にできないクレームは iss、aud、exp、nbf、iat、scope、scp です。

署名アルゴリズムはRS256、RS384、RS512、ES256、ES384、ES512に対応し、許可するものを defaultAlgorithms（必須）で宣言します。HMAC系（HS256など）と alg: none のトークンは拒否されます。発行者のURLは、トークンの iss と末尾のスラッシュまで含めて完全一致させる必要があり、絶対HTTPS URLで、クエリ文字列やフラグメントは付けられません。発見文書と鍵セットは、プライベートREST APIの場合でも、パブリックインターネットから到達できる場所に公開されている必要があります。

作成はコンソール、AWS CLI、CloudFormation（AWS::ApiGateway::Authorizer の JwtConfiguration）、OpenAPI定義（x-amazon-apigateway-authorizer で type: jwt）のいずれでもできます。オーソライザーやメソッドの変更は、ステージへ再デプロイして初めて反映されます。対象はRegional、エッジ最適化、プライベートの各REST APIで、提供範囲は全商用リージョンとAWS GovCloud（US）です。JWTオーソライザー自体の追加料金については、公式発表とドキュメントに明記を確認できなかったため未確認です。認可結果のキャッシュ（Lambdaオーソライザーにあるような結果キャッシュ）についても、REST API版のドキュメントに記載は確認できませんでした。

既存のオーソライザーとの使い分けは、公式ドキュメントの比較表が基準になります。JWTオーソライザーは、1つ以上のOIDC／OAuth 2.0 IdP（Cognitoユーザープールを含む）のトークン検証に向きます。Cognitoユーザープールオーソライザーは、利用者がCognitoユーザープールにいて、プールの全アプリクライアントのトークンをクライアントIDの列挙なしで受け付けたい場合の選択肢です。Lambdaオーソライザーは、JWTオーソライザーでは評価できないクレームの確認や、JWT以外の資格情報など、カスタムの認可ロジックが必要な場合に使います。公式ブログも、トークンのイントロスペクション（失効確認など）が必要な場合はLambdaオーソライザーが適切だとしています。

HTTP APIには以前からJWTオーソライザーがありましたが、別物です。HTTP API版は発行者が1つだけで、対応する署名アルゴリズムはRSA系のみ、公開鍵のキャッシュは最大2時間（ベストエフォート）です。今回のREST API版は、発行者を複数持てること、EC系の署名にも対応することが主な違いです。

API Portal：APIの自動発見と棚卸し（11月23日）

公式発表。API PortalはAmazon API Gatewayの新機能で、API Gateway、Application Load Balancer、Amazon CloudFrontの背後で動いているAPIを自動で発見し、継続的に更新される台帳（APIインベントリ）を作ります。対象は1つのAWSアカウント、またはAWS Organizationsの組織全体です。発見はトラフィックログとサービス設定レコードから行い、エージェントの導入も、ログの転送も、トラフィックの経路変更も要りません。発見自体は読み取り専用で、API側の設定は変わりません。

台帳でのAPIの単位は、フロントドアのリソース上の「HTTPメソッドとURIパス」です。たとえば GET /v1/payments が1行になります。API Gatewayの RestApi リソースとは単位が違い、1つのREST APIは通常、メソッドとパスの組み合わせごとに複数行として現れます。同じAPIが複数の入口（例：CloudFront配下のREST API）から到達できる場合は、入口ごとに行が分かれます。

発見のされ方は入口ごとに異なります。API GatewayはREST APIだけが対象で、設定（AWS Configの構成アイテム）とトラフィックの両方から発見します。HTTP APIとWebSocket APIは発見されません。リテラルなパスに明示されたメソッドは、リクエストがなくても台帳に現れます。一方、ANY メソッドや /{proxy+} のような貪欲（greedy）なパスは設定からは発見されず、実際に呼ばれた具体的なメソッドとパスの形で、トラフィックの後に現れます。Application Load BalancerとCloudFrontはトラフィックからのみ発見するため、リクエストを受けていないエンドポイントは台帳に現れません。CloudFrontはグローバルサービスのため、発見はバージニア北部（us-east-1）リージョンでのみ行われます。新しいAPIが台帳に現れるまでには通常数時間かかり、発見を初めて有効にした場合は最大24時間見ておく必要があります。APIを削除したりトラフィックが止まったりしても、その行は約30日間台帳に残ってから消えます。

分類の定義も公式ドキュメントにあります。発見されたAPIはすべて「シャドウAPI」から始まります。これは、実在して到達できるのに、組織の管理下に置かれていない状態です。台帳から昇格させたAPIが「管理対象API」で、セキュリティ態勢の評価対象になり、後述のドキュメントポータルにも載せられます。管理対象APIのうち、30日間トラフィックがなく、かつ裏付けリソースの設定変更が90日間ないものは「ゾンビAPI」として示されます（両方の条件が必要です。トラフィックが戻れば表示は消えます）。所有アカウントが組織を離脱した、または閉鎖された管理対象APIは「孤立API」で、台帳には最後に分かった状態が残りますが、再発見も所見の更新もされません。

管理対象APIについては、セキュリティ態勢が評価されます。評価項目は認証、リクエスト検証、スロットリング、TLSバージョン、AWS WAF保護などで、結果は所見として報告されます。WAF保護が付いていないAPIも所見に含まれます。AIエンドポイントの識別を有効にすると、トラフィックに現れるプロトコルから、MCPサーバ、A2Aサーバ、LLM向けのAPIといったAI向けエンドポイントも識別します。

API Portalには、発見とは別の顔としてドキュメントポータルもあります。管理対象APIを「製品」にまとめ、API定義から生成したリファレンスページと自作ドキュメントを載せたポータルサイトとして公開する機能です。既存の「API Gateway Portals」（API Gatewayで作ったAPI専用の開発者ポータル）とは別リソースで、現時点では移行手段はありません。既存のポータルは従来の料金のまま動き続け、API Portal内の「Documentation portals」から管理します。

料金は2本立てで、1つのAPIが両方で課金されることはありません。発見は、発見されたAPIの数×月で、発見を有効にしたアカウント（組織全体の場合は管理アカウント）に、発見を有効にしたリージョンごとに月額の最低料金付きで課金されます。ドキュメントポータルはポータル数×月で、含まれるAPI数を超えた分はAPI単位の追加課金です。具体的な単価はAPI Gatewayの料金ページで確認してください。提供範囲は東京を含む32リージョンです。API Portalには apiportal という専用のAPI名前空間があり、CLIでは aws apiportal として操作します。

WAFとの連携：保護はWAFのマネージドルールが担う（11月23日）

API Portalは発見と評価までで、攻撃を止める保護自体はAWS WAFが担います。同日発表の2件がその保護側です。詳細はWAF記事にまとめているため、ここではAPI Gateway側との関係に絞ります。

API security with WAFでは、WAFのAPI Securityマネージドルールグループが、悪用されやすいAPI攻撃の分類を担います。リクエスト内のレコードIDを差し替えて他人のデータを読むBOLA（オブジェクトレベル認可の不備）、トークンの偽造や盗まれたパスワードの大量試行を含む認証破りとクレデンシャルスタッフィング、隠れたルートの推測や公開ドキュメントの探索による偵察・列挙の3分類です。WAFが検出したイベントはAPI Portalの所見に統合され、管理対象APIの詳細画面で、態勢の所見と実際に検出された脅威をあわせて見られます。

AIエンドポイント向けの発表では、API Portalの発見範囲にLLM、MCP、A2Aのエンドポイントが含まれます。未文書化のまま公開されているMCPサーバは、シャドウAPIとして台帳に現れます。保護はWAFのAI Securityマネージドルールグループが担い、MCPとA2Aのプロトコル認識と準拠チェックで不正な形式のメッセージを止めます。内容検査を有効にすると、Amazon Bedrock Guardrailsの InvokeGuardrailsCheck APIを呼び、プロンプトインジェクションやジェイルブレイクの試み、リクエスト内の有害コンテンツ、レスポンス内の機微情報を検出します。この内容検査には追加料金がかかり、Bedrock側の料金も別にかかります。AI Securityの提供は東京を含む7リージョンです。
